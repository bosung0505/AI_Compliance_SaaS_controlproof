# ControlProof Constitution

## Core Principles

### I. 판정은 증적에서만 나온다

- 모든 PASS와 FAIL은 기대 결과, 실제 관찰값, 원본 증적을 연결해야 한다.
- 필수 증적이 없거나 읽을 수 없거나 서로 모순되면 PASS로 추정하지 않고 `INCONCLUSIVE`로 판정해야 한다.
- 저장된 증적에는 최소한 Run, 시나리오, 시험 대상, 수집 출처, 수집 시각, 실행 구간, 단계, 시도 횟수와 무결성 해시가 연결되어야 한다.
- 화면 요약이나 판정 문구만 저장한 결과는 완료된 검증으로 인정하지 않는다.
- ControlProof는 법적 준수 전체를 자동 인증한다고 표현해서는 안 된다. 제품이 주장할 수 있는 범위는 실행한 시나리오와 확보한 증적까지다.

근거 없는 낙관적 판정을 막는 것이 제품 신뢰성의 출발점이다.

### II. 시험 대상·실행 준비·실행 결과를 분리한다

- WhyYou에 시험할 통제나 기능이 존재하는지, ControlProof가 그것을 실행할 준비가 되었는지, 실행 결과가 무엇인지를 서로 다른 상태로 관리해야 한다.
- 대상 기능이 없을 때만 `NO_TEST_TARGET`을 사용해야 한다.
- 대상은 있으나 실행기·어댑터·장애 주입기가 준비되지 않았으면 `RUNNER_NOT_READY`, 권한이나 접근이 막혔으면 `ACCESS_BLOCKED` 또는 판정 시 `ACCESS_LIMITED`로 표시해야 한다.
- 아직 실행하지 않은 상태는 `NOT_RUN`이며, 증적 부족·충돌에 따른 `INCONCLUSIVE`와 같지 않다.
- 실행기 장애, 중단 또는 복구 실패를 WhyYou 통제의 FAIL이나 PASS로 바꾸어서는 안 된다.

실행할 수 없음과 제품이 실패함은 전혀 다른 사실이며, 이 구분은 UI·API·보고서에서 동일해야 한다.

### III. 사람의 최종 결정 권한을 보존한다

- WhyYou의 AI 점수와 리포트는 참고 정보이며 합격·탈락 임계값으로 사용해서는 안 된다.
- 최종 채용 결정은 권한 있는 `COMPANY_USER`만 수행할 수 있어야 한다.
- AI 어시스턴트, 워커, 시스템 주체 또는 직접 API 우회가 최종 채용 상태를 변경할 수 없어야 한다.
- 더 낮은 AI 점수의 지원자가 사람의 종합 판단으로 채용될 수 있고, 더 높은 점수의 지원자가 채용되지 않을 수 있어야 한다.
- ControlProof의 합성 점수는 사람 판단의 독립성을 시험하기 위한 입력일 뿐 자동 결정 규칙을 뜻하지 않는다.

기능 Spec과 테스트가 점수 경계값 기반 자동 합격·탈락을 전제로 삼으면 이 원칙을 위반한다.

### IV. 시나리오는 데이터로, 제품 연결은 어댑터로 둔다

- 시나리오의 의도, 전제조건, 단계, 기대값, 필요한 증적과 판정 규칙은 버전 관리되는 데이터로 표현해야 한다.
- WhyYou의 API, DB, 로그, 브라우저와 메시지 큐 연결은 어댑터 경계 뒤에 두어야 한다.
- 판정 엔진은 WhyYou 내부 구현 상세나 특정 화면 셀렉터에 직접 의존해서는 안 된다.
- 시나리오 변경은 가능한 한 시나리오 정의와 어댑터 설정 변경으로 수용하고, 핵심 실행·증적·판정 모델의 전면 재작성으로 이어져서는 안 된다.
- 새 서비스를 검증할 때는 공통 엔진을 유지하고 서비스별 어댑터와 capability map을 교체하는 것을 기본으로 한다.

이 원칙은 WhyYou 데모에 묶인 일회성 스크립트가 아니라 다른 AI 서비스에도 확장 가능한 제품을 만든다.

### V. 시험은 격리되고 결정론적이며 복구 가능해야 한다

- 실제 지원자 개인정보나 운영 채용 결정을 시험 데이터로 사용해서는 안 된다.
- 모든 시험은 합성 데이터, 테스트 계정과 격리된 로컬 또는 명시적 테스트 환경에서 실행해야 한다.
- 외부 LLM 호출은 MVP에서 고정 결과 대역으로 대체하여 같은 입력과 상태에서 재현 가능한 결과를 만들어야 한다.
- 장애·누락·우회 주입은 테스트 환경에서만 활성화되고, 기본적으로 비활성화되며, 실행 ID와 허용 목록으로 제한되어야 한다.
- 장애 시험은 복구 단계를 반드시 가져야 하며, 복구 실패 시 위험 상태를 표시하고 수동 확인 전 후속 장애 시험을 차단해야 한다.
- 비밀값과 개인정보는 저장 전에 제거하거나 마스킹해야 한다.

ControlProof 자체가 새로운 운영 장애나 개인정보 위험을 만들지 않는 것이 기능 완료보다 우선한다.

### VI. 실행 결과는 불변이며 재시험은 계보로 연결한다

- 최초 실행의 FAIL, INCONCLUSIVE와 증적을 수정 후 결과로 덮어써서는 안 된다.
- 재시험은 새로운 Run으로 생성하고 `parent_run_id` 또는 동등한 계보 필드로 이전 Run과 연결해야 한다.
- Run은 시나리오 버전, 대상 서비스 버전, 정책·평가 기준·모델·프롬프트·설정 버전을 가능한 범위에서 동결해 기록해야 한다.
- 중단되거나 복구에 실패한 Run도 삭제하지 않고 실행 상태와 확보된 증적을 보존해야 한다.
- FAIL→수정→PASS 데모는 두 결과와 차이를 동시에 보여줘야 하며 PASS만 남겨서는 안 된다.

변화의 증명이 제품 가치이므로 과거 결과의 보존은 선택 기능이 아니다.

### VII. 명세에서 증적까지 추적 가능해야 한다

- 구현 전에 사용자 이야기, 범위, acceptance criteria와 필요한 증적을 기능 Spec에 작성해야 한다.
- 각 acceptance criterion은 하나 이상의 시나리오 assertion, 구현 task와 테스트에 연결되어야 한다.
- 각 최종 verdict는 어떤 요구사항과 assertion을 검증했는지 역추적할 수 있어야 한다.
- 기술 편의를 위해 제품 의미를 바꾸면 안 되며, 의미 변경은 먼저 Product Brief·결정 기록·Spec 중 해당 문서를 수정해야 한다.
- 구현 코드는 승인된 Spec과 Plan 없이 추가하지 않는 것을 원칙으로 한다. 탐색용 spike는 제품 코드와 분리하고 제품 계약으로 간주하지 않는다.

명세·코드·실행·증적이 한 사슬로 연결되어야 팀과 외부 검토자가 같은 결과를 설명할 수 있다.

## 제품 경계와 데이터 안전

### MVP 검증 범위

- 검증 대상 서비스는 WhyYou다.
- 시나리오 범위는 N-01~N-03, H-01~H-03, E-01~E-03이다.
- A-01~A-03은 WhyYou에 이의제기 기능이 없으므로 신규 구현하지 않고 `INCONCLUSIVE: NO_TEST_TARGET`로 보고한다.
- CSV 대량 업로드 경로는 WhyYou 저장소에 독립 경로가 없으므로 별도 시나리오로 만들지 않는다. 합성 지원자 생성에는 기존 batch API를 사용한다.
- ControlProof는 AI 모델 정확도·편향 평가, 법령 전체 자동 판정, 운영 모니터링 대시보드 또는 인증서 발급 제품이 아니다.

### 허용되는 변경

- ControlProof 실행기, 판정 엔진, 어댑터, 증적 저장, 보고 화면과 테스트 전용 장애 주입·상태 시드는 구현할 수 있다.
- WhyYou의 실제 실패를 확인한 뒤 보호조치를 수정할 수 있으나, 최초 실패 Run을 먼저 보존해야 한다.
- 테스트 편의를 위해 추가한 endpoint나 fault hook은 테스트 환경에서만 사용할 수 있어야 하고 운영 기본 경로와 명확히 구분해야 한다.

### 금지되는 변경

- WhyYou에 없는 이의제기 기능을 MVP 통과를 위해 새로 구현해서는 안 된다.
- ControlProof가 WhyYou 대신 최종 채용 결정을 내려서는 안 된다.
- 증적이 없는 항목을 UI에서 녹색 PASS로 표시해서는 안 된다.
- 장애 주입 기능이 운영 환경에서 일반 사용자의 호출로 활성화되어서는 안 된다.

## 공통 데이터·상태 계약

### 실행과 관찰

- 하나의 Run은 한 시나리오의 한 번 실행이다.
- 한 Run은 여러 합성 시험 대상을 포함할 수 있으나 모든 관찰과 증적은 `subject_ref`를 가져야 한다.
- 관찰값은 `phase`, `step_id`, `attempt`를 가져야 한다.
- `phase`는 MVP에서 `BASELINE`, `INJECTED`, `RECOVERED`를 사용한다.
- 시간 변화는 증적 충돌이 아니다. 같은 Run·대상·구간·단계·시도의 같은 사실을 표현해야 하는 값이 모순될 때만 `EVIDENCE_CONFLICT`가 성립한다.

### 실행 상태와 판정

- Run 실행 상태는 `PENDING`, `RUNNING`, `RESTORING`, `COMPLETED`, `ABORTED`, `RESTORE_FAILED`를 사용한다.
- 시나리오 표시 결과는 `PASS`, `FAIL`, `INCONCLUSIVE`, `NOT_RUN`을 구분한다.
- 판정 불가 reason code는 `NO_TEST_TARGET`, `ACCESS_LIMITED`, `INSUFFICIENT_EVIDENCE`, `EVIDENCE_CONFLICT`를 사용한다.
- 실행 준비 상태는 `READY`, `RUNNER_NOT_READY`, `ACCESS_BLOCKED`, `NO_TEST_TARGET`을 사용한다.
- 문서·YAML·API·코드·화면은 이 명칭을 동일하게 사용해야 하며 임의의 별칭을 추가해서는 안 된다.

### 증적 보존

- 판정에 사용한 최소 원본은 Run 증적 저장소에 보존하고 원본 locator도 함께 남긴다.
- 전체 로그나 데이터베이스 전체 덤프는 수집하지 않는다.
- 모든 저장 증적은 SHA-256, 수집 시각, MIME 유형과 크기를 가져야 한다.
- 전자서명과 공인 시점확인은 MVP 범위 밖이다.

## 개발 흐름과 품질 게이트

### 명세 순서

모든 기능 작업은 다음 순서를 따라야 한다.

1. Product Brief와 결정 기록에서 제품 의미를 확인한다.
2. 기능 Spec에 사용자 이야기, 범위, acceptance criteria, 실패·판정 불가 조건과 필요한 증적을 작성한다.
3. 모호함을 해소하되 이미 확정된 제품 결정을 구현 편의를 이유로 재개방하지 않는다.
4. Plan에서 adapter 경계, 데이터 계약, 안전장치, 마이그레이션과 시험 전략을 정한다.
5. Tasks를 요구사항·acceptance criterion 단위로 연결한다.
6. 구현 후 정적 검사, 단위 테스트, 계약 테스트와 대표 end-to-end 실행을 수행한다.
7. 결과와 증적을 검토한 뒤 완료 처리한다.

### 첫 수직 흐름

- 첫 구현은 H-03의 최소형인 `리포트 생성 실패 주입 → 담당자 화면에서 부재 확인 → 결정 안전성 확인 → 복구 → 증적과 판정 생성`을 끝까지 연결해야 한다.
- 첫 수직 흐름이 안정된 뒤 재시도 소진·DLQ와 E-03 멱등성 검증을 추가한다.
- DLQ 검증은 첫 수직 흐름에서는 후속이지만 최종 2주 MVP 완료 범위에는 포함된다.
- 동일 요청 재전송 시 이벤트·결정 이력의 중복·누락은 E-03이 소유하며, H-03은 리포트 부재 상태의 결정 안전성을 소유한다.

### 필수 품질 게이트

- 핵심 판정 로직은 단위 테스트와 고정 fixture를 가져야 한다.
- WhyYou 어댑터는 접근 성공, 권한 거부, 대상 부재와 일시 장애를 구분하는 계약 테스트를 가져야 한다.
- N-01은 PC와 모바일 viewport 각각에서 화면 증적을 수집해야 한다.
- 장애 시나리오는 주입 성공과 복구 성공 또는 실패를 모두 증적으로 남겨야 한다.
- 대표 흐름은 최초 FAIL과 수정 후 PASS를 별도 Run으로 재현해야 한다.
- 실제 개인정보 없이 전체 데모가 가능해야 한다.
- Constitution 위반이 남은 기능은 일정상 동작하더라도 완료로 표시해서는 안 된다.

## Governance

### 문서 권한과 우선순위

이 Constitution은 개발 방식과 공통 품질 규칙의 최상위 문서다. 제품 범위와 시나리오 의미는 V4와 Product Brief를 입력으로 삼으며, 문서 간 충돌은 다음 순서로 해결한다.

1. 명시적으로 승인된 최신 제품 범위 변경
2. 이 Constitution의 안전·증적·판정 원칙
3. `ControlProof_MVP_Decision_Log.md`의 최신 확정 결정
4. 승인된 기능 Spec
5. 기술 Plan과 ADR
6. Tasks와 구현 코드
7. 첨부 골격과 탐색용 spike

하위 문서는 상위 문서의 의미를 조용히 바꿀 수 없다. 충돌이 발견되면 구현을 맞추기 전에 관련 상위 문서의 변경 여부를 결정해야 한다.

### 개정 절차

- 개정에는 변경 이유, 영향받는 Spec·코드·시험, 마이그레이션 필요 여부와 승인 날짜가 있어야 한다.
- 기존 원칙을 제거하거나 호환되지 않게 바꾸면 MAJOR 버전을 올린다.
- 새 원칙·필수 게이트를 추가하거나 의미를 실질적으로 확장하면 MINOR 버전을 올린다.
- 의미를 바꾸지 않는 설명·오탈자·표현 수정은 PATCH 버전을 올린다.
- 모든 기능 Spec과 Plan은 시작과 완료 시 Constitution 준수 여부를 확인해야 한다.
- 예외가 불가피하면 책임자, 근거, 영향, 만료일과 해소 task를 ADR 또는 결정 기록에 남겨야 한다. 구두 예외는 인정하지 않는다.

### 운영 상태

- 현재 버전은 팀 동기화가 어려운 상황에서 제품 책임자의 위임에 따라 2주 MVP 개발 기준으로 발효한다.
- 팀 검토에서 변경이 필요하면 기존 버전과 이유를 보존한 채 위 개정 절차로 수정한다.
- 기능 Spec 001은 이 버전을 기준으로 작성하며, 현재 첨부 골격의 코드나 YAML이 이 Constitution보다 우선하지 않는다.
