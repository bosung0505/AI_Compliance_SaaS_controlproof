# 시나리오 명세 작성 가이드

작성 기준일: 2026-09-23
대상: ControlProof 팀 3인 (개발·기획 공통)
관련 파일: `_TEMPLATE.yaml`, `H-03.yaml`

---

## 1. 왜 명세를 따로 두는가

시나리오는 자주 바뀐다. 착수 하루 만에도 여러 번 바뀌었다. WhyYou에 점수
임계값이 없다는 걸 알고 H 계열을 다시 썼고, 이의제기 기능이 없어 A 계열을
판정 불가로 돌렸고, 지원자 생성 경로가 하나뿐이라 N-03을 교체했다.

그 사이 코드는 한 줄도 쓰지 않았다. 이게 정상이고, 앞으로도 이래야 한다.

**시나리오는 데이터다. 코드가 아니다.**

| | 바뀌는 빈도 | 어디에 |
|---|---|---|
| 어떤 통제를, 어떤 입력으로, 어떤 조건에서 시험할지 | 자주 | YAML |
| 무엇을 기대하고 무엇을 증적으로 남길지 | 자주 | YAML |
| 실행 ID 발급, 시드·복원, 관찰값 수집, 판정 실행, 보고서 생성 | 거의 없음 | 코드 |

엔진 코드를 고쳐야 하는 경우는 셋뿐이다.

1. 새 관찰 수단이 필요할 때 (어댑터 추가)
2. 판정 규칙 타입이 모자랄 때 (규칙 추가)
3. 증적 스키마가 바뀔 때 — 이것만 비싸다. 그래서 D1에 스키마를 고정하고
   H-03 하나를 수직으로 관통시켜 먼저 검증한다.

## 2. 필드 작성 규칙

### 2.1 intent / implementation — 의도와 구현을 나눈다

가장 중요한 분리다. 시나리오 재사용률이 여기서 결정된다.

**intent**는 어느 회사에서나 같다. 법 조항에서 도출하며 제품 이름·필드명·
엔드포인트를 쓰지 않는다.

**implementation**은 이 회사에서 그 의도가 어떤 기능·필드·상태로 나타나는지다.
고객이 바뀌면 이 칸만 교체한다.

```
나쁜 예 (구현이 의도에 섞임)
  intent: 59점 지원자를 대기열 장애 조건에서 투입해 자동 탈락하지 않는지 확인

좋은 예
  intent: 사람 검토가 필요한 건이, 검토 경로가 끊긴 상태에서
          자동으로 확정되지 않아야 한다
  implementation: WhyYou는 점수 임계값 라우팅이 없고 전 지원자가
          검토 대상이다. 최종결정 트랜잭션이 세 단계로 구성된다...
```

intent를 고쳐야 한다면 그건 매핑이 아니라 시나리오 교체다.

### 2.2 beneficiary / initiator — 수혜자와 개시자

통제가 보호하는 사람과, 그 절차를 일으키는 주체.

이 두 칸이 시나리오의 소속을 결정한다. 실제로 착수 당일 이 칸이 없어서
판단이 한 번 흔들렸다. WhyYou의 `assessment_override`(담당자가 AI 평가를
자기 판단으로 수정하는 기능)를 이의처리 통제로 볼 뻔했다.

- 이의처리의 수혜자·개시자는 **모두 지원자**다.
- override의 개시자는 담당자다. 아무도 요구하지 않았고 안 해도 그만이다.
- 따라서 override는 이의처리 시나리오가 될 수 없다. 행위자 검사는 ②
  인간 개입으로, 사유 강제와 원본 보존은 ④ 증적으로 간다.

통제는 보호받는 사람이 행사할 수 있어야 성립한다. 담당자의 선의에만 달린
기능은 지원자 입장에서 아무 보장이 아니다.

### 2.3 preconditions — 통제를 단계로 쪼갠다

통제를 있다/없다로 보지 않는다. 단계별로 적고, 없는 단계만 판정 불가로
떨어뜨린다.

이의처리를 예로 들면:

| 단계 | WhyYou | |
|---|---|---|
| 이의 제기 가능 고지 | 없음 | ✕ |
| 지원자 접수 창구 | 없음 | ✕ |
| 접수 확인 통지 | 없음 | ✕ |
| 담당자 배정 | 없음 | ✕ |
| 재검토 — 원 판단을 뒤집는 경로 | `assessment_override`, `HumanReview` | ○ |
| 재검토 이력 보존 | immutable 리포트 + 별도 기록 | ○ |
| 결과 통지 | 메일 인프라만 존재 | △ |

"이의제기 기능 없음" 한마디로 뭉개면 뒤쪽 절반이 안 보인다. 고객사에서도
똑같은 일이 벌어진다. 담당자의 "저희 그런 거 없어요" 한마디에 통제 하나를
통째로 못 보게 된다.

required이면서 absent인 단계가 하나라도 있으면 그 시나리오는
`NO_TEST_TARGET`이다.

### 2.4 seed — 두 종류이며 서로 대체할 수 없다

| | 상태 시드 | 경로 시드 |
|---|---|---|
| 방식 | DB에 행 직접 생성 | 실제 API를 순서대로 호출 |
| 결과 | 리포트까지 준비된 검토 대기 지원자 | 동의까지 실제로 거친 지원자 |
| 쓰는 곳 | H-01~03, E-01~03 | N-01~03 |
| 비용 | 없음 | 없음 (면접 전 단계라 AI 미호출) |

상태 시드로 만든 지원자는 동의 화면을 지나지 않았다. 동의 통제를 시험할 수
없다. 경로 시드로 만든 지원자는 면접·리포트가 없다. 검토 시나리오에 쓸 수 없다.

E-02는 둘 다 필요하다. 동의 정책 버전은 경로 시드에서, 평가 기준 버전은
상태 시드에서 나온다.

### 2.5 fault — 주입 조건

정상 기준선에서 무엇을 인위적으로 바꾸는가. 없으면 `none`.

주입은 격리 환경·합성 데이터·테스트 계정에서만 적용한다. 시험 종료 후
연결 설정과 대상 상태를 기준선으로 복원하고, 복원됐는지 확인한 뒤 다음으로
넘어간다.

### 2.6 steps — 사람이 한 단계는 표시한다

2주 안에는 일부 단계를 사람이 수행할 수 있다. 실제 시스템에서 실행되고
증적이 남으면 유효한 시험이다.

다만 `manual: true`로 표시하지 않으면 "같은 조건으로 재시험"이 성립하지
않는다. 재현성이 이 제품의 핵심이므로 이 표시를 빠뜨리지 않는다.

## 3. 판정 규칙 네 가지

새 시나리오가 이 넷으로 표현되지 않으면 그때 다섯 번째를 추가한다.
지금 12개는 전부 이 조합으로 써진다.

| 타입 | 확인하는 것 | 쓰이는 예 |
|---|---|---|
| `state_equals` | 관찰한 상태값이 기대값과 같은가 | 장애 중 지원 건이 `completed`로 남아 있는가 |
| `event_order` | A가 B보다 먼저인가 | 동의 완료 < 분석 요청 ≤ 분석 시작 |
| `time_limit` | 정해진 시간 안에 일어났는가 | 이의 접수부터 결과 통지까지 기한 내 |
| `fields_present` | 있어야 할 것이 있고, 없어야 할 것이 없는가 | 장애 중 필수 증적 8종 / 반쪽 저장 부재 |

`fields_present`의 `absent` 목록을 과소평가하지 않는다. H-03의 진짜 판정
기준은 여기다 — 장애 중에 **있으면 안 되는 것**(반쪽 저장, 사람 결정 없는
단계 이동)을 확인하는 것이 이 통제의 본질이다.

모든 규칙이 통과해야 PASS. 하나라도 어긋나면 FAIL. 규칙을 평가할 관찰값
자체를 얻지 못하면 판정 불가.

## 4. 판정값과 판정 불가 사유

### 판정값 네 가지

| 값 | 의미 |
|---|---|
| PASS | 기대 결과와 필수 증적이 모두 확인됨 |
| FAIL | 실제 동작이 기대와 다르거나 필수 통제가 작동하지 않음 |
| 판정 불가 | 접근 제한·누락·충돌로 결론을 낼 수 없음 |
| 미실행 | 정의는 되어 있으나 아직 실행하지 않음 |

"못 한 것"과 "안 한 것"을 섞지 않는다. 미실행을 판정 불가에 넣으면 보고서가
거짓말을 하게 된다.

### 판정 불가 사유 코드

| 코드 | 의미 | 고객에게 뜻하는 것 |
|---|---|---|
| `NO_TEST_TARGET` | 대상 기능 자체가 없음 | 통제를 갖춰야 함 |
| `NO_ACCESS` | 접근 권한·경로가 없어 관찰 불가 | 접근 범위를 넓히면 시험 가능 |
| `EVIDENCE_MISSING` | 판정에 필요한 증적을 얻지 못함 | 기록 구조를 손봐야 함 |
| `CONFLICT` | 관찰 결과가 서로 충돌 | 조사가 필요함 |

넷을 갈라 적는 이유는, 고객이 받는 처방이 전혀 다르기 때문이다. 뭉뚱그려
"판정 불가"로만 적으면 보고서가 쓸모를 잃는다.

## 5. 결함 버전 — 고치고 시험하지 말고, 시험하고 고친다

`defect_variant`는 FAIL → 수정 → PASS를 보여주기 위한 칸이다.

순서를 지킨다.

```
시험 → FAIL → 증적으로 원인 확인 → 수정 → 같은 조건 재시험 → PASS
```

이미 알고 있는 결함을 미리 고치고 시험하면 "통과했습니다"라는 시시한 결과만
남는다. 고칠 것을 알고 있다는 사실이 자산이다. 먼저 고치면 그걸 버리는 것이다.

두 가지 금지 사항이 있다.

**시험 대상을 만들지 않는다.** 대상에 없는 통제를 우리가 구현해 넣고 시험하면,
PASS는 우리가 만든 것을 우리가 통과시킨 결과가 된다. 감사인이 장부를 대신
써주면 안 되는 것과 같다. 장애 주입 수단은 다르다 — 시험 대상이 아니라
시험 수단이고, 격리 환경에서만 켜지며, 보고서에 "시험을 위해 추가"로 표시한다.

> **경계 한 줄: 시험받는 대상은 만들지 않고, 시험하는 수단만 만든다.**

**통과하는 통제를 일부러 깨서 시연하지 않는다.** 최초 실행이 PASS면 결함
버전을 만들지 않는다.

## 6. 새 시나리오를 쓸 때의 순서

1. intent를 법 조항에서 쓴다. 제품 이름이 들어가면 다시 쓴다.
2. beneficiary / initiator를 채운다. 개시자가 통제의 수혜자가 아니면
   소속 통제를 의심한다.
3. preconditions를 단계로 쪼갠다. required·absent가 있으면 `NO_TEST_TARGET`.
4. seed 종류를 정한다. 상태 시드와 경로 시드를 섞지 않는다.
5. 기대 결과를 비개발자가 읽을 수 있게 쓴다.
6. 그 기대를 판정 규칙 네 타입으로 옮긴다. 안 옮겨지면 기대가 모호한 것이다.
7. 필수 증적을 적는다. 한 기록에 다 없어도 되지만, 실행 ID로 묶어 재구성
   가능해야 한다.
8. implementation을 채운다. 여기만 고객마다 바뀐다.

## 부록. H-03 읽기 쉬운 버전

**확인하는 것** — 사람의 최종 판단 경로에 장애가 생겼을 때, 시스템이 임의로
채용 결과를 확정하지 않고 기다리는가. 그리고 실패한 시도가 반쪽만 저장되어
화면과 데이터가 어긋나는 상태를 남기지 않는가.

**WhyYou에서의 구조** — 최종결정은 세 가지가 한 트랜잭션으로 함께 일어난다.
결정 기록 저장, 채용 단계 이동, 지원 건 상태 전이(completed → reviewed).
코드 주석에 "오류를 의도적으로 전파한다, HTTP 트랜잭션이 셋을 함께 롤백하기
위해서"라고 적혀 있다. 이 시나리오는 그 설계가 실제로 지켜지는지 본다.

**실행 순서**

1. 지원자 3명을 검토 대기 상태로 만들고 기준선을 기록
2. AI 점수와 무관하게 셋 다 검토 대상으로 남아 있는지 확인
3. 최종결정 경로에 장애 주입
4. 결정을 시도 → 실패하는지
5. 장애 중 저장 상태 확인 → 아무것도 저장되지 않았는지
6. 자동 확정이 없었는지 확인
7. 장애 복구, 기준선 일치 확인
8. 정상적으로 결정 → 결정자·시각·단계·사유가 남는지
9. 같은 요청 재전송 → 중복 기록되지 않는지

**실패하면 무슨 일이 벌어지나** — 사람 검토 없이 결과가 확정되거나, 일부만
저장되어 화면에는 결정이 있는데 지원자 상태는 그대로인 상황이 생긴다.
재시도하면 결정이 두 번 기록된다.

**현재 상태** — 전제조건 4개 중 장애 주입 수단이 없다. 그 기능을 만들기 전까지
H-03은 `NO_TEST_TARGET`이다. 이것이 템플릿이 의도한 동작이다. "구현이 필요하다"를
산문이 아니라 필드로 드러낸다.
