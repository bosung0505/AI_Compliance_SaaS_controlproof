# 아키텍처

`CLAUDE.md`의 규칙을 그림으로 옮긴 것. 코드를 읽기 전에 이걸 먼저 본다.

---

## 1. 무엇이 바뀌고 무엇이 안 바뀌는가

이 경계가 이 프로젝트의 핵심 설계다. 착수 당일 시나리오를 네 번 갈아엎었지만
코드는 한 줄도 쓰지 않았다. 앞으로도 이래야 한다.

```mermaid
flowchart LR
    subgraph CHANGE["자주 바뀜 — 데이터"]
        Y["시나리오 YAML<br/>무엇을 어떤 조건에서<br/>무엇을 기대하고"]
        M["연결 설정<br/>키 → 실제 엔드포인트·필드"]
    end
    subgraph FIXED["거의 안 바뀜 — 코드"]
        E["엔진<br/>실행 ID · 시드 · 관찰 · 판정<br/>증적 저장 · 보고서"]
    end
    Y -->|"관찰값 키로만 대화"| E
    M -->|"어댑터가 참조"| E
```

엔진을 고쳐야 하는 사유는 셋뿐이다.

| 사유 | 비용 |
|---|---|
| 새 관찰 수단이 필요 | 어댑터 하나 추가. 기존 것은 그대로 |
| 판정 규칙 타입이 모자람 | 규칙 하나 추가 |
| **증적 스키마 변경** | **비싸다.** 어댑터·판정·저장·보고서가 전부 영향 |

그래서 D1에 스키마를 고정하고, D5에 H-03을 수직으로 관통시켜 검증한다.
D5에 깨지는 건 싸고 D11에 깨지면 비싸다.

## 2. 관찰값 키 — 시나리오와 어댑터의 유일한 접점

```mermaid
flowchart TB
    S["시나리오 규칙<br/>subject: invitation.state<br/>equals: completed"]
    K(["관찰값 키 사전<br/>engine/observations.py"])
    A1["API 어댑터"]
    A2["로그 어댑터"]
    A3["브라우저 어댑터"]
    A4["장애 주입"]
    W[("WhyYou")]
    O["Observation<br/>key=invitation.state"]

    S -->|"추상 키만 가리킴"| K
    K --> A1 & A2 & A3 & A4
    A1 & A2 & A3 & A4 --> W
    W --> O
    O -->|"같은 키로 매칭"| S
```

시나리오는 `invitation.state`라고만 쓴다. 그 키를 어느 엔드포인트의 어느
필드에서 가져올지는 어댑터의 연결 설정이 정한다.

**고객사가 바뀌면 연결 설정만 교체하고 시나리오 YAML은 그대로 둔다.**
키 자체를 바꿔야 한다면 그건 매핑이 아니라 시나리오 교체다.

## 3. Observation의 세 가지 상태 — FAIL과 판정 불가를 가르는 지점

어댑터가 여기서 대충하면 **없는 것을 확인한 것처럼 판정된다.**
이 프로젝트에서 가장 미묘하고 가장 중요한 구분이다.

```mermaid
flowchart TB
    Q{"관찰을 시도했다"}
    Q -->|"조회 성공, 값 있음"| V["Observation value=..."]
    Q -->|"조회 성공, 존재하지 않음"| B["Observation absent=True"]
    Q -->|"조회 자체 실패"| N["Observation을 만들지 않음"]

    V --> R["규칙 평가"]
    B --> R
    N --> I["판정 불가<br/>INSUFFICIENT_EVIDENCE"]

    R --> P["PASS 또는 FAIL"]
```

"없었다"와 "못 봤다"는 다르다. 조회에 실패했는데 `absent=True`를 만들면
없는 것을 확인한 것처럼 처리된다.

## 4. 판정 흐름

```mermaid
flowchart TB
    START(["실행 종료"])
    T{"전제조건에<br/>required·absent 가 있나"}
    AC{"허용된 연결로<br/>관찰 가능했나"}
    CF{"같은 키에<br/>모순된 관찰이 있나"}
    RULE["규칙 4타입 평가"]
    F{"실패한 규칙이<br/>하나라도 있나"}
    MISS{"평가 못 한<br/>규칙이 있나"}

    START --> T
    T -->|예| NTT["판정 불가<br/>NO_TEST_TARGET"]
    T -->|아니오| AC
    AC -->|아니오| AL["판정 불가<br/>ACCESS_LIMITED"]
    AC -->|예| CF
    CF -->|예| EC["판정 불가<br/>EVIDENCE_CONFLICT"]
    CF -->|아니오| RULE
    RULE --> F
    F -->|예| FAIL["FAIL"]
    F -->|아니오| MISS
    MISS -->|예| IE["판정 불가<br/>INSUFFICIENT_EVIDENCE"]
    MISS -->|아니오| PASS["PASS"]
```

두 가지 설계 판단이 들어 있다.

**FAIL이 판정 불가보다 우선한다.** 관찰된 실패는 다른 증적을 못 얻었다고
사라지지 않는다.

**대상이 없으면 규칙을 아예 평가하지 않는다.** 없는 것을 통과시키지 않기
위해서다. A-01~A-03이 여기서 걸러진다.

## 5. 판정 불가 네 가지 — 고객이 받는 처방이 다르다

```mermaid
flowchart LR
    X["판정 불가"]
    X --> A["NO_TEST_TARGET<br/>대상 기능이 없음"]
    X --> B["ACCESS_LIMITED<br/>접근 경로가 없음"]
    X --> C["INSUFFICIENT_EVIDENCE<br/>증적을 못 얻음"]
    X --> D["EVIDENCE_CONFLICT<br/>관찰이 충돌"]

    A --> A2["통제를 갖춰야 함"]
    B --> B2["접근 범위를 넓히면 시험 가능"]
    C --> C2["기록 구조를 손봐야 함"]
    D --> D2["조사가 필요함"]
```

뭉뚱그려 "판정 불가"로만 적으면 보고서가 쓸모를 잃는다.

## 6. 시드 두 종류 — 섞지 않는다

```mermaid
flowchart TB
    subgraph ST["상태 시드 — DB 직접 삽입"]
        S1["회사·포지션·초대"]
        S2["면접 세션·턴·자막"]
        S3["리포트·Evidence"]
        S1 --> S2 --> S3
    end
    subgraph PT["경로 시드 — 실제 API 순서 호출"]
        P1["초대 발급"]
        P2["토큰 교환"]
        P3["본인 확인"]
        P4["동의 기록"]
        P1 --> P2 --> P3 --> P4
    end
    ST --> HE["H 계열 · E 계열<br/>검토 · 결정 · 증적"]
    PT --> NN["N 계열<br/>고지 · 동의"]
```

- 상태 시드로 만든 지원자는 **동의 화면을 거치지 않았다** → N 계열에 쓸 수 없다
- 경로 시드로 만든 지원자는 **면접·리포트가 없다** → H·E 계열에 쓸 수 없다
- E-02는 둘 다 쓴다. 동의 정책 버전은 경로 시드에서, 평가 기준 버전은 상태 시드에서

## 7. 실행 한 바퀴

```mermaid
sequenceDiagram
    participant CP as ControlProof
    participant DB as WhyYou DB
    participant API as WhyYou API
    participant W as Worker · Queue

    CP->>CP: 실행 ID 발급
    CP->>DB: 시드 투입 (멱등 upsert)
    CP->>API: 기준선 조회
    API-->>CP: 상태 · 단계 · row_version
    CP->>W: 조건 주입 (장애 · 변경 · 우회)
    CP->>API: 시나리오 단계 실행
    API-->>CP: 응답 · 오류
    CP->>DB: 상태 · 이벤트 · 기록 조회
    DB-->>CP: 관찰값
    CP->>CP: 규칙 평가 → 판정
    CP->>W: 주입 해제 · 기준선 복원
    CP->>API: 복원 확인
    CP->>CP: 증적 묶음 저장
```

복원 확인을 건너뛰지 않는다. 다음 실행의 기준선이 오염되면 재현성이 깨진다.

## 8. 재시험은 덮어쓰지 않는다

```mermaid
flowchart LR
    R1["최초 실행<br/>FAIL"] --> FIX["WhyYou 수정"]
    FIX --> R2["재시험<br/>retest_of = 최초 실행 ID"]
    R2 --> CMP["두 결과 비교"]
    R1 -.->|"보존"| CMP
```

알고 있는 결함을 미리 고치고 시험하면 이 그림이 성립하지 않는다.
**고치고 시험하지 말고, 시험하고 고친다.**

## 9. 통제 4종 × 시나리오 12개

```mermaid
flowchart TB
    subgraph N["① AI 사용 사전 고지"]
        N1["N-01 고지 표시<br/>정적"]
        N2["N-02 동의 없이 처리<br/>우회 + 장애"]
        N3["N-03 정책 교체 귀속<br/>변경 + 우회"]
    end
    subgraph H["② 인간 개입"]
        H1["H-01 비인가 주체 거부<br/>우회"]
        H2["H-02 쓰기 권한 표면<br/>정적"]
        H3["H-03 reporting 장애<br/>장애"]
    end
    subgraph A["③ 이용자 보호·이의처리"]
        A1["A-01 진입·접수"]
        A2["A-02 원 결정 보류"]
        A3["A-03 독립 재검토"]
    end
    subgraph E["④ 증적 기록"]
        E1["E-01 인용 없는 점수<br/>우회 + 변경"]
        E2["E-02 기준 동결<br/>변경"]
        E3["E-03 장애 시 증적<br/>장애"]
    end
    A --> NT["전부 판정 불가<br/>NO_TEST_TARGET<br/>지원자 개시 경로 부재"]
```

시험 가능 9개 중 **7개가 조건을 직접 만드는 시나리오**다.
정적 2개(N-01·H-02)는 기존 QA로도 가능하며, 이 사실을 보고서에 숨기지 않는다.

## 10. 2주 일정

```mermaid
gantt
    dateFormat X
    axisFormat D%d
    section 기반

    H-03 완주                 :crit, d5, 4, 1d

    section 시나리오
    E-03                      :d7, 6, 1d
    경로 시드 + N-02          :d8, 7, 1d
```
