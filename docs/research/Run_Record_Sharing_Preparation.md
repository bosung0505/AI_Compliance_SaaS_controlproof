# 실제 실행 기록 공유: 설계 이유 조사와 전환 준비

기준일: 2026-10-19. 결정: [D-029](../product/ControlProof_MVP_Decision_Log.md#d-029-실제-실행-기록을-공유하고-같은-결과-화면을-제공한다).

이 문서는 **원래 설계 조사·공유 정책 변경·구현 준비 당시 기준선**이다. 이후 사용자 구현 승인에 따라
Spec008에서 실제 원본25건/600파일과 공유 화면을 구현하고 별도 Git clone으로 검증했다.
현재 실행은 [공유 기록 README](../../review-data/README.md), 검증은 [Spec008 Validation](../../specs/008-shared-run-records/validation.md)을 따른다.
아래 준비 당시의 미구현 표현·원본 위치는 당시 조사 이력으로 읽는다.

## 1. 처음에 왜 PC별로 기록을 보관했나

문서와 Git 이력에 명시된 이유가 있다. 영구적으로 공유하지 않겠다는 제품 원칙이라기보다,
로컬 MVP의 단순성·데이터 안전·독립 재현의 의미를 지키면서 공유 기능을 후속으로 미룬 선택이었다.

| 근거 | 당시 결정과 이유 |
|---|---|
| [Spec001 research R-06](../../specs/001-execution-evidence-h03/research.md#r-06-controlproof-영속화-방식) | 한 번 실행한 기록을 JSON/JSONL·증거 파일·manifest가 있는 독립 폴더로 저장. 별도 DB의 migration·백업·export 비용과 S3 우선 도입은 로컬 2주 MVP에 과하다고 판단했다. 폴더 단위 검토·전달·변조 검사가 쉽다는 이유도 명시돼 있다. |

민감정보 검토는 추상적인 우려만은 아니었다. [Spec005 원천 조사 §2](Spec005_Workbench_Report_Source_Baseline.md#2-위험-이번-spec에서-고치지-않음-웹-설계-입력)에
당시 JSON 이스케이프된 Windows 사용자 경로를 기존 검사기가 놓칠 수 있다는 문제가 기록돼 있다.
저장 전에 마스킹하고 저장된 바이트에 해시를 매기는 원칙은 [Spec001 R-07](../../specs/001-execution-evidence-h03/research.md#r-07-증적-마스킹과-해시-순서)에 있다.

10/2에는 사용자 승인으로 N-02 최초 부모 `15cef078…`와 정비 증거만 게시한 일회성 예외도 있었다(`9f61713`).
따라서 ‘실제 기록은 기술적으로 공유할 수 없다’는 설명은 맞지 않는다. 안전한 일반 공유 절차가 범위에서 빠져 있었던 것이다.
Git 파일 크기나 비용이 이 정책의 주된 이유였다는 명시적 근거는 이번 조사에서 찾지 못했다.

**구분해야 할 점:** 독립 재현을 요구한다는 사실이 결과 열람까지 금지해야 한다는 뜻은 아니다.
공유받은 원본을 읽는 일과 다른 PC에서 새 테스트를 실행하는 일을 구분하면 두 목표를 함께 충족할 수 있다.
[D-021](../product/ControlProof_MVP_Decision_Log.md#d-021-웹-워크벤치는-장기적으로-권한이-있는-원격-접속을-지원한다-구현-보류)의
로그인·원격 서비스 구축도 Git으로 같은 기록을 배포하는 이번 목표와는 별도다.

N02 중간 원본은 추가 조사에서도 미발견이며 원본 부재를 표시한다.
예시 파일을 대신 만들어 실제 기록처럼 연결해서는 안 된다. E-01의 별도 DB 직접 주입 진단도 본 테스트와 구분한 기존 설명을 유지한다.

현재 Git에 추적된 실제 원본 예외는 N-02 최초 `15cef078…`다. 이것은 최신 PASS가 아니라 최초 INCONCLUSIVE 기록이다.
실제 기록은 요약 문서만이 아니라 `run.json`, assertion·관찰 기록, 증거 파일, `manifest.json` 등으로 구성된 봉인 bundle이다.
원본의 존재·무결성 확인과 외부 공유 적합성 검사는 별개이며 공유 전 재검사가 남아 있다.

## 3. 변경된 정책: 검토한 실제 기록을 함께 공유한다

사용자는 2026-10-19 코드와 실제 검증 기록을 함께 공유해 팀원이 같은 결과 화면을 보도록 전환하라고 요청했다.

- 검토·검증한 실제 bundle과 필요한 계보, 공식 선택 목록을 Git으로 함께 배포한다. 저장 위치 제안은 `review-data/bundles/<run-id>`다.
  `.gitignore`의 `runs/`는 하위 동명 폴더도 제외하므로 공유 폴더 이름에 그대로 쓰지 않는다. 이 경로는 후속 Spec008에서 구현했다.
- `.controlproof/`, 임시 probe, DB·큐·볼륨 전체, `.env`와 자격 증명은 통째로 게시하지 않는다. 실제 개인정보·비밀값을 공유하지 않는다.
  이 구분은 결과 기록을 공유하겠다는 사용자 결정을 유지하면서 PC 내부 상태까지 섞이지 않게 하기 위한 것이다.
- FAIL·INCONCLUSIVE·중단 기록과 부모 참조도 조사·포함하며 PASS만 선별하지 않는다. 찾지 못한 계보는 누락 목록에 명시한다.
- 원본은 바이트 그대로 보존한다. 추가 검사에서 공개 부적합 내용이 나오면 봉인 파일을 직접 고치지 않는다.
  필요한 경우 원본과의 관계·제외 사유·별도 manifest를 가진 공유용 파생본의 형식과 판독 지원을 먼저 설계한다.
  파생본을 원본 VERIFIED bundle처럼 취급하지 않는다.
- 공유본을 열람·검증한 사실을 독립 실행으로 표시하지 않는다. 기존 Run의 시간·source SHA·환경·verdict는 유지한다.
  AWS, 외부 모델 품질, 독립 PC 실행 여부도 기존 범위 그대로다.

## 5. ‘같은 화면’의 구체적인 기준

같은 ControlProof 코드 버전과 같은 공유 snapshot이면 카탈로그의 공식 결과, 대표 Run, 상세 관찰·근거, 계보와
H-02 발견→보완→재테스트 설명이 동일해야 한다. 기존 합성 DEMO와 실제 공유 결과도 구분한다.
이 열람에는 WhyYou를 다시 실행하거나 DB를 복사할 필요가 없도록 한다. 새 테스트 실행 환경 준비는 별도다.

다만 bundle만 복사하면 현재 화면 전체가 자동으로 같아지지는 않는다. 현재 `engine/web/readmodel.py`의 `_target_identity()`는
PC별 최신 준비 확인 기록을 읽고, 수정 메모도 `.controlproof/web/memos`에 별도 보관한다. 따라서 후속 Spec은 다음을 함께 정해야 한다.

- 공유 결과 화면의 대상 버전·확인 시각은 선택된 snapshot의 과거 실행 맥락으로 고정한다.
- 현재 PC의 새 테스트 준비 상태는 별도 로컬 정보로 표시한다. 과거 READY를 현재 PC의 READY로 복사하지 않는다.
- 기존 메모의 공유 필요성을 조사하고, 필요한 검토 메모는 봉인 원본 밖의 별도 버전 관리 자료로 정한다.
  개인 로컬 메모가 공식 공유 설명이나 대표 결과 선택을 바꾸지 않도록 한다.
- 데이터가 없거나 해시가 다르면 누락/무결성 오류를 명확히 표시하며 요약 PASS로 상세 근거를 대신하지 않는다.

이 작업은 기존 기록을 공동 열람하는 기능이다. 원격 공개 서버·로그인 구현, 새 시나리오 실행, 다른 PC 재실행 완료,
Spec005 비작성자 사용성 완료나 main 병합을 포함하지 않는다.

## 조사 방법과 이번 변경 범위

위 문서 원문, `.gitignore`, 플레이북 §7과 D-014의 `git blame`, 해당 commit의 `git log`, 카탈로그와 웹 판독 코드를 확인했다.
로컬 원본 존재/검증 조사는 앞선 이번 세션의 두 root 조사 결과를 정리했다. 출처가 불명확한 기록의 실행자는 추정하지 않았다.
이 조사 단계의 변경은 문서·작업 규칙뿐이었다. 후속 Spec008 구현·열람 검증·게시 상태는 현재 Validation을 따른다.
원본 bundle과 WhyYou 제품 코드는 공유 기능을 만들기 위해 변경하지 않았다.
