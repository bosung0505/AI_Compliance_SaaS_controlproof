## 1. 제품 정의

### 1.1 한 문장 정의

> ControlProof는 합성 데이터를 이용해 AI 서비스의 절차적 보호조치를 정상·우회·변경·장애 조건에서 직접 시험하고, 관찰 결과를 판정과 재현 가능한 증적 묶음으로 만들어 수정 후 재시험까지 보여주는 능동적 통제 검증 도구다.

### 1.2 이번 MVP의 검증 대상

- 대상 서비스: WhyYou
- 대상 범위: AI 사용 사전 고지, 인간 개입, 이용자 보호·이의처리의 대상 존재 여부, 증적 기록
- 실행 환경: 합성 데이터와 테스트 계정을 사용하는 격리된 로컬 시험환경
- 최종 결과: 화면 보고서와 연결된 원본 증적

### 1.3 해결하려는 문제

AI 서비스 사업자는 정책 문서나 코드만으로 다음 질문에 답하기 어렵다.

- 고지와 동의가 실제 처리보다 먼저 일어나는가?
- 사람만 내려야 할 결정을 AI나 다른 경로가 우회할 수 없는가?
- 근거가 없거나 바뀐 AI 점수가 정상 결과처럼 남지 않는가?
- 의존 경로가 실패해도 보호조치와 기록이 유지되는가?
- 실패를 수정한 뒤 같은 조건에서 개선됐음을 보여줄 수 있는가?
- 시험하지 못한 영역을 통과로 오해하지 않게 설명할 수 있는가?

ControlProof는 이 질문을 문답이나 체크리스트가 아니라 실제 실행과 증적으로 답한다.

## 2. 절대 원칙

다음 원칙은 [Constitution](../../.specify/memory/constitution.md)으로 승격되었으며, 기능별 Spec이나 구현 편의를 이유로 바꾸지 않는다.

### 2.1 AI 점수는 참고 정보다

- 점수 임계값으로 합격·탈락을 자동 확정하지 않는다.
- 모든 최종 채용 결정은 회사 사용자인 사람이 수행한다.
- 점수가 더 낮은 지원자가 사람의 종합 판단으로 채용될 수 있다.
- 합성 점수는 사람 판단의 독립성과 기록 구조를 시험하기 위한 입력일 뿐이다.

### 2.2 시험 대상과 시험 수단을 구분한다

- WhyYou에 없는 보호 기능을 ControlProof가 대신 구현해 넣고 통과시키지 않는다.
- 장애 주입, 데이터 변경과 우회 호출은 시험 수단이며 테스트 환경에서만 사용한다.
- 시험을 위해 추가한 기능은 보고서에 명시한다.
- 현재 WhyYou의 실패 가능성을 먼저 시험하고, 관찰된 실패를 보존한 뒤 수정한다.

### 2.3 근거 없는 통과를 금지한다

- 관찰하지 못한 사실을 `PASS`로 처리하지 않는다.
- 조회 결과가 없었던 것과 조회 자체를 못 한 것을 구분한다.
- 대상 기능이 없는 것과 ControlProof 실행기가 준비되지 않은 것을 구분한다.
- 서로 충돌하는 증적은 임의로 하나를 선택하지 않는다.

### 2.4 최초 결과를 보존한다

- 재시험은 최초 실행을 덮어쓰지 않는다.
- 최초 실행, 실패 원인, 수정 내용, 재시험과 최종 결과를 하나의 이력으로 연결한다.
- 최초 실행이 `PASS`라면 데모를 위해 통과하는 통제를 인위적으로 깨지 않는다.

### 2.5 시나리오와 대상 연결을 분리한다

- 시나리오의 통제 의도와 판정 의미는 서비스에 독립적이어야 한다.
- WhyYou의 엔드포인트, 테이블, 큐와 상태값은 대상별 연결 정보로 관리한다.
- 새 서비스로 확장할 때 공통 시나리오 의미와 판정 이력을 최대한 재사용한다.
- 새 관찰 수단이나 판정 표현이 필요할 때만 엔진을 확장한다.

## 3. 사용자와 사용 목적

### 3.1 실행 담당자

대상 서비스의 테스트 환경을 연결하고 시나리오를 실제로 수행하는 개발자 또는 QA 담당자다.

주요 목적:

- 실행 가능한 시나리오와 준비 상태 확인
- 합성 데이터와 시험 조건 선택
- 시험 시작·중단·복구·재시험
- API·화면·로그·이벤트 관찰값 수집
- 실패 원인과 누락 증적 확인

### 3.2 검증 책임자

시험 범위와 판정 근거를 검토하는 제품, 컴플라이언스 또는 내부 감사 담당자다.

주요 목적:

- 무엇을 어떤 근거로 시험했는지 확인
- 기대 결과와 실제 결과 비교
- `PASS`, `FAIL`, `판정 불가`, `미실행` 구분 검토
- 수정과 재시험 결과 승인
- 검증하지 못한 범위와 한계 확인

### 3.3 결과 검토자

납품 실사, 공공조달, 내부 감사 또는 사업 검토를 위해 결과 보고서를 읽는 비개발자다.

주요 목적:

- 보호조치가 실제로 작동했는지 이해
- 실패의 영향과 수정 여부 확인
- 판정에 사용된 증적을 필요한 수준까지 추적
- 법적 준수 전체를 보증하지 않는다는 검증 한계 확인

### 3.4 이번 MVP에서 직접 지원하지 않는 사용자

- 실제 지원자
- 외부 고객사의 운영 관리자
- 법률 자문가를 위한 법적 적합성 확정 기능
- 여러 고객사를 동시에 관리하는 ControlProof 관리자

## 4. 핵심 사용자 여정

### 4.1 시험 준비

1. 실행 담당자가 검증 대상 `WhyYou`와 시험할 버전을 확인한다.
2. 시나리오 목록에서 대상 기능 존재 여부와 실행 준비 상태를 확인한다.
3. 실행할 시나리오와 합성 데이터 유형을 선택한다.
4. 정상·우회·데이터 변경·장애 중 필요한 시험 조건을 선택한다.
5. ControlProof가 시험 실행 ID를 발급한다.
6. 실행 담당자가 실행 전 기준선과 복구 방법을 확인한다.

### 4.2 시험 실행과 관찰

1. ControlProof가 상태 시드 또는 경로 시드를 준비한다.
2. 실행 전 상태와 대상 버전을 기록한다.
3. 정의된 시험 조건을 적용한다.
4. 시나리오 단계를 순서대로 실행한다.
5. API, 브라우저, 로그, 이벤트와 저장 상태에서 관찰값을 수집한다.
6. 시험 조건을 해제하고 기준선 복구 여부를 확인한다.

### 4.3 판정과 설명

1. ControlProof가 기대 결과와 관찰값을 비교한다.
2. 각 판정 규칙의 성공·실패·평가 불가를 표시한다.
3. 전체 결과를 `PASS`, `FAIL`, `판정 불가`, `미실행`으로 표시한다.
4. 판정에 사용된 증적과 사용하지 못한 증적을 구분한다.
5. 비개발자가 이해할 수 있는 실패 의미와 검증 한계를 표시한다.

### 4.4 수정과 재시험

1. 팀이 `FAIL` 원인과 수정 대상을 확인한다.
2. WhyYou를 수정하되 최초 실행과 증적은 그대로 보존한다.
3. 같은 시나리오·합성 데이터·시험 조건으로 재시험한다.
4. 새 실행은 최초 실행 ID를 참조한다.
5. 최초 결과와 재시험 결과를 나란히 비교한다.

### 4.5 대상 기능 부재 처리

1. 시나리오가 요구하는 기능이 WhyYou에 존재하지 않는지 확인한다.
2. 기능 부재 근거를 연결한다.
3. 실행을 수행한 것처럼 꾸미지 않는다.
4. 결과를 `판정 불가: NO_TEST_TARGET`로 표시한다.
5. 향후 기능이 생겼을 때 활성화할 시나리오로 보존한다.

## 5. 제품 경계

### 5.1 ControlProof가 책임지는 것

- 시나리오 정의와 버전 관리
- 실행 준비 상태 확인
- 시험 실행 ID 발급
- 합성 데이터 준비와 기준선 복원
- 우회·변경·장애 조건 적용과 해제
- 관찰값과 원본 증적 수집
- 판정 규칙 실행
- 최초 실행과 재시험 연결
- 결과 화면과 보고서 제공

### 5.2 WhyYou가 책임지는 것

- 고지·동의·자료 제출·분석 흐름
- 면접·리포트·Evidence 생성
- 사람 검토와 최종 채용 결정
- 지원 건·채용 단계·상태 전이
- 감사 로그·Outbox·큐·작업 상태
- ControlProof가 시험하는 보호조치의 실제 동작

### 5.3 시험을 위해 허용하는 WhyYou 변경

- 테스트 환경에서만 동작하는 장애·변경 주입 연결점
- 합성 데이터와 테스트 계정 생성 지원
- 필요 시 읽기 전용 증적 조회 경로
- 최초 실패가 확인된 뒤 해당 실패를 수정하는 제품 코드

다음은 허용하지 않는다.

- WhyYou에 없는 이의제기 기능을 이번 MVP를 위해 신규 구현
- 운영 환경에서 장애 주입을 활성화할 수 있는 구조
- 실제 지원자 개인정보 사용
- 시험이 통과하도록 결과를 직접 조작하는 전용 우회

## 6. 핵심 도메인 개념

### 6.1 검증 대상

시험할 AI 서비스와 그 버전이다. MVP에서는 WhyYou 하나만 지원한다.

최소 식별 정보:

- 서비스 이름
- 코드 버전 또는 커밋
- 정책 버전과 내용 해시
- 평가 기준·모델·프롬프트·설정 버전 중 시나리오에 필요한 값

### 6.2 시나리오 정의

서비스에 독립적인 통제 의도와 서비스별 실행 정보를 결합한 시험 명세다.

최소 포함 내용:

- 시나리오 ID와 통제 분류
- 통제 의도
- 수혜자와 개시자
- 법·정책 근거
- 전제조건
- 합성 데이터 종류
- 시험 조건 종류
- 실행 단계
- 기대 결과
- 판정 규칙
- 필수 증적
- WhyYou 연결 정보

### 6.3 시나리오 준비 상태

시나리오의 대상 존재 여부와 ControlProof의 실행 준비 여부를 분리한다.

| 준비 상태 | 의미 | 사용자 표시 |
|---|---|---|
| `READY` | 대상 기능과 필요한 실행·관찰 수단이 모두 준비됨 | 실행 가능 |
| `RUNNER_NOT_READY` | 대상 기능은 있으나 시드·어댑터·주입 수단이 미구현 | 준비 중, 실행 불가 |
| `ACCESS_BLOCKED` | 대상 기능은 있으나 허용된 접근 범위로 관찰할 수 없음 | 접근 필요 |
| `NO_TEST_TARGET` | 대상 서비스에 필수 기능 자체가 없음 | 판정 불가 대상 |

`RUNNER_NOT_READY`를 `NO_TEST_TARGET`로 처리하지 않는다. 예를 들어 H-03의 reporting 기능은 존재하지만 장애 주입 수단이 아직 없다면 대상 부재가 아니라 실행기 미준비다.

### 6.4 시험 실행

한 시나리오를 특정 대상 버전, 합성 데이터와 시험 조건으로 수행한 단위다.

각 실행은 다음을 가진다.

- 고유 실행 ID
- 시나리오 버전
- 대상 서비스 버전
- 시험 대상 합성 데이터
- 실행 시작·종료 시각
- 실행 전 기준선
- 적용한 시험 조건
- 수동 단계와 자동 단계
- 복구 결과
- 관찰값과 증적
- 판정
- 최초 실행 또는 재시험 관계

### 6.5 시험 대상 합성 데이터

한 실행 안에 여러 지원자가 있을 수 있으므로 모든 관찰값은 어느 지원자나 처리 건에 속하는지 식별할 수 있어야 한다.

- 상태 시드: H·E 시나리오에 사용하는 검토 가능한 합성 지원자
- 경로 시드: N 시나리오에 사용하는 실제 동의 경로를 거친 합성 지원자
- 대조군: 장애를 적용하지 않아 정상 기준을 보여주는 합성 지원자

### 6.6 시험 조건

| 종류 | 의미 | 예시 |
|---|---|---|
| 정상 | 변경 없이 정상 흐름 실행 | 유효한 Evidence로 리포트 생성 |
| 우회 시도 | 정상 화면 흐름을 건너뛰거나 주체·순서를 바꿈 | 동의 전 분석 호출, 비회사 주체 결정 요청 |
| 데이터 변경 | 정책·기준·증적을 시험 목적으로 바꿈 | 정책 교체, Evidence 제거, 가중치 변경 |
| 장애 주입 | 처리 경로나 워커·저장을 사용할 수 없게 함 | reporting 워커 중단, 저장 직전 오류 |

각 조건은 적용 방법, 적용 시각, 영향 대상, 해제 방법과 복구 확인을 가져야 한다.

### 6.7 관찰값

판정에 사용하는 구조화된 사실이다. 같은 키라도 지원자·시점·단계·재시도에 따라 값이 달라질 수 있으므로 이를 구분할 수 있어야 한다.

제품 수준에서 필요한 최소 구분:

- 어떤 실행인가
- 어떤 시험 대상인가
- 어떤 실행 단계인가
- 장애 전·장애 중·복구 후 중 어느 구간인가
- 몇 번째 시도인가
- 언제 관찰했는가
- 어디에서 관찰했는가
- 값이 존재하는가, 조회 결과 존재하지 않는가, 조회하지 못했는가
- 어떤 원본 증적을 참조하는가

`조회했고 존재하지 않음`은 판정 가능한 관찰이다. `조회하지 못함`은 증적 부족이며 같은 의미가 아니다.

### 6.8 증적

화면 캡처, API 요청·응답, 로그, 이벤트, DB 조회 결과와 테스트 조건 기록 등 판정을 뒷받침하는 원본 또는 원본 참조다.

증적은 최소한 다음 정보를 확인할 수 있어야 한다.

- 실행 ID와 시나리오 ID
- 대상 버전
- 시험 대상 식별자
- 수집 단계와 구간
- 수집 시각과 출처
- 원본 위치 또는 저장 파일
- 원본이 이후 바뀌지 않았음을 확인할 수 있는 식별값
- 판정에 사용됐는지 여부

### 6.9 판정 규칙과 판정

판정 규칙은 개별 기대 결과를 구조화한 것이다. 한 실행의 전체 판정은 규칙 결과와 증적 확보 상태를 종합한다.

사용자에게 표시하는 결과 상태:

| 결과 | 의미 |
|---|---|
| `PASS` | 모든 필수 기대 결과와 증적을 확인함 |
| `FAIL` | 관찰한 동작이 기대 결과와 다르거나 보호조치가 작동하지 않음 |
| `판정 불가` | 대상 부재, 접근 제한, 증적 부족 또는 증적 충돌로 결론을 낼 수 없음 |
| `미실행` | 시나리오는 정의됐지만 실제 실행 결과가 없음 |

판정 불가 사유 코드는 다음 명칭으로 통일한다.

- `NO_TEST_TARGET`
- `ACCESS_LIMITED`
- `INSUFFICIENT_EVIDENCE`
- `EVIDENCE_CONFLICT`

`FAIL`과 일부 증적 부족이 함께 있으면 관찰된 실패를 숨기지 않는다. 다만 보고서에는 확인하지 못한 증적도 함께 표시한다.

### 6.10 재시험

수정 후 같은 시나리오를 다시 실행한 별도 시험 실행이다.

- 최초 실행을 참조한다.
- 최초 실행을 수정하거나 삭제하지 않는다.
- 대상 버전과 수정 내용을 구분한다.
- 입력·조건이 달라지면 그 차이를 표시한다.
- 비교 화면에서 규칙별 변화와 증적 차이를 확인할 수 있어야 한다.

## 7. 핵심 화면

### 7.1 검증 워크벤치

사용 목적: 현재 검증 범위와 실행 현황을 한눈에 확인한다.

필수 정보:

- 검증 대상과 버전
- 통제 4종과 시나리오 12개
- 시나리오별 대상 존재 여부와 실행 준비 상태
- 최근 결과 상태
- `PASS`, `FAIL`, `판정 불가`, `미실행` 개수
- 재시험이 필요한 실패
- 보고서 진입

핵심 행동:

- 시나리오 상세 열기
- 실행 가능한 시나리오 필터링
- 실패와 판정 불가 항목 필터링

### 7.2 시나리오 상세·실행 화면

사용 목적: 무엇을 왜 시험하는지 이해하고 실행 조건을 확인한 뒤 시험을 시작한다.

필수 정보:

- 시나리오 의도와 보호 대상
- 법·정책 근거
- WhyYou에서의 구현 위치
- 전제조건과 준비 상태
- 합성 데이터와 대조군
- 시험 조건과 복구 방법
- 실행 단계
- 기대 결과와 판정 규칙
- 필수 증적
- 수동 단계 표시

핵심 행동:

- 시험 실행 시작
- 실행 불가 사유 확인
- 이전 실행 열기
- 재시험 시작

### 7.3 실행 결과·증적 화면

사용 목적: 기대 결과와 실제 관찰 결과를 비교하고 판정 근거를 추적한다.

필수 정보:

- 실행 ID, 대상 버전과 실행 시각
- 실행 단계별 진행 결과
- 적용·해제한 시험 조건
- 시험 대상별 관찰값
- 규칙별 기대값·관찰값·결과
- 전체 판정과 사유 코드
- 누락·충돌 증적
- 원본 증적 링크 또는 미리보기
- 복구 확인 결과
- 비개발자용 실패 의미

핵심 행동:

- 원본 증적 열기
- 실패 규칙만 보기
- 수정 메모 등록
- 재시험 시작

### 7.4 재시험 비교·보고서 화면

사용 목적: 최초 결과와 수정 후 결과를 비교하고 검증 범위와 한계를 공유한다.

필수 정보:

- 최초 실행과 재시험의 대상 버전
- 수정 내용
- 규칙별 이전·이후 결과
- 이전·이후 증적
- 결과 변화와 남은 실패
- 실행하지 않은 시나리오
- 대상 기능 부재와 판정 불가 사유
- 합성 데이터 사용 표시
- 검증 범위와 미검증 범위
- 법적 준수 전체를 보증하지 않는다는 한계

## 8. 대표 제품 흐름

### 8.1 첫 번째 개발 수직 흐름: H-03 최소형

목적: ControlProof의 핵심 구조인 조건 주입 → 관찰 → 판정 → 증적 → 복구를 가장 작은 범위에서 검증한다.

최소 범위:

1. 합성 지원자 한 명을 리포트 생성 대기 상태로 준비한다.
2. 정상 기준선을 기록한다.
3. reporting 워커 또는 처리 경로 한 곳을 중단한다.
4. 리포트 생성 실패가 관찰 가능한지 확인한다.
5. 최종결정 요청이 차단되는지 확인한다.
6. 장애와 요청 결과의 원본 증적을 수집한다.
7. 판정을 화면에 표시한다.
8. 장애를 해제하고 복구를 확인한다.

이 최소 흐름이 성공한 뒤 다음을 확장한다.

- 칸반·일괄 단계 이동 우회
- 재시도 한도 소진과 DLQ
- 저장 직전·직후 오류
- 복구 후 중복 이벤트·결정 방지
- 대조군과 복수 지원자
- 최초 실패와 수정 후 재시험 비교

### 8.2 MVP 필수 완주 흐름

V4의 비협상 완료선은 다음 세 시나리오다.

- N-02: 동의 완료 전 처리 차단과 정상 처리 순서
- H-03: reporting 장애의 실패 노출과 결정 차단
- E-03: 장애·재시도·복구 과정의 증적과 중복 부작용 확인

H-03과 E-03은 같은 장애 실행에서 서로 다른 통제 관점으로 판정할 수 있다. 동일한 실행과 증적을 공유하더라도 판정 목적과 규칙은 구분한다.

### 8.3 근거 무결성 보조 데모

- E-01: 유효하지 않거나 사라진 Evidence를 인용한 점수 차단
- E-02: 기준·가중치 변경 후 과거 리포트 보존

### 8.4 검증 공백 공개

- A-01~A-03은 WhyYou에 지원자가 개시하는 이의제기 기능이 없으므로 실행하지 않는다.
- 기능 부재 근거와 함께 `판정 불가: NO_TEST_TARGET`로 표시한다.
- 이번 MVP에서 이의제기 기능이나 고지 문구를 새로 만들지 않는다.

## 9. 핵심 제품 요구사항

### 9.1 시나리오 변경 가능성

- 시나리오 문구, 단계, 기대 결과와 필수 증적을 코드 수정 없이 변경할 수 있어야 한다.
- 시나리오 버전과 그 버전으로 실행한 결과를 연결해야 한다.
- 과거 실행은 당시 시나리오 정의로 해석할 수 있어야 한다.
- 서비스별 구현 정보가 공통 통제 의도에 섞이지 않아야 한다.

### 9.2 실행 재현성

- 같은 초기 상태와 조건으로 재시험할 수 있어야 한다.
- 합성 데이터 식별자는 실행 간 충돌하지 않아야 한다.
- 사람이 수행한 단계는 명확히 표시해야 한다.
- 복구 실패 시 다음 실행을 시작하지 않거나 오염 가능성을 경고해야 한다.

### 9.3 관찰 정확성

- 여러 지원자와 여러 실행 단계를 구분해야 한다.
- 시간에 따른 정상 상태 변화와 같은 시점의 증적 충돌을 구분해야 한다.
- 조회 성공·부재와 조회 실패를 구분해야 한다.
- 동일 요청의 재시도와 중복 효과를 구분할 수 있어야 한다.

### 9.4 판정 설명 가능성

- 전체 판정만 보여주지 않고 규칙별 결과를 보여줘야 한다.
- 기대값, 관찰값과 사용한 증적을 연결해야 한다.
- 실패와 판정 불가의 원인을 비개발자가 이해할 수 있게 설명해야 한다.
- 판정 규칙만으로 표현할 수 없는 기대 결과를 억지로 자동 판정하지 않는다.

### 9.5 증적 신뢰성

- 모든 증적은 실행·시나리오·대상·단계·시각과 연결돼야 한다.
- 원본과 화면용 설명을 구분해야 한다.
- 보고서에서 사용한 증적과 참고 증적을 구분해야 한다.
- 민감정보와 인증정보를 증적에 저장하지 않는다.
- 최초 실행 증적은 재시험으로 덮어쓰지 않는다.

### 9.6 대상 서비스 보호

- 장애·변경 주입은 허용된 테스트 환경과 합성 데이터에만 적용한다.
- 주입 전 기준선과 해제 후 복구 상태를 확인한다.
- 운영 환경으로 오인될 경우 실행을 차단해야 한다.
- 실제 외부 AI 호출과 비용이 발생하는 경로를 기본 실행에서 사용하지 않는다.

## 10. 2주 MVP 성공 기준

### 10.1 제품 성공 기준

- 사용자가 워크벤치에서 12개 시나리오의 대상 존재 여부와 준비 상태를 이해할 수 있다.
- N-02, H-03, E-03을 실제 WhyYou 시험환경에서 완주한다.
- 실행 ID로 화면, 요청·응답, 로그, 이벤트와 상태 기록을 연결한다.
- 최소 한 건에서 `FAIL → 수정 → 재시험 → PASS`를 보여준다.
- 최초 실행과 재시험 결과가 모두 보존된다.
- A-01~A-03이 기능 부재 근거와 함께 `NO_TEST_TARGET`로 표시된다.
- 실행하지 않은 항목이 `PASS`로 표시되지 않는다.
- 실제 개인정보와 실제 클라우드 AI 호출 없이 대표 데모가 가능하다.

### 10.2 품질 성공 기준

- 동일한 시나리오와 기준선으로 반복 실행했을 때 판정이 일관된다.
- 조회 실패가 `absent`로 잘못 기록되지 않는다.
- 여러 지원자·단계·시도의 관찰값이 서로 섞이지 않는다.
- 장애 해제 후 기준선 복구 여부가 기록된다.
- 판정 결과에서 사용한 원본 증적으로 이동할 수 있다.
- 스펙에 없는 기능을 AI 에이전트가 임의로 추가하지 않는다.

### 10.3 데모 성공 기준

비개발자가 다음 질문에 화면만 보고 답할 수 있어야 한다.

- 무엇을 왜 시험했는가?
- 어떤 조건을 직접 만들었는가?
- 실제로 무엇이 일어났는가?
- 왜 이 판정이 나왔는가?
- 실패 후 무엇을 수정했는가?
- 같은 조건의 재시험에서 무엇이 달라졌는가?
- 무엇은 아직 검증하지 못했는가?

## 12. UI 프로토타입 원칙

상세 기술 Spec 전에 목업 데이터로 네 핵심 화면을 확인한다. 이 프로토타입은 제품 흐름 검증용이며 실제 실행을 한 것처럼 표시하지 않는다.

- 모든 목업 실행에는 `DEMO DATA` 또는 `MOCK` 표시를 한다.
- 실제 판정 로직을 프런트엔드에 하드코딩하지 않는다.
- WhyYou의 테이블·큐·내부 필드명을 기본 사용자 언어로 노출하지 않는다.
- 개발자용 원본 정보와 비개발자용 설명을 단계적으로 보여준다.
- `판정 불가`와 `미실행`, `NO_TEST_TARGET`과 `RUNNER_NOT_READY`를 시각적으로 구분한다.
- 최초 실행과 재시험이 별도 기록이라는 점을 화면에서 확인할 수 있어야 한다.

프로토타입 승인 후 화면 구조와 상태 이름을 기능별 Spec에 반영한다.

## 13. 첨부 골격의 채택 기준

### 13.1 우선 채택할 개념

- 시나리오를 데이터로 관리하는 방향
- 서비스 독립적인 통제 의도와 WhyYou 구현 정보 분리
- 실행 ID와 재시험 관계
- `PASS`, `FAIL`, `INCONCLUSIVE`, `NOT_RUN` 구분
- 판정 불가 사유 세분화
- 조회 결과 부재와 조회 실패의 구분
- 상태 시드와 경로 시드 분리
- H-03 최소 수직 흐름을 통한 조기 검증

### 13.2 재검토 후 채택할 부분

- Observation과 EvidenceBundle의 구체적인 필드
- 관찰값 키 사전의 범위와 명명 규칙
- 네 가지 판정 규칙 타입만으로 충분하다는 가정
- H-03 전체 YAML의 단계와 규칙 구성
- 상태 시드의 실제 WhyYou DB 호환성
- 오류·DLQ·감사 로그의 수집 방법

### 13.3 수정이 필요한 부분

- 실행기 미준비를 `NO_TEST_TARGET`로 판정하는 구조
- 대상 지원자와 실행 구간을 구분하지 못하는 관찰값 구조
- 시간에 따른 정상 상태 변화를 증적 충돌로 볼 수 있는 구조
- 문서·템플릿·코드 사이의 판정 불가 사유 코드 불일치
- 제품 흐름과 UI 요구사항 없이 증적 스키마를 먼저 고정한 순서

### 13.4 현재 코드의 위치

첨부 코드는 폐기 대상이 아니라 검증해야 할 아키텍처 스파이크다. 기능별 Spec과 기술 Plan이 승인되기 전에는 제품 계약으로 간주하지 않는다. 승인된 설계와 맞는 코드는 재사용하고, 맞지 않는 부분은 최초 구현 비용으로 보고 수정한다.

## 15. 구현 전 결정 사항 — 확정

기존 미결정 항목은 2026-09-23에 MVP 구현 기준으로 확정했다. 상세한 이유, 영향과 재검토 조건은 [MVP 결정 기록](./ControlProof_MVP_Decision_Log.md)을 기준으로 한다.

| ID | 항목 | 확정 내용 |
|---|---|---|
| D-001 | 실행과 대상 | 한 Run에 여러 합성 지원자를 허용하되 모든 관찰·증적에 `subject_ref`를 필수로 둔다. |
| D-002 | 관찰 구간 | `phase(BASELINE/INJECTED/RECOVERED)`, `step_id`, `attempt`를 함께 기록한다. |
| D-003 | 증적 충돌 | 같은 대상·구간·단계·시도의 같은 사실을 말하는 출처가 모순될 때만 충돌로 본다. 시간에 따른 정상 변화는 충돌이 아니다. |
| D-004 | 증적 보관 | 판정에 사용한 최소 원본은 Run 저장소에 복사하고 원본 locator도 남긴다. 전체 로그·DB는 복사하지 않는다. |
| D-005 | 증적 해시 | 저장 증적에 SHA-256과 수집 메타데이터를 필수로 둔다. 전자서명은 MVP에서 제외한다. |
| D-006 | 중단·복구 실패 | 실행 생명주기와 판정을 분리한다. 중단·복구 실패는 PASS/FAIL이 될 수 없고 `INCONCLUSIVE`로 표시한다. |
| D-007 | 브라우저 자동화 | Playwright는 N-01 PC·모바일과 핵심 화면 증적에 한정하고, API·로그·DB 검증은 adapter 기반으로 한다. |
| D-008 | H-03과 DLQ | 첫 수직 흐름은 리포트 실패·표시·결정 안전·복구까지, DLQ는 후속 확장으로 구현하되 2주 최종 범위에는 포함한다. |
| D-009 | 멱등성 | 재시도 중 이벤트·결정 이력의 중복·누락 판정은 E-03이 소유하고, H-03은 결정 안전성을 판정한다. |
| D-010 | 첨부 골격 | 구현 시작점으로 채택하되 spike로 취급한다. 핵심 계약을 바로잡은 뒤 확장하며 현재 YAML·스키마를 고정하지 않는다. |
| D-011 | reason code | 판정 불가 4종과 실행 준비 상태를 표준화하고 문서·코드·화면에서 같은 명칭을 사용한다. |

이 결정은 기능 Spec 001의 입력이다. `clarify` 단계에서는 결정을 다시 원점에서 고르는 대신, 실제 WhyYou 접점과 모순되는 사실이 발견될 때만 변경 제안을 낸다. 증적 스키마와 시나리오 YAML은 기능 Spec과 Plan을 거쳐 계약으로 고정한다.

## 16. Product Brief 완료 기준

이 문서는 다음 질문에 팀이 같은 답을 할 수 있을 때 최종 승인한다. 현재는 제품 책임자의 위임에 따라 기능 Spec 001을 시작할 수 있는 임시 기준선으로 승인한다.
