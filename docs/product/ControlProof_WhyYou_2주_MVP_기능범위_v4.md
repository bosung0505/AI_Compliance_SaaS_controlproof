# ControlProof × WhyYou 2주 MVP 기능 범위

## 0. 문서 상태

- 문서 목적: WhyYou를 검증 대상으로 사용하는 ControlProof 2주 MVP의 제품 범위와 완료 기준 합의
- 검토 기준: WhyYou 공개 저장소 `jhkim0602/gbsa_aws`의 현재 `main` 소스
- 작성 기준일: 2026-09-23
- 현재 단계: 기능·시나리오·결과물 범위 정의
- 아직 다루지 않는 것: 상세 API, DB 스키마, 배포 아키텍처, 구현 프레임워크 선정

이 문서는 팀원이 개발을 시작하기 전에 다음 내용을 같은 의미로 이해하기 위한 기준 문서다.

- WhyYou에 이미 있는 기능과 새로 만들어야 할 기능
- 2주 안에 반드시 작동해야 하는 핵심 흐름
- 실제로 실행할 시나리오와 증적
- 통과·실패·판정 불가·미실행의 구분
- 2주 MVP의 완료선과 제외 범위

## 1. 한 문장 제품 정의

> 합성 지원자를 WhyYou에 투입해 정상·우회·예외·장애 조건을 실제로 실행하고, ControlProof가 보호 절차의 작동 여부를 근거와 함께 판정하며, 실패 수정 후 재시험 결과까지 보여주는 검증 MVP다.

## 2. 절대 바뀌면 안 되는 전제

### 2.1 AI 점수는 참고 정보다

- WhyYou의 AI 점수는 채용 담당자의 판단을 돕는 참고 정보다.
- 특정 점수 미만을 자동 탈락시키거나 특정 점수 이상을 자동 합격시키지 않는다.
- 모든 지원자의 최종 채용 판단은 사람이 수행한다.
- AI 점수가 더 낮은 지원자가 사람의 종합적인 판단에 따라 채용될 수 있다.
- AI 점수가 더 높은 지원자도 사람이 확인한 다른 근거에 따라 채용되지 않을 수 있다.
- 서로 다른 점수를 가진 합성 지원자는 인간 판단의 독립성을 확인하기 위한 시험 데이터일 뿐, 점수 임계값을 의미하지 않는다.

### 2.2 ControlProof는 문서 체크리스트가 아니다

ControlProof는 다음 제품이 아니다.

- 법령을 요약해 주는 서비스
- 사용자가 체크박스에 완료 표시만 하는 서비스
- 이미 발생한 로그를 모아 보여주는 모니터링 화면
- AI 채용 모델의 정확도나 편향을 평가하는 서비스
- 법적 준수 전체를 자동으로 인증하는 서비스

이번 MVP가 보여줘야 하는 본질은 다음과 같다.

1. 실패할 수 있는 조건을 직접 만든다.
2. WhyYou의 보호 절차가 실제로 작동하는지 시험한다.
3. 기대 결과와 실제 관찰 결과를 비교한다.
4. 통과·실패·판정 불가·미실행을 근거와 함께 보여준다.
5. 실패를 수정한 뒤 같은 조건으로 재시험한다.
6. 최초 결과와 재시험 결과를 모두 보존한다.

## 3. WhyYou 저장소 확인 결과와 MVP 출발점

현재 WhyYou에는 일부 보호 기능이 이미 존재하지만, ControlProof의 12개 시나리오를 곧바로 전부 실행할 수 있는 상태는 아니다. 기존 기능과 신규 개발 범위를 다음과 같이 구분한다.

| 영역 | WhyYou 현재 상태 | 2주 MVP에서 할 일 | 분류 |
|---|---|---|---|
| AI 사용 고지 | AI 평가 보조, 사람의 최종 결정, 녹화·처리 목적 문구가 동의 정책에 존재 | PC·모바일 표시와 동의 전 처리 차단, 정책 버전 전환 검증 | 기존 기능 검증 |
| 동의 기록 | 정책 버전, 내용 해시, 동의 시각, 동의 완료 이벤트 존재 | ControlProof 실행 ID와 연결하고 분석 시작과 순서 비교 | 기존 기능 활용 |
| 지원자 생성 | 초대 batch API가 여러 합성 지원자 생성에 충분함 | CSV를 별도 통제 경로로 시험하지 않고 batch API 사용 | 별도 시나리오 제외 |
| 인간 최종 결정 | 사람 전용 최종결정 경로가 있으나 우회·장애 조건은 추가 확인 필요 | 현재 상태를 먼저 시험해 FAIL을 남기고, 필요한 보완 후 PASS 재시험 | 시험 후 수정 대상 |
| 이의제기 | 결과 통지·접수·배정·재검토·통지 기능이 없음 | 신규 구현하지 않고 A-01~A-03 모두 `판정 불가` 처리 | 검증 대상 없음 |
| 증적 기록 | Evidence 인용 검증, 점수 입력 동결, Outbox·재시도·DLQ 기반 존재 | 검증 우회·기준 변경·워커 장애를 실제로 주입해 불변식 확인 | 기존 기능 검증 |
| 장애 주입 | ControlProof용 장애·누락 주입 기능 없음 | 테스트 환경 전용 최소 장애·누락 주입 기능 추가 | 신규 구현 |
| 상태 시드 | 데모 시드가 제거된 상태 | 회사·포지션·초대·면접·리포트·Evidence 행을 직접 생성해 검토 대기 지원자를 만든다 | 신규 구현 |
| 경로 시드 | 초대·토큰 교환·본인 확인·동의 API는 존재 | 실제 API를 순서대로 호출해 동의까지 실제로 거친 지원자를 만든다 | 신규 구현 |
| 결정론적 AI 대역 | 제거된 상태 | 실제 클라우드 호출 없이 고정 결과로 리포트를 생성한다 | 신규 구현 |
| 초기화·재실행 | 없음 | 시험 전 초기 상태 생성과 시험 후 기준선 복원을 자동화한다 | 신규 구현 |

### 3.1 현재 상태를 숨기지 않는다

- 아직 존재하지 않는 기능을 이미 구현된 것처럼 표시하지 않는다.
- 현재 WhyYou에서 실행하면 실패하는 시나리오는 최초 결과를 `FAIL`로 남길 수 있다.
- 접근할 증적이 부족하면 `PASS`가 아니라 `판정 불가`로 표시한다.
- 대상 기능 자체가 없으면 `판정 불가: NO_TEST_TARGET`로 표시한다.
- 대상 기능은 있으나 일정상 실행하지 못한 시나리오는 `미실행`으로 표시한다.
- 데모를 위해 만든 테스트 전용 기능은 기존 WhyYou 제품 기능과 구분한다.

### 3.2 저장소에서 재사용할 기반

다음 자산은 새로 만들지 않고 최대한 재사용한다.

- 지원자 초대와 접근 링크
- 본인 확인과 동의 단계
- 동의 정책 버전과 내용 해시
- 제출 자료 등록과 분석 상태
- AI 면접 및 리포트
- 사람 검토 화면과 HumanReview 기록
- 채용 단계와 최종결정 기록
- 감사 로그와 아웃박스 이벤트
- 평가 기준 버전 고정
- 모델·프롬프트·설정 버전
- 로컬 PostgreSQL, LocalStack, Mailpit 환경

### 3.3 합성 지원자를 만드는 두 가지 방법

합성 지원자를 만드는 방법은 두 가지이며 서로 대체할 수 없다.

| | 상태 시드 | 경로 시드 |
|---|---|---|
| 방식 | DB에 행을 직접 생성 | 초대 발급부터 동의까지 실제 API를 순서대로 호출 |
| 결과 | 리포트까지 준비된 검토 대기 지원자 | 동의 절차를 실제로 거친 지원자 |
| 사용 시나리오 | H-01~H-03, E-01~E-03 | N-01~N-03 |
| AI 호출 | 없음 (고정 결과 대역 사용) | 없음 (면접 전 단계에서 끝남) |

- 상태 시드로 만든 지원자는 동의 화면을 거치지 않았으므로 고지·동의 통제 시험에 사용하지 않는다.
- 경로 시드로 만든 지원자는 면접과 리포트가 없으므로 검토·결정 시험에 사용하지 않는다.
- E-02는 두 시드를 함께 사용한다. 동의 정책 버전은 경로 시드에서, 평가 기준 버전과 `scoring_inputs`는 상태 시드에서 확보한다.

- ControlProof 제품 담당자
- WhyYou 개발자
- QA 담당자

- 납품 및 사업 책임자

- 법무·컴플라이언스 담당자

비개발 검토자도 다음 내용을 판단할 수 있어야 한다.

- 어떤 조건에서 실행했는가

- 어떤 근거로 판정했는가
- 수정 후 결과가 어떻게 달라졌는가
- 무엇은 아직 검증하지 못했는가

## 5. MVP 전체 사용자 흐름

1. 검증 대상 `WhyYou`와 대상 버전을 선택한다.
2. 통제 4종과 12개 시나리오의 준비 상태를 확인한다.
3. 실행할 시나리오와 합성 지원자를 선택한다.
4. 정상·예외·장애·증적 누락 조건 중 하나를 선택한다.
5. ControlProof가 고유한 시험 실행 ID를 발급한다.
6. 시험 실행 ID를 기준으로 WhyYou의 화면·요청·이벤트·로그를 연결한다 (6.2).
7. WhyYou에서 실제 사용자 흐름을 실행한다.
8. ControlProof가 화면, 상태, 이벤트, 감사 기록, 버전 정보를 수집한다.
9. 기대 결과와 실제 관찰 결과를 비교한다.
10. `PASS`, `FAIL`, `판정 불가`, `미실행` 중 하나로 판정한다.
11. 실패 원인과 누락된 증적을 확인한다.
12. WhyYou를 수정하거나 정상 상태로 복구한다.
13. 동일한 시나리오와 초기 조건으로 재시험한다.
14. 최초 결과와 재시험 결과를 비교한다.
15. 전체 결과와 한계를 보고서에서 확인한다.

## 6. 공통 시험 개념

### 6.1 시험 실행 ID

모든 실행은 고유한 시험 실행 ID를 가진다. 이 ID는 다음 기록을 하나의 시험 건으로 묶는 기준이다.

- 합성 지원자
- WhyYou 지원자·초대·면접·리포트 식별자
- 브라우저 화면 캡처
- API 요청과 응답
- 감사 로그와 아웃박스 이벤트
- 상태 변경 이력
- 오류 및 장애 기록
- 최종 판정과 재시험 관계

WhyYou의 기존 `trace_id`를 활용할 수 있지만, ControlProof 화면에서는 사람이 이해할 수 있는 시험 실행 ID로 표시한다.

### 6.2 시험 실행 ID를 WhyYou 기록과 연결하는 방식

연결 방식은 두 가지이며, 2주 MVP는 1단계를 기본으로 한다.

**1단계 상관관계 연결 (기본)**

WhyYou를 수정하지 않는다. 합성 지원자 ID, 초대 ID, 실행 시각 범위, WhyYou가 자체 생성한 `trace_id`를 ControlProof가 수집해 시험 실행 ID에 매핑한다. 합성 데이터만 사용하므로 식별자가 유일하며, 한 건을 동의부터 최종결정까지 재구성할 수 있다.

**2단계 실행 ID 전파 (여유 시)**

요청 헤더로 시험 실행 ID를 전달하고 WhyYou가 감사 로그에 함께 기록한다. 증적이 더 직접적이지만 WhyYou 수정이 필요하므로 1단계가 완주한 뒤에 검토한다.

두 방식 중 무엇을 사용했는지는 결과 보고서에 표시한다.

### 6.3 Reporting 장애와 검토 가능 상태

H-03의 `reporting 큐`는 사람 검토 대기자 목록이 아니라 면접 분석 결과를 최종 리포트로 만드는 비동기 처리 경로를 뜻한다. 다음 상태를 구분한다.

- 리포트 생성 대기·처리 중
- 리포트 생성 실패·재시도 중
- 애플리케이션 작업이 `JobStatus.DLQ`로 전환됨
- 메시지가 인프라의 SQS DLQ로 이동함
- 리포트가 준비돼 사람이 검토할 수 있음

리포트가 준비되지 않은 지원자는 사람의 최종결정 대상이 아니다. 담당자 화면은 아직 처리 중인 상태와 최종 실패를 구분해 보여줘야 하며, H-03에서는 정상 최종결정 API뿐 아니라 칸반·일괄 이동 등 일반 단계 변경 경로의 우회도 함께 시험한다.

### 6.4 AI 처리 시작 시점

`동의 완료 이벤트가 분석 큐에 들어간 시점`을 AI 평가 시작으로 잘못 해석하지 않는다. N-02에서 비교할 사건은 다음과 같다.

1. 고지 확인 또는 동의 완료
2. 지원 자료 제출
3. 분석 요청
4. 실제 분석 시작 또는 `analyzing` 상태 전환

최소 판정 조건은 `동의 완료 시각 < 분석 요청 시각 ≤ 실제 분석 시작 시각`이다.

### 6.5 실행 방식

- `브라우저`: 화면 노출, 모바일 가독성, 버튼·메일 링크 확인
- `API`: 상태 전환, 우회 호출, 보류·거부 응답 확인
- `로그`: 감사 로그, 이벤트, 버전, 처리 주체 확인
- `장애 주입`: 검토 처리 불가, 기록 누락 등 시험 전용 조건 생성
- `혼합`: 브라우저·API·로그를 하나의 실행에서 함께 사용

완전 자동화 여부와 실제 실행 여부는 구분한다. 사람이 일부 단계를 수행하더라도 실제 시스템에서 실행되고 증적이 남으면 유효한 시험이다.

### 6.6 조건 주입의 세 가지 종류

ControlProof의 차별점은 "정상 상태에 존재하지 않는 조건을 직접 만든다"는 데 있다. 그 조건은 장애만이 아니며 세 종류로 나뉜다. 시나리오마다 어떤 종류를 쓰는지 명시한다.

| 종류 | 무엇을 만드는가 | 정상 테스트가 못 잡는 이유 |
|---|---|---|
| `장애 주입` | 처리 경로·워커·저장을 사용할 수 없게 만든다 | 그 상황이 실제로 발생해야만 드러난다 |
| `데이터 변경 주입` | 기준·정책·증적을 시험 목적으로 바꾸거나 제거한다 | 변경 이후의 과거 기록 영향은 배포 시점에 보이지 않는다 |
| `우회 시도` | 화면 흐름을 건너뛰고 경로·주체·순서를 바꿔 호출한다 | 기능 테스트는 정상 경로만 통과시킨다 |

12개 시나리오 중 대상 기능이 존재하는 9개는 다음과 같이 분포한다.

| 종류 | 시나리오 |
|---|---|
| 장애 주입 | N-02(동의 저장 실패), H-03(reporting 장애), E-03(워커 장애·DLQ) |
| 데이터 변경 주입 | N-03(정책 교체), E-01(Evidence 제거), E-02(기준 변경) |
| 우회 시도 | N-02(동의 전 호출), N-03(stale 제출), H-01(비인가 주체) |
| 주입 없음 (정적 검사) | N-01(고지 표시), H-02(쓰기 권한 표면) |

주입이 없는 두 시나리오는 조건을 만들 대상이 아니라 현재 상태를 확인하는 항목이다. 이 둘은 기존 QA로도 수행할 수 있으며, ControlProof의 기여는 시험 자체가 아니라 법 조항과의 연결·변경 시 반복·제출 가능한 증적에 있다. 보고서에는 이 구분을 숨기지 않고 표시한다.

## 7. WhyYou에서 준비해야 할 기능

### 7.1 AI 사용 사전 고지 보완

- 기존 `AI 평가 보조`, `사람이 최종 결정함`, 녹화·처리 목적, 보관·삭제 문구를 시험한다.
- 아직 존재하지 않는 이의제기 기능을 고지 문구에 먼저 추가하지 않는다. 기능 없는 권리를 안내하는 허위 고지가 될 수 있기 때문이다.
- 문구 변경이 필요해지는 시점에는 정책 버전과 내용 해시를 함께 변경한다.
- 사용자가 동의 화면을 연 뒤 정책이 변경된 경우, 이전 `policy_version`·`content_digest`로 제출한 동의가 거부되는지 확인한다.
- PC와 390px 수준 모바일 화면에서 문구가 잘리지 않아야 한다.
- 고지 확인 또는 동의 완료 시각을 증적으로 확보한다.
- 동의 전에는 분석·녹화·평가가 시작되지 않아야 한다.

### 7.2 합성 지원자 생성 경로

합성 지원자 생성에는 WhyYou의 초대 batch API를 사용한다.

- CSV·JSON 불러오기는 별도의 백엔드 처리·동의 경로가 아니라 같은 초대 batch API로 수렴하므로 독립 시나리오로 시험하지 않는다.
- 여러 지원자 생성, 서로 다른 점수 조건과 반복 실행은 batch API만으로 구성한다.
- 지원자 생성 후에는 동일한 접근 → 본인 확인 → 동의 → 자료 제출 → 분석 흐름을 사용한다.

외부 ATS, 별도 재지원, CSV 전용 처리 경로는 이번 MVP의 시험 대상에 포함하지 않는다.

### 7.3 인간 최종결정 안전성 — 시험 후 수정 대상

H-01~H-03은 현재 WhyYou 상태에서 먼저 실행한다. 사전에 모두 고쳐 놓지 않고, 발견된 실패를 최초 `FAIL` 증적으로 보존한 뒤 필요한 부분만 수정하고 같은 조건으로 재시험한다. 이 흐름은 ControlProof의 `FAIL → 수정 → PASS` 핵심 데모 재료로 사용한다.

- H-01에서는 `COMPANY_USER`가 아닌 AI·SYSTEM·지원자 주체의 최종결정 시도가 거부되는지 확인한다.
- H-02에서는 AI 어시스턴트와 워커에 채용 상태 변경 기능이 노출되지 않았는지 확인한다.
- H-02에는 회사 사용자가 AI 점수 순위와 독립적으로 결정을 내릴 수 있는지도 함께 확인한다.
- H-03에서는 reporting 큐 장애로 리포트가 없을 때 실패가 화면에 드러나는지, 최종결정과 일반 단계 이동 모두 차단되는지, 재시도와 DLQ 이력이 남는지 확인한다.
- 최초 시험에서 발견된 우회, 실패 은폐, 부분 저장 또는 이력 누락만 수정한다.
- 수정 후 동일한 입력과 장애 조건으로 재시험해 `PASS` 전환을 확인한다.

### 7.4 이용자 보호·이의처리 — 신규 구현 제외

현재 WhyYou에는 지원자 결과 통지, 이의제기 접수, 원 결정 집행 보류, 재검토자 배정과 결과 통지 경로가 없다. 이번 2주 MVP에서는 이 기능을 새로 만들지 않는다.

- A-01~A-03은 모두 `판정 불가`로 기록한다.
- 공통 사유 코드는 `NO_TEST_TARGET`로 표시한다.
- 기능 부재를 `PASS`, `FAIL` 또는 `미실행`으로 바꾸지 않는다.
- ControlProof는 대상 기능이 없기 때문에 시험할 수 없다는 사실과 확인한 범위를 보고서에 설명한다.
- 향후 WhyYou에 이의제기 기능이 생기면 같은 시나리오 정의를 활성화해 다시 실행한다.

`NO_TEST_TARGET`는 증적 부족을 뜻하는 `INSUFFICIENT_EVIDENCE`, 접근 제한인 `ACCESS_LIMITED`, 증적 충돌인 `EVIDENCE_CONFLICT`와 구분한다.

### 7.5 증적 조회와 연결

ControlProof가 시험 실행 ID를 기준으로 다음 자료를 읽고 연결할 수 있어야 한다.

- 감사 이벤트와 아웃박스 이벤트
- 지원자 상태 변경 이력
- 동의 기록
- 리포트와 Evidence
- HumanReview와 최종결정
- 적용 버전
- 오류·재시도·실패 기록

MVP에서는 테스트 환경 전용 읽기 경로나 읽기 전용 저장소 접근을 허용할 수 있다. 운영 고객용 범용 커넥터는 만들지 않는다.

### 7.6 반복 가능한 합성 시험환경

- 실제 개인정보가 아닌 합성 회사·포지션·지원자만 사용한다.
- 상태 시드와 경로 시드를 각각 구성한다 (3.3). 둘을 하나로 합치지 않는다.
- 실행마다 같은 결과를 재현할 수 있는 고정 AI 응답 대역을 둔다.
- 실제 AWS·GCP AI·음성·OCR 호출 없이 대표 시나리오를 실행할 수 있어야 한다.
- 필요한 경우 Mailpit으로 실제 테스트 메일을 확인한다.
- 시험 전 초기 상태 생성과 시험 후 정리가 가능해야 한다.
- 동일한 초기 조건으로 재시험할 수 있어야 한다.
- 실제 클라우드 AI 경로는 결정론적 시험과 명확히 구분한다.

### 7.7 테스트 전용 시험 조건 주입

최소한 다음 조건을 선택적으로 만들고 복구할 수 있어야 한다.

**장애 주입**

- 동의 기록 저장 트랜잭션 실패
- 동의 완료 이벤트의 아웃박스 디스패치 지연
- reporting 큐 또는 워커 중단과 재시도 한도 소진
- 리포트 저장 직전·직후 워커 오류

**데이터 변경 주입**

- 동의 정책 버전·내용 해시 교체
- 저장된 Evidence 또는 연결된 자막 구간 제거
- 리포트 생성 후 평가 기준·가중치 변경

**우회 시도** (주입 기능 불필요, 호출 방식으로 구성)

- 동의 전 제출·분석·녹화 직접 호출
- stale 정책 버전·해시로 동의 제출
- 비인가 주체의 최종결정 요청
- 리포트 없이 일반 채용 단계 이동 시도
- 잘못된 `quoted_evidence_ids` 입력

**복구**

- 모든 주입은 해제 후 장애 전 기준선으로 복원하고, 복원 일치를 확인한 뒤 다음 단계로 진행한다.

장애 주입 기능은 합성 데이터와 테스트 계정에만 적용하며 운영 환경에서는 사용할 수 없어야 한다.

## 8. ControlProof에서 만들어야 할 기능

### 8.1 검증 워크벤치

- 검증 대상과 서비스 버전
- 적용 정책·평가기준 버전
- 통제 4종과 시나리오 12개
- 시나리오별 현재 준비 상태
- 기존 기능 활용·보완·신규 구현·미실행 구분
- 통과·실패·판정 불가·미실행 수
- 최근 실행과 재시험 결과
- 보고서 진입

### 8.2 시나리오 카탈로그

각 시나리오에 다음 정보가 있어야 한다.

- 통제와 시나리오 ID
- 시험 목적
- WhyYou 현재 준비 상태
- 필요한 신규 개발
- 실행 방식과 전제조건
- 입력 데이터와 주입 조건
- 기대 결과와 필수 증적
- 판정 기준과 현재 실행 상태

### 8.3 실행 제어

- 합성 지원자와 테스트 사용자를 선택한다.
- 정상·장애·누락 조건을 선택한다.
- 고유 시험 실행 ID를 발급한다.
- WhyYou 실행 전 상태를 기록한다.
- 브라우저·API·로그 실행 단계를 안내한다.
- 진행 중·완료·실패 상태를 표시한다.
- 같은 초기 조건으로 재실행한다.

### 8.4 증적 수집 및 정규화

화면 캡처, 요청·응답, 감사·아웃박스 이벤트, 상태 변경, 동의, 리포트, HumanReview, 적용 버전과 오류를 하나의 증적 묶음으로 만든다. A-01~A-03에는 실행 증적 대신 대상 기능 부재를 확인한 저장소·화면 조사 자료를 연결한다. 원본 기록은 보존하고 비개발자도 이해할 수 있는 설명을 함께 표시한다.

### 8.5 판정

- `PASS`: 기대 결과와 필수 증적이 모두 확인됨
- `FAIL`: 실제 동작이 기대 결과와 다르거나 필수 통제가 작동하지 않음
- `판정 불가`: 대상 기능 부재, 접근 제한, 증적 누락 또는 충돌로 결론을 낼 수 없음
- `미실행`: 정의는 되어 있으나 아직 실제 실행하지 않음

근거가 부족한 항목을 `PASS`로 처리하지 않는다. 화면이 정상처럼 보여도 필수 증적이 누락되면 통과시키지 않으며, AI의 비정형 설명만으로 통과를 확정하지 않는다.

`판정 불가`에는 반드시 다음과 같은 사유 코드를 함께 표시한다.

- `NO_TEST_TARGET`: 대상 기능이나 처리 경로가 존재하지 않음
- `INSUFFICIENT_EVIDENCE`: 판정에 필요한 증적이 부족함
- `ACCESS_LIMITED`: 필요한 화면·로그·데이터에 접근할 수 없음
- `EVIDENCE_CONFLICT`: 서로 다른 증적이 충돌함

### 8.6 실패 설명과 재시험

실패 결과에는 실패 항목, 기대 상태, 실제 상태, 누락·충돌 증적, 예상 영향, 수정 대상과 재시험 대상을 표시한다. 재시험은 최초 실행을 덮어쓰지 않는다.

### 8.7 결과 보고서

- 검증 대상과 버전
- 검증 목적과 범위
- 합성 데이터 사용 표시
- 통제 4종과 시나리오 12개 상태
- 통과·실패·판정 불가·미실행 요약
- 시나리오별 기대 결과와 관찰 결과
- 주요 실패와 영향
- 증적 목록과 누락 여부
- 적용 정책·모델·프롬프트·평가기준 버전
- 최초 실행과 재시험 비교
- WhyYou에 시험 목적으로 추가한 기능
- 검증하지 못한 영역
- 법적 준수 전체를 보증하지 않는다는 한계

2주 MVP에서는 화면 보고서를 우선한다. PDF 내보내기는 핵심 흐름이 끝난 뒤 추가한다.

| 이용자 보호 및 이의처리 | A-01 | 이의제기 진입 경로와 접수 확인 | 대상 없음 | 대상 확인 | `판정 불가: NO_TEST_TARGET` |
| 이용자 보호 및 이의처리 | A-02 | 이의 접수 후 후속 확정 처리 보류 | 대상 없음 | 대상 확인 | `판정 불가: NO_TEST_TARGET` |
| 이용자 보호 및 이의처리 | A-03 | 접수 → 독립 재검토 → 결과 통지 완주 | 대상 없음 | 대상 확인 | `판정 불가: NO_TEST_TARGET` |
| 증적 기록의 완전성 | E-01 | 인용 근거 없는 점수가 저장·노출되는가, 근거가 사라진 뒤에도 노출되는가 | 대상 존재 | 우회+변경 주입+API+로그 | 인용 검증 우회와 Evidence 제거 |
| 증적 기록의 완전성 | E-02 | 점수 입력과 가중치가 동결되고 기준 변경 후 과거 리포트가 유지되는가 | 대상 존재 | API+DB+로그 | `scoring_inputs`와 저장 가중치 검증 |
| 증적 기록의 완전성 | E-03 | 워커 장애·재시도·DLQ에서 Outbox와 상태·결정·처리 이력이 보존되는가 | 대상 존재 | 장애 주입+로그 | 이벤트 유실·중복 검증 |

## 10. 시나리오 상세 설명

### 10.1 N-01. 동의 화면의 필수 고지 항목 표시 — PC·모바일

**목적**

지원자가 자료를 제출하고 AI 처리가 시작되기 전에 현재 WhyYou가 실제로 수행하는 AI 평가 보조, 사람의 최종 결정, 녹화와 개인정보 처리 내용을 읽을 수 있는 형태로 확인했는지 검증한다.

**현재 상태**

AI 평가 보조, 사람의 최종 결정, 녹화·처리 목적, 보관기간과 삭제 방법은 동의 정책으로 제공된다. 이의제기 기능은 존재하지 않으므로 이번 MVP에서 이의제기 가능 문구를 추가하지 않는다.

**실행**

- PC와 390px 수준 모바일 화면으로 동의 단계에 진입한다.
- AI 사용, 사람의 최종 결정, 녹화·처리 목적, 보관기간과 삭제 방법이 모두 표시되는지 확인한다.
- 문구가 잘리거나 버튼·팝업에 가려지지 않는지 확인한다.
- 화면의 정책과 실제 저장된 동의 정책 버전을 연결한다.

**기대 결과와 증적**

필수 고지 항목이 제출과 분석 시작 전에 확인돼야 한다. PC·모바일 캡처, 정책 버전·내용 해시, 동의 완료 시각과 지원자 ID를 남긴다.

**실패 의미**

지원자가 AI 평가·녹화·인간 결정 원칙을 모른 채 참여하거나 화면 문구와 실제 동의 기록이 다른 정책을 가리킬 수 있다.

### 10.2 N-02. 동의 완료 전 분석·녹화·평가가 시작되지 않는가

**조건 주입**: 우회 시도 + 장애 주입

**목적**

문서와 화면이 주장하는 대로 실제 처리 순서가 동의 → 제출 → 분석·녹화·평가 순서로 지켜지는지 확인한다. 나아가 동의 기록 자체가 저장되지 않은 상황에서도 후속 처리가 차단되는지 확인한다.

**실행**

- 합성 지원자가 본인 확인까지만 완료한 상태에서 자료 제출, 분석 요청, 녹화·평가 시작을 각각 직접 호출한다. (우회)
- 동의를 정상 완료한 뒤 `동의 완료 < 분석 요청 ≤ 분석 시작` 순서가 성립하는지 확인한다.
- 동의 기록 저장 트랜잭션을 실패시킨 뒤 지원자가 다음 단계로 진행을 시도한다. (장애)
- 화면상 동의를 마쳤지만 서버에 동의 기록이 없는 상태에서 제출·분석이 시작되는지 확인한다.
- 동의 완료 이벤트의 아웃박스 디스패치를 지연시킨 상태에서 분석 요청을 보내 처리가 시작되는지 확인한다. (장애)
- 장애를 복구한 뒤 같은 지원자가 정상 흐름을 완주할 수 있는지 확인한다.

**기대 결과와 증적**

동의 기록이 없는 상태에서는 제출·분석·녹화·평가가 모두 거부돼야 한다. 화면 진행 상태가 아니라 저장된 동의 기록이 처리의 기준이어야 한다. 정상 흐름에서는 세 사건의 순서가 성립한다. 동의 기록 유무, 각 시도의 응답 코드, 사건별 발생 시각, 분석 상태 전이, 장애 주입·복구 기록을 동일한 시험 실행 ID로 연결한다.

**실패 의미**

화면상 고지는 있지만 실제 분석·녹화·평가가 먼저 시작되거나, 동의 저장이 실패했는데도 화면 진행만으로 AI 처리가 진행돼 동의 없는 처리가 발생할 수 있다.

### 10.3 N-03. 정책 교체 구간에서 어떤 버전에 동의한 것으로 기록되는가

**조건 주입**: 데이터 변경 주입 + 우회 시도

**목적**

지원자가 읽은 정책과 서버에 기록된 동의 정책이 일치하는지, 정책이 교체되는 구간에서도 그 일치가 유지되는지 확인한다. 단순히 낡은 버전이 거부되는지가 아니라, 교체 타이밍에 걸친 요청이 어느 버전으로 귀속되는지를 본다.

**실행**

- 합성 지원자가 동의 화면을 열어 현재 `policy_version`과 `content_digest`를 읽는다.
- 동의를 제출하기 전에 서버의 정책 문구와 버전·해시를 새 버전으로 교체한다. (변경 주입)
- 화면에 남아 있는 이전 버전·해시로 동의를 제출한다. (우회)
- 서버가 stale 동의를 거부하고 최신 정책 재확인을 요구하는지 확인한다.
- 정책 교체와 동의 제출을 근접한 시점에 함께 실행해, 저장된 동의 기록의 버전·해시가 지원자가 실제로 읽은 화면과 일치하는지 확인한다.
- 교체 직후 시작된 분석 작업이 어느 정책 버전에 귀속돼 기록되는지 확인한다.
- 최신 정책을 다시 읽고 제출한 동의가 정상 저장되는지, 이미 완료된 과거 동의는 영향받지 않는지 확인한다.

**기대 결과와 증적**

이전 정책 정보로 제출한 동의는 거부되고, 저장된 동의 기록의 버전·해시는 지원자가 실제로 확인한 화면과 일치해야 한다. 교체 전후 버전·해시, 화면에 표시된 값, 거부 응답, 최종 저장된 동의 기록, 분석 작업에 기록된 정책 버전, 과거 동의 기록의 불변 여부를 남긴다.

**실패 의미**

지원자가 읽지 않은 정책에 동의한 것으로 기록되거나, 교체 구간의 요청이 임의의 버전으로 귀속돼 "이 지원자는 어떤 내용에 동의했는가"를 설명할 수 없게 된다. 이미 정상 완료된 과거 동의 전체가 정책 변경만으로 자동 무효화된다는 의미는 아니다.

### 10.4 H-01. `COMPANY_USER`가 아닌 주체의 최종결정 거부

**목적**

최종 채용 결정을 기록할 수 있는 주체가 사람인 회사 사용자로 제한되고, AI 어시스턴트·워커·지원자 또는 인증되지 않은 호출이 같은 명령을 실행할 수 없는지 확인한다.

**실행**

- 검토 가능한 리포트가 준비된 합성 지원자를 만든다.
- 정상 `COMPANY_USER` 권한으로 최종결정을 기록해 허용되는 기준 동작을 확인한다.
- 같은 최종결정 요청을 AI 어시스턴트, 워커·`SYSTEM`, 지원자와 인증 정보가 없는 주체로 각각 시도한다.
- 각 거부 응답과 감사 기록에 요청 주체, 시각, 대상 지원자와 실패 사유가 남는지 확인한다.
- 거부된 호출이 HumanReview, 최종결정 또는 채용 단계의 일부도 변경하지 않았는지 확인한다.

**기대 결과와 증적**

정상 회사 사용자의 결정만 허용되고 나머지 주체의 시도는 상태 변화 없이 거부돼야 한다. 주체별 요청·응답, 권한 정보, 변경 전후 상태, HumanReview와 감사 기록을 남긴다. 회사 사용자가 정상 API를 직접 호출하는 것은 허용된 사용이므로 우회로 판정하지 않는다.

**실패 의미**

사람만 내려야 할 채용 결정을 AI나 백그라운드 프로세스가 확정하거나, 거부된 요청이 일부 상태를 변경할 수 있다.

### 10.5 H-02. AI 어시스턴트·워커의 쓰기 권한 표면 검사

**조건 주입**: 없음 (정적 검사)

**목적**

최종 채용 상태를 바꿀 수 있는 명령이 AI 어시스턴트의 도구 목록과 워커의 처리 계약에 **애초에 노출되어 있지 않은지** 확인한다.

H-01과 겹치지 않는 이유 — H-01은 호출했을 때 거부되는지를 본다(문이 잠겼는가). H-02는 그 명령이 기능 표면에 존재하는지를 본다(문이 아예 없는가). 거부되더라도 명령이 목록에 있으면 권한 설정이 한 번 느슨해지는 순간 뚫린다. 외부 도구 연동이 늘어날수록 이 차이가 커진다.

**실행**

- AI 어시스턴트가 사용하는 도구 계약을 열거하고 최종결정·채용 단계 변경·상태 쓰기 명령이 포함됐는지 검사한다.
- 워커의 처리 계약과 구독 이벤트 목록에 같은 종류의 쓰기 명령이 있는지 검사한다.
- 조회·검색·보조 목적의 도구만 노출됐는지 확인한다.
- 노출된 도구가 있다면 그 도구가 실제로 어떤 상태를 바꿀 수 있는지까지 확인한다.

**기대 결과와 증적**

AI 어시스턴트와 워커의 기능 표면에는 조회·보조 도구만 존재하고, 채용 상태를 변경하는 명령이 노출되지 않아야 한다. 도구·이벤트 계약 전체 목록, 각 항목의 읽기·쓰기 구분, 검사 시점의 대상 커밋을 남긴다.

**실패 의미**

AI에게 쓰기 권한이 숨어 있으면 사람 개입 원칙이 형식에 그친다. 지금은 권한 검사로 막히더라도, 그 검사 한 줄이 사라지는 변경만으로 AI가 채용 결과를 확정할 수 있는 상태가 된다.

### 10.6 H-03. Reporting 장애 시 실패 노출·결정 차단·DLQ 보존

**목적**

리포트 생성 큐가 실패하거나 메시지가 DLQ로 이동했을 때 실패가 담당자에게 드러나고, 리포트 없이 채용 결정을 확정할 수 없으며, 실패 건이 조용히 사라지지 않는지 확인한다.

**실행**

- 면접 분석은 완료됐지만 최종 리포트는 아직 없는 합성 지원자를 만든다.
- reporting 큐 또는 워커를 중단해 리포트 생성을 실패시키고 재시도 한도를 소진시킨다.
- 담당자 화면과 리포트 조회 API가 `리포트 없음·생성 중·실패`를 구분해 보여주는지 확인한다. 단순히 계속 `queued`로만 보이는 경우도 실패 은폐로 기록한다.
- 정상 최종결정 API로 결정을 시도해 리포트 부재 때문에 거부되는지 확인한다.
- 칸반·일괄 이동 등 일반 채용 단계 변경 경로로 확정 단계를 시도해 같은 보호 규칙을 우회할 수 없는지 확인한다.
- 애플리케이션의 `JobStatus.DLQ`와 메시지 인프라의 SQS DLQ를 구분해, 실패 건과 원인이 어느 쪽에 어떻게 남는지 확인한다.
- 장애를 복구해 메시지를 재처리하고 리포트·결정·이벤트가 한 번만 생성되는지 확인한다.

**기대 결과와 증적**

장애와 리포트 부재가 화면에서 식별되고, 모든 확정 경로가 리포트 없는 결정을 막아야 한다. 실패 메시지나 작업은 DLQ 또는 추적 가능한 실패 상태에 남고, 복구 후 중복 부작용 없이 한 번만 처리돼야 한다. 화면, API 응답, 큐·DLQ, 작업 상태, Outbox, HumanReview와 단계 변경 전후를 증적으로 남긴다.

**실패 의미**

담당자가 리포트 실패를 모른 채 결정하거나 일반 단계 이동으로 보호 규칙을 우회할 수 있고, DLQ 건이 운영자에게 보이지 않거나 재시도에서 중복 리포트·이벤트·결정이 생길 수 있다.

### 10.7 A-01. 이의제기 진입 경로 및 접수 확인 — 판정 불가

**목적**

지원자가 결과 화면이나 통지에서 이의제기 절차에 진입하고 접수 사실을 확인할 수 있는지 확인하는 시나리오다.

**현재 상태**

WhyYou에는 지원자 결과 통지와 이의제기 접수 경로가 없다. 이번 MVP에서는 신규 구현하지 않는다.

**실행**

- 저장소와 실행 화면에서 결과 통지, 이의제기 링크·폼·API와 접수 확인 기능의 존재 여부만 확인한다.
- 대상 기능이 없다는 확인 자료를 시나리오 증적으로 연결한다.

**판정**

`판정 불가: NO_TEST_TARGET`. 기능 부재는 통제의 통과나 실패가 아니라 시험할 대상이 없다는 뜻이다.

**향후 활성화 조건**

결과 통지와 실제 이의 접수·확인 경로가 구현되면 동일한 정의로 실행한다.

### 10.8 A-02. 이의 접수 후 후속 확정 처리 보류 — 판정 불가

**목적**

재검토가 끝나기 전까지 원 결정을 확정적으로 집행하는 후속 처리가 보류되는지 확인한다.

**현재 상태**

이의제기를 접수할 대상과 이의 처리 상태가 없으므로 보류 규칙을 실행할 수 없다. 이번 MVP에서는 신규 구현하지 않는다.

**실행**

- 저장소와 상태 모델에서 이의 접수 상태, 원 결정 집행 보류 규칙과 관련 명령의 존재 여부만 확인한다.
- 대상 기능이 없다는 확인 자료를 시나리오 증적으로 연결한다.

**판정**

`판정 불가: NO_TEST_TARGET`. 접수 기능이 없는 상태에서 가상의 보류 흐름을 만들어 통과로 표시하지 않는다.

**향후 활성화 조건**

이의 접수 상태와 후속 처리 보류 규칙이 구현되면 접수 전후 상태 및 차단 응답을 시험한다.

### 10.9 A-03. 접수 → 독립 재검토 → 결과 통지 완주 — 판정 불가

**목적**

이의제기 후 담당자 배정, 독립적인 사람의 재검토, 결과 통지까지 정해진 기한 안에 완료되는지 확인한다.

**현재 상태**

접수, 재검토자 배정, 독립 재검토와 결과 통지 기능이 모두 없다. 이번 MVP에서는 신규 구현하지 않는다.

**실행**

- 저장소와 실행 화면에서 접수·배정·재검토·통지 상태와 처리기한 기능의 존재 여부만 확인한다.
- 대상 기능이 없다는 확인 자료를 시나리오 증적으로 연결한다.

**판정**

`판정 불가: NO_TEST_TARGET`. A-01과 A-02를 포함한 선행 경로가 없으므로 종단 간 완주를 시험할 수 없다.

**향후 활성화 조건**

접수부터 결과 통지까지의 전체 기능이 구현되면 최초 결정자와 다른 재검토자, 처리기한과 단계별 증적을 포함해 실행한다.

### 10.10 E-01. 유효한 인용 근거 없는 점수 저장·노출 차단

**조건 주입**: 데이터 변경 주입 + 우회 시도

**목적**

AI가 산출한 점수가 실제 답변 근거와 연결되지 않은 채 저장되거나 리포트에 노출되지 않는지 확인한다. 저장 시점의 검증뿐 아니라, 저장 이후 근거가 사라진 경우까지 본다.

**실행**

- 기준별 점수에 `quoted_evidence_ids`를 비운 요청을 저장 경로에 보낸다. (우회)
- 존재하지 않는 Evidence ID, 다른 지원자의 Evidence ID, 다른 평가 기준의 Evidence ID를 각각 연결해 저장을 시도한다. (우회)
- AI 응답 검증 경로에도 같은 잘못된 인용을 넣어 점수와 인용이 어떻게 정규화되는지 확인한다.
- 유효한 동일 지원자·동일 기준 Evidence를 넣은 기준 사례가 정상 저장되는지 확인한다.
- 정상 저장된 뒤 그 점수가 인용한 Evidence와 연결된 자막 구간을 제거한다. (변경 주입)
- 근거가 사라진 점수가 리포트 조회에서 여전히 정상 점수처럼 노출되는지, 재생 불가능한 인용이 그대로 표시되는지 확인한다.
- 제거한 근거를 복원한 뒤 같은 조회 결과가 원래대로 돌아오는지 확인한다.

**기대 결과와 증적**

인용이 비어 있거나 유효하지 않은 점수는 저장 경로에서 거부되거나 검증 과정에서 `null` 처리되고 인용도 제거돼야 한다. 저장 이후 근거가 사라진 경우에도 그 점수를 정상 점수로 노출하지 않고 근거 부족 상태로 드러내야 한다. 입력 payload, 검증 결과, 저장 레코드, 제거 전후 리포트 조회 결과, 연결된 Evidence의 지원자·기준 ID를 남긴다.

**실패 의미**

근거가 없거나 다른 지원자의 근거를 참조한 점수가 정상 점수처럼 표시돼 평가 결과를 설명할 수 없다. 특히 근거가 사라진 뒤에도 점수만 남으면, 담당자는 확인할 수 없는 숫자를 신뢰하게 되고 지원자에게 이유를 설명할 수 없다.

### 10.11 E-02. 점수 입력·가중치 동결 및 과거 리포트 보존

**목적**

리포트가 생성 당시의 점수 입력과 계산 조건을 자체 기록하고, 이후 평가 기준이나 가중치를 바꿔도 과거 리포트가 새 기준으로 조용히 바뀌지 않는지 검증한다.

**실행**

- 첫 지원자를 기존 평가 기준으로 처리하고 `scoring_inputs`, 기준별 `criterion_weight`, 축별 `axis_weights`, `competency_model_version_id`와 리포트·모델·프롬프트·설정 버전을 수집한다.
- 평가 기준의 점수 또는 가중치와 관련 버전을 변경한다.
- 두 번째 지원자를 처리한다.
- 첫 지원자의 리포트를 다시 조회하고 최초 결과·입력·가중치·버전이 그대로인지 확인한다.
- 같은 저장 입력으로 총점을 재계산해 리포트에 저장된 결과와 일치하는지 확인한다.

**기대 결과와 증적**

과거 리포트는 생성 당시의 점수 입력, 기준별·축별 가중치와 관련 버전을 보존해야 한다. `scoring_inputs`만 존재하고 실제 계산 가중치가 없으면 동결이 완전하다고 판정하지 않는다. 변경 전후 설정, 두 지원자의 리포트와 재계산 결과를 남긴다.

**실패 의미**

현재 설정만으로 과거 결과를 해석하게 되거나 기준 변경이 과거 점수와 리포트를 덮어써 당시 평가를 재현할 수 없게 된다.

### 10.12 E-03. 워커 장애·재시도·DLQ의 Outbox와 상태·결정 이력 보존

**목적**

워커 처리 도중 오류가 발생하고 재시도 또는 DLQ 전환이 일어나도 업무 사건, 상태 전이, 사람의 결정과 처리 시도 이력이 사라지거나 중복되지 않는지 확인한다.

**확인할 증적**

1. 시험 실행 ID
2. 지원자 또는 처리 건 ID
3. 원 업무 사건과 Outbox 이벤트 ID
4. 워커별 처리 시도 횟수와 발생 시각
5. 장애 전후 작업·지원자·리포트 상태
6. 오류 종류와 재시도 또는 DLQ 전환 원인
7. 애플리케이션 `JobStatus.DLQ`와 SQS DLQ의 식별 정보
8. 복구 후 생성된 리포트·상태 변경·사람의 결정 이력·후속 Outbox 이벤트

8종은 한 로그 행에 모두 존재할 필요는 없다. Outbox, 큐 메시지, 작업 상태, 감사·워커 로그와 리포트를 연결해 하나의 처리 이력으로 재구성할 수 있어야 한다.

**실행**

- reporting 워커가 메시지를 받은 뒤 리포트를 저장하기 전과 저장한 직후 각각 오류를 발생시킨다.
- 재시도 횟수와 각 시도의 작업 상태·오류·Outbox 기록을 수집한다.
- 재시도 한도를 소진해 애플리케이션 실패 상태 또는 SQS DLQ로 이동시키고 원 메시지와 연결되는지 확인한다.
- 장애를 복구하고 같은 메시지를 재처리한다.
- 최종 리포트, 상태 전이와 후속 이벤트가 누락 없이 한 번만 반영됐는지 확인한다.
- 복구 후 회사 사용자가 결정을 기록하고 HumanReview·최종결정 이력과 관련 이벤트가 한 번만 남는지 확인한다.
- ControlProof가 누락이나 중복을 발견하면 해당 항목과 원본을 표시하는지 확인한다.

**기대 결과와 증적**

장애 발생부터 재시도·DLQ·복구까지 원 사건과 모든 처리 시도를 연결할 수 있고, 업무 결과·사람의 결정 이력·후속 이벤트는 정확히 한 번의 효과만 가져야 한다. 필수 연결 정보가 없거나 중복 효과가 있으면 `FAIL`, 접근 가능한 증적이 부족하면 사유 코드와 함께 `판정 불가`로 처리한다.

**실패 의미**

실패 메시지가 조용히 사라지거나 리포트는 저장됐지만 완료 이벤트가 없을 수 있고, 재시도에서 같은 리포트·상태 변경·이벤트가 중복 생성될 수 있다.

## 12. 2주 MVP 완료 기준

### 12.1 반드시 완료해야 하는 기반

- [ ] 상태 시드로 검토 대기 지원자를, 경로 시드로 동의를 거친 지원자를 각각 반복 생성할 수 있다.
- [ ] 실제 클라우드 AI 호출 없이 재현 가능한 고정 AI 결과를 만들 수 있다.
- [ ] 각 실행에 고유한 시험 실행 ID가 부여된다.
- [ ] 시험 실행 ID로 WhyYou의 주요 기록을 연결할 수 있다.
- [ ] reporting 장애, 잘못된 인용과 기준 변경 조건을 만들고 정상 상태로 복구할 수 있다.
- [ ] 최초 실행과 재시험 결과가 모두 보존된다.
- [ ] 실제 개인정보 없이 전체 데모가 가능하다.

### 12.2 반드시 실제 완주할 대표 시나리오

2주 MVP의 비협상 완료선은 대상 기능이 실제로 존재하는 다음 3개 대표 시나리오를 시스템에서 끝까지 완주하는 것이다.

- [ ] N-02: 동의 후 AI 처리 시작 순서 확인
- [ ] H-03: reporting 장애 시 실패 노출·결정 차단·DLQ 보존
- [ ] E-03: 워커 장애·재시도·DLQ의 Outbox와 상태·결정 이력 보존

A-01~A-03은 실제 완주 대상이 아니다. 세 항목 모두 대상 기능 부재를 확인한 증적과 함께 `판정 불가: NO_TEST_TARGET`로 보고하는 것이 이번 MVP의 완료 조건이다.

### 12.3 12개 시나리오 관리 기준

- [ ] 통제 4종과 시나리오 12개가 워크벤치에 표시된다.
- [ ] 각 시나리오에 현재 준비 상태와 실행 방식이 표시된다.
- [ ] 실행한 시나리오는 기대 결과·관찰 결과·판정·증적을 가진다.
- [ ] 실행하지 않은 시나리오는 `미실행`으로 표시된다.
- [ ] 증적 부족, 접근 제한, 증적 충돌 또는 대상 기능 부재는 구분된 사유 코드와 함께 `판정 불가`로 표시된다.
- [ ] 대상 기능이 존재하는 9개 시나리오의 전체 실제 실행은 목표 상한으로 두되 미실행 항목을 통과로 포장하지 않는다.

### 12.4 결과물 완료 기준

- [ ] 판정이 `PASS`, `FAIL`, `판정 불가`, `미실행`으로 구분된다.
- [ ] 각 판정의 원본 증적을 확인할 수 있다.
- [ ] AI 점수가 자동 합격·탈락 기준처럼 표현되지 않는다.
- [ ] 사람의 최종결정과 판단 사유를 확인할 수 있다.
- [ ] 실패 → 수정 → 재시험 흐름을 확인할 수 있다.
- [ ] A-01~A-03이 `NO_TEST_TARGET`로 표시되고 신규 구현된 것처럼 보이지 않는다.
- [ ] 전체 결과를 하나의 화면 보고서에서 확인할 수 있다.
- [ ] 검증 범위와 미검증 범위가 구분된다.
- [ ] 법적 준수 전체를 보증하지 않는다는 한계가 표시된다.

- WhyYou 기록 수집
- 초기화와 재시험

### 2순위: 인간 결정·Reporting 안전성의 최초 시험과 수정

- 비회사 주체의 최종결정 거부 확인
- AI 어시스턴트·워커의 변경 권한 부재 확인
- reporting 장애, 일반 단계 이동 우회와 DLQ 보존 시험
- 최초 `FAIL` 보존 후 발견된 문제만 수정하고 `PASS` 재시험

### 3순위: 고지와 실제 처리 순서

- 현재 고지 문구의 PC·모바일 표시 확인
- 동의 전 분석·녹화·평가 차단 확인
- 정책 버전·내용 해시 변경 중 stale 동의 제출 거부
- PC·모바일 확인
- 동의·제출·분석 이벤트 연결

### 4순위: 점수 근거와 계산 조건 보존

- 잘못된 `quoted_evidence_ids` 우회 시도
- 지원자·평가 기준 간 Evidence 연결 검증
- `scoring_inputs`, 기준별·축별 가중치와 관련 버전 보존
- 기준 변경 후 과거 리포트 불변 확인

### 5순위: ControlProof 화면과 보고서

- 워크벤치와 시나리오 상세
- 증적 묶음과 판정
- 최초 실행과 재시험 비교
- 최종 보고서

UI 완성도를 먼저 높이기보다 실제 실행과 증적 연결을 우선한다.

## 14. 반드시 시연해야 할 대표 흐름

### 14.1 N-02 동의와 처리 순서 데모

1. 동의하지 않은 합성 지원자로 자료 제출, 분석, 녹화와 평가 시작을 각각 시도한다.
2. 모든 시도가 거부되고 처리 상태가 변하지 않는지 확인한다.
3. 현재 정책에 동의한 뒤 정상 흐름을 진행한다.
4. `동의 완료 < 분석 요청 ≤ 분석 시작` 순서와 정책 버전·내용 해시를 확인한다.
5. 화면·API·이벤트·로그를 하나의 시험 실행 ID로 보여준다.

### 14.2 H-03 + E-03 FAIL → 수정 → PASS 데모

1. 합성 지원자의 면접 분석을 완료하고 reporting 큐 또는 워커를 중단한다.
2. 리포트 생성 재시도를 실패시켜 애플리케이션 실패 상태 또는 SQS DLQ로 이동시킨다.
3. 담당자 화면에서 리포트 실패가 드러나는지 확인한다.
4. 정상 최종결정 API와 일반 단계 이동 경로로 결정을 시도한다.
5. 현재 동작에서 발견된 실패를 `FAIL`과 원본 증적으로 보존한다.
6. 실패 은폐, 우회 또는 이력 누락 원인만 수정한다.
7. 같은 초기 조건과 장애로 재시험해 결정 차단과 DLQ·Outbox·처리 이력 보존을 확인한다.
8. 장애 복구 후 리포트와 후속 이벤트가 중복 없이 한 번만 생성되는지 확인한다.
9. 사람이 실제 답변과 AI 결과를 함께 검토해 점수가 더 낮은 지원자를 채용하는 결정을 기록한다.
10. 최초 `FAIL`과 재시험 `PASS`를 나란히 비교한다.

### 14.3 E-01 + E-02 근거 무결성 데모

1. 비어 있거나 다른 지원자·기준에 속한 `quoted_evidence_ids`로 점수 저장을 시도한다.
2. 점수가 거부되거나 무효화되고 최종 리포트에 노출되지 않는지 확인한다.
3. 유효한 인용으로 첫 리포트를 만든 뒤 점수 입력, 기준별·축별 가중치와 관련 버전을 확인한다.
4. 평가 기준과 가중치를 변경해 두 번째 리포트를 만든다.
5. 첫 리포트가 생성 당시 값으로 유지되고 저장 입력만으로 계산을 재현할 수 있는지 보여준다.

### 14.4 A-01~A-03 대상 부재 공개 데모

1. 결과 통지, 이의 접수, 처리 보류, 재검토자 배정과 결과 통지 기능이 없다는 조사 증적을 연다.
2. A-01~A-03이 `PASS`, `FAIL` 또는 `미실행`이 아닌 `판정 불가`로 표시되는지 확인한다.
3. 세 항목의 사유 코드가 모두 `NO_TEST_TARGET`인지 확인한다.
4. 이의제기 기능과 안내 문구를 이번 MVP에서 새로 만들지 않았음을 범위 제한으로 보여준다.

## 16. 팀 공통 제품 원칙

### 16.1 근거 없는 통과 금지

대상 기능이 없거나 필수 관찰값·증적을 확보하지 못하면 `PASS`가 아니라 사유 코드가 있는 `판정 불가`로 표시한다.

### 16.2 실제 실행과 화면 연출의 구분

실행하지 않은 시나리오를 실행된 것처럼 표시하지 않는다. 목업, 합성 실행, 실제 WhyYou 실행을 구분한다.

### 16.3 합성 데이터 우선

실제 지원자 개인정보를 기본 검증 데이터로 사용하지 않는다.

### 16.4 인간 결정 원칙

AI 점수는 참고 정보다. 모든 점수대의 지원자는 사람의 검토 대상이며 최종 채용 결정은 사람이 한다.

### 16.5 이전 결과 보존

재시험은 이전 실패 결과를 덮어쓰지 않는다. 실패, 수정, 재시험, 최종 결과를 하나의 이력으로 보존한다.

### 16.6 테스트 기능 격리

장애 주입, 로그 누락, 고정 AI 결과와 같은 기능은 테스트 환경과 합성 데이터에만 적용한다.

### 16.7 검증 한계 표시

절차적 통제 시험의 통과를 법적 준수 전체, 차별 부재 또는 모델 정확성의 보증으로 표현하지 않는다.

### 16.8 비개발자도 이해할 수 있는 결과

개발 로그만 제공하지 않는다. 시험 목적, 조건, 관찰 결과, 판정 근거와 영향이 하나의 흐름으로 읽혀야 한다.

## 17. 최종 범위 선언

> 이번 2주 MVP는 WhyYou 하나를 대상으로 통제 4종과 시나리오 12개를 관리하고, 대상 기능이 존재하는 대표 시나리오 N-02·H-03·E-03을 실제로 완주하며, H 영역의 최초 실패 발견 → 증적 확인 → 수정 → 재시험 → 보고의 한 바퀴를 증명하는 단계다. A-01~A-03은 기능 부재를 숨기지 않고 `판정 불가: NO_TEST_TARGET`로 보고한다.

이번 MVP의 핵심은 12개 항목을 모두 초록색으로 보이게 만드는 것이 아니다. 실제로 실행한 것과 실행하지 못한 것을 구분하고, 실패를 발견했을 때 그 이유와 근거를 설명하며, 수정 후 같은 조건에서 결과가 달라지는 것을 보여주는 것이다.
