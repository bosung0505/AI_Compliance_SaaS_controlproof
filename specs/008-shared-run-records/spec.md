# Spec008: 실제 실행 기록 공동 열람

2026-10-19 사용자 D-029 후속 구현 승인. 기존 `fixes-and-remaining-work` 유지.
목표는 같은 코드와 공유 snapshot을 받은 팀원이 같은 공식 결과·상세 근거·계보를 보는 것이다.

## 요구사항

- FR01: 7개 완료 시나리오·9개 프로필의 최종 원본과 발견한 최초 FAIL·중간/중단 기록을 배포한다. 없는 원본은 ID와 부재를 명시한다.
- FR02: 원본 바이트·시간·판정·source SHA를 유지한다. JSON/JSONL/YAML과 개별 검토한 PNG만 포함하고 비밀값·개인정보·임시 probe를 제외한다.
- FR03: snapshot은 Run/파일 해시·catalog/표시 코드 해시·기존 무결성 상태를 고정한다. 누락·변조·추가 파일·경로 이탈·symlink를 거부한다.
  원래 INVALID인 중단 기록도 그대로 보존하고 동일 INVALID 상태를 확인하며 정상 결과로 승격하지 않는다.
- FR04: `python -m engine.web` 기본 실행은 공유 snapshot을 검증해 연다. `--run-root` 또는 기존 환경 변수는 명시적 로컬 모드로 유지한다.
  `--shared-snapshot`으로 공유 목록을 지정할 수 있으며 다른 root/env와 혼용하지 않는다.
- FR05: 공유 모드는 고정 확인 시각·공유 묶음 ID를 표시하고 PC별 준비 상태/메모를 읽지 않는다. POST 변경은 거부한다.
  보관 기록은 실제 실행 원본이며 공유본 열람을 독립 재실행이나 현재 READY로 표현하지 않는다. DEMO 분리와 기존 디자인 유지.
- FR06: 기존 검증/판독/근거/비교 경로를 재사용한다. 카탈로그와 다른 새 verdict를 만들지 않는다. H02 보완 이력도 그대로 제공한다.
- FR07: WhyYou·Docker·DB·.env·기존 로컬 기록 없이 별도 checkout에서 열람 가능해야 한다. 양쪽 결과 API가 동일해야 한다.
- FR08: 재현 방법·검사 결과·부재·제한을 README/인수인계/범위표/Validation/Traceability에 기록한다.

## Clarify (구현 전 확정)

사용자 승인 범위의 통상 구현 선택: 데이터는 `review-data/bundles`, 목록은 `review-data/snapshot.json`으로 둔다.
공유본은 읽기 전용이다. 새 테스트 준비는 명시적인 기존 로컬 모드에서 한다. 로컬 메모 파일은 조사 결과 0건이다.
N02 과거 중간 원본은 찾지 못한 사실을 유지하며 최종 결과 연결을 막지 않는다. E01/E02 추가 재현 원본은 보관 폴더에서 발견했다.
원래 INVALID인 N02 기록은 해시와 검사 상태를 보존해 공유하며 기존 UI에서 결과를 차단한다.
이 기능 검증은 새로운 WhyYou actual Run을 필요로 하지 않는다. 실제 기록 공동 열람을 검증하며 AWS/모델 품질/독립 PC 실행은 별도다.

## 성공 기준

SC01: 9개 프로필 최종과 발견한 계보가 새 checkout에서 동일한 Run·근거·비교로 연결된다.
SC02: 원본/공유본 모든 파일 해시 일치. 정해진 INVALID 이외 모든 봉인 원본 VERIFIED. 민감정보 검사 0건 또는 명시적 검토 근거.
SC03: 변조·경로 탈출·부재·중복 충돌을 시험으로 검출한다. 공유 POST는 거부하고 PC별 state/env 영향이 없다.
SC04: 두 checkout의 실제 결과/시나리오/비교 API 일치, 공통 화면 1280/1024px 검토와 문서 수렴.

범위 밖: 새 모델/시나리오 실행, WhyYou 제품 수정, 원격 바인딩·인증, main 병합, 누락 원본 생성, Spec005 외부 사용성 완료.
