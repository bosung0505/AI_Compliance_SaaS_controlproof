## 구성

기존 표준 라이브러리 HTTP 서버·Jinja·정적 CSS/JS와 `WorkbenchReader`를 사용한다. 새 의존성·DB는 도입하지 않는다.
새 라우트/표시 투영/PNG 제공은 계약 확정 뒤 후속 단계에서 구현한다. 실행 엔진과 WhyYou는 변경하지 않는다.
원본 디자인의 고정 배열·최근/이전 boolean·innerHTML 조립은 데이터 원천으로 이식하지 않는다.

| 층 | 현재 자산 | 후속 구현 |
| --- | --- | --- |
| 라우트/경계 | `engine/web/server.py` | 신규 읽기 전용 페이지, 명세화한 PNG content 응답, 기존 보안 유지 |
| 데이터 투영 | `readmodel.py`, `review.py`와 시나리오별 review | 기존 필드 유지, 필요하면 별도의 명시적 UI 표시 투영 추가 |
| 화면 | 기존 templates·partials | 팀원 디자인 공통화, 정의/프로필/기록/결과/자료의 단계적 정보 노출 |
| 동작 | static CSS/JS | CSP 준수·반응형·URL query·패널·키보드·인쇄 |
| 저장 | 카탈로그/봉인 자료/로컬 준비·메모 | 원본 읽기 전용, 로컬 상태는 기존 별도 경로 |
| 공유 | `engine/shared_records.py` | 후보 snapshot과 해당 표시 코드의 동시 검증, 원본 불변 |

## 현재 필드와 추가 계약의 구분

`latest_run`은 현재 시간순 실행 중 첫 기록이며 공식 final 의미로 바꾸지 않는다. `result_links`는 5개 제한이 있다.
전체 이력은 `scenario.previous_runs`를 사용하고 공식 대표는 계약의 별도 프로필별 선택 결과로 제공한다.
N-03 `scope_items` 문자열은 이미 있으나 ID·구조·정의 출처의 표시 투영은 명시적 추가로 다룬다.
기존 `controlproof.web.v1`의 의미/오류/enum을 보존하고 추가 필드가 필요하면 계약에 구별해 기록한다.

## PNG와 출력 경계

현재 `_viewability`는 텍스트 전용이며 기존 evidence HTML 주소는 유지한다.
새 binary content는 manifest ref와 선택 root/모드·검토 허용·해시/MIME/signature/크기를 통과한 PNG만 제공한다.
텍스트 redaction을 PNG 바이트에 적용해 원본을 변형하지 않는다. 대신 검토된 해시 허용과 무결성 확인을 읽기 직전에 수행한다.
이는 텍스트 응답의 redaction을 없애는 전역 예외가 아니다. 오류는 기존 마스킹 경계로 응답한다.
정책과 실패 행렬은 [PNG 계약](contracts/png-evidence.md)에 고정한다.

## 공유본과 복구

0·1단계에서는 표시 코드 해시를 유지했다. 2단계부터 표시 코드가 바뀌므로 원래 r2와 현재 코드는 불일치한다.
검증을 우회하지 않고 새 ID·새 로컬 경로의 2단계 후보를 생성하고 명시적으로 지정한다. 기본 r2 파일은 보존한다.
현재는6단계 후보 `stage6-shared-r3`와 새 표시 코드를 함께 사용한다. [실행 방법](stage6-validation.md).
후속 구현의 후보는 새 경로/ID로 생성하고 기존 28건·INVALID·누락·PNG 검토 해시를 보존한다.
과거 snapshot을 현재 코드에 강제로 맞추거나 원본을 재봉인하지 않는다. 복구는 `fb219d0`와 r2의 짝이다.

IV: 카탈로그/시나리오와 어댑터 경계를 유지한다. V: 새 actual/장애 동작이 없다. VI: 모든 과거 원본/계보 불변.
