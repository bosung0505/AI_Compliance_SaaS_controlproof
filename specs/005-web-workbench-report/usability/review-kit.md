# Spec 005 웹 화면 사용성 검토 키트 (T070)

이 문서는 진행자용 키트다. 근거는 FR-034, SC-008, SC-009이고 표본·과업·질문·제한 시간·정답 기준은 `../spec.md`를 따른다.
검토 결과는 이 문서가 아니라 `results.md`에 적는다(T071).

- **대상 화면**: 실제 Run 기록이 들어 있는 로컬 웹 워크벤치(`python -m engine.web --run-root <run root>`, `127.0.0.1:8765`). 목업이 아니다.
- **표본(D-020)**: 한 라운드에 Spec 005를 쓰지 않은 3명. 실행 담당자·검증 책임자·결과 검토자 각 1명. **라운드마다 새 참여자**다 — 앞 라운드에서 화면을 본 사람은 다시 참여하지 않는다(처음 보는 사람이 읽을 수 있는지를 재는 검토이기 때문).
- **합격 기준**: 질문마다 3명 중 2명 이상 3분 안에 정답, 치명적 오독 0건, Q7에 3명 중 2명 이상 세 항목 모두. 불합격이면 화면을 고치고 다음 라운드. 처음 합격한 라운드로 마감한다.
- **진행 방식**: 연우 PC 대면. 웹은 `127.0.0.1`에만 연결하고 Host가 다르면 거부하므로(로컬 보안 경계) 원격으로 열 수 없다. 참여자가 연우 PC 앞에서 **직접 마우스를 쥔다**. 과업이 "화면에서 찾기"라서 진행자나 작성자가 대신 조작하면 측정이 무의미해진다.
- **작성자 비개입**: 연우(Spec 005 작성자)는 웹만 띄워 주고 검토 중에는 자리를 비운다. 옆에 있으면 무의식적 힌트가 나가고 비작성자 표본의 취지가 깨진다.
- **1인당 소요**: 과업 3개 + 질문 7개. 질문은 1개당 3분이므로 질문만 최대 21분, 전체 40분 안쪽으로 잡는다. 한 라운드의 3명을 하루에 몰지 않아도 된다. 봉인 기록은 바뀌지 않으므로 며칠에 나눠 진행해도 같은 조건이다. 다만 라운드 도중에는 화면을 고치지 않는다(한 라운드 안의 3명은 같은 화면을 봐야 한다).
- **기록**: §7 기록 시트. 개인 식별자(이름·사번·연락처)는 적지 않는다. 참여자는 라운드별로 P1~P3으로만 쓴다(예: 라운드 2의 P1).

## 1. 참여자 안내문 (그대로 읽어 준다)

보시는 화면은 AI 면접 서비스의 통제가 실제로 작동하는지 시험한 기록입니다. 시험은 이미 끝났고, 여기서는 그 결과를 읽는 화면만 보시게 됩니다.

세 가지만 기억해 주세요.

1. **화면에 있는 것만 보고 답해 주세요.** 코드나 다른 문서를 찾아보지 않으셔도 됩니다. 모르겠으면 "화면에서 찾을 수 없다"고 말씀해 주시면 됩니다. 그 답도 중요한 결과입니다.
2. **평가받는 건 여러분이 아니라 화면입니다.** 답이 틀리면 화면이 잘못 만들어진 겁니다. 편하게 답해 주세요.
3. **화면에서 누르실 수 있는 건 "준비 상태 확인" 버튼 하나입니다.** 그 버튼은 기록을 바꾸지 않습니다. 눌러도 괜찮지만 누르지 않아도 됩니다. 그 밖에 시험을 다시 돌리거나 기록을 고치는 버튼은 화면에 없습니다.

생각하신 걸 소리 내어 말씀해 주시면 도움이 됩니다. 중간에 제가 설명을 덧붙이지 않는 건 불친절해서가 아니라, 화면만으로 읽히는지 보려는 것입니다.

## 2. 과업 3개

과업에는 제한 시간이 없다(시간 기준은 §3의 질문에만 적용된다). 다만 걸린 시간은 참고로 기록한다.
진행자는 화면 이름만 알려 주고, 어디를 눌러야 하는지는 알려 주지 않는다.

### 과업 1. 12개 시나리오의 상태 읽기

> "첫 화면에 시험 항목 12개가 있습니다. 각각이 지금 어떤 상태인지 읽어 주세요. 같은 상태끼리 묶어서 말씀해 주셔도 됩니다."

- 시작 화면: 워크벤치(`/`)
- 보려는 것: 세 가지 상태를 구분하는지. 특히 "실행하지 않음"과 "대상 기능이 없음"을 통과로 읽지 않는지.

### 과업 2. E-01 최초 실패의 근거 증적 찾기

> "E-01 항목에는 실패한 기록과 그 뒤 다시 시험해서 통과한 기록이 있습니다. 먼저 **실패한** 기록을 열어 주세요. 그 실패 판정이 왜 나왔는지, 무엇을 근거로 그렇게 판정했는지 화면에서 찾아 주세요."

- 시작 화면: 워크벤치 → E-01 시나리오 상세 → 실패한 실행 결과
- 보려는 것: 실패한 규칙 하나를 짚고, 그 규칙에 딸린 증적까지 내려가는지. 개발자용 원본을 한 단계 더 여는 동작을 스스로 찾는지.

### 과업 3. 재시험에서 달라진 점 찾기

> "같은 E-01에서 다시 시험한 기록이 있습니다. 두 기록을 비교하는 화면을 찾아서, 처음 시험과 다시 한 시험 사이에 무엇이 달라졌는지 말씀해 주세요."

- 시작 화면: E-01 시나리오 상세 → 재시험 비교(`/compare/{child}`)
- 보려는 것: 실패했던 규칙이 통과로 바뀐 것과, 시험 대상 버전이 바뀐 것을 짚는지. **그리고 화면 상단 줄을 오독하지 않는지(§5 필수 메모 참고).**

## 3. 질문 7개 (Product Brief §10.3)

질문당 **3분**. 3분을 넘기면 진행자가 끊고 "시간"이라고만 말하고 다음으로 넘어간다. 넘긴 질문은 오답으로 기록한다.
질문은 과업 2·3에서 본 **E-01**을 기준으로 묻는다. 7번만 12개 전체를 묻는다.

1. 무엇을 왜 시험했는가?
2. 어떤 조건을 직접 만들었는가?
3. 실제로 무엇이 일어났는가?
4. 왜 이 판정이 나왔는가?
5. 실패 후 무엇을 수정했는가?
6. 같은 조건의 재시험에서 무엇이 달라졌는가?
7. 무엇은 아직 검증하지 못했는가?

진행자는 질문을 그대로 읽는다. 바꿔 말하거나 선택지를 주지 않는다. 참여자가 되물으면 질문만 한 번 더 읽어 준다.

## 4. 치명적 오독 목록 (SC-008, 0건이어야 함)

하나라도 나오면 그 자리에서 기록하고, §7 시트의 "치명적 오독" 칸에 어떤 말을 했는지 그대로 적는다. 진행자가 즉석에서 바로잡지 않는다(바로잡으면 뒤 질문의 답이 오염된다). 세션이 끝난 뒤에 설명해 준다.

| # | 오독 | 어떤 말이 나오면 해당하는가 |
|---|---|---|
| 1 | `NOT_RUN`을 통과로 읽음 | "이것도 문제 없다", "통과했다", "괜찮은 걸로 나왔다" — 실행하지 않은 4개 항목에 대해 |
| 2 | `NO_TEST_TARGET`을 통과로 읽음 | "문제 없음", "이상 없다" — 대상 기능이 없는 3개 항목에 대해 |
| 3 | `INCONCLUSIVE`를 통과로 읽음 | "통과", "괜찮다" — 판정 불가 항목(N-02)에 대해 |
| 4 | AI 점수를 채용 결정으로 읽음 | "이 점수로 떨어뜨린다/뽑는다", "AI가 불합격 결정했다" |
| 5 | 결과를 법적 인증으로 읽음 | "법적으로 문제없다는 뜻", "규제 통과", "인증받았다", "AI 기본법 준수 확인" |

참고: "잘 모르겠다", "화면에서 못 찾았다"는 오답이지 치명적 오독이 아니다. 둘을 구분해서 기록한다. 영문 때문에 막힌 경우도 오독이 아니다(§5-3의 (가)로 적는다).

## 5. 진행자 메모

### 5-1. 필수 — 재시험 비교 화면 상단 줄 (반드시 읽고 들어간다)

**재시험 비교 화면(`/compare/{child}`) 상단 줄에는 "대상 버전 확인 기록 없음"이 표시된다. 이것은 재시험이 끝나지 않았다는 뜻이 아니다.**

- 상단 줄의 "대상 버전 확인"은 **가장 최근 준비 상태 확인 기록**의 대상을 가리킨다. 재시험의 완료 여부와는 무관하다.
- 보고서 화면에서는 같은 줄이 "대상 버전 WhyYou commit `374b122`"로 나온다. 두 화면의 표시가 다른 것은 각 화면이 상단 줄에 넘기는 값이 다르기 때문이고, 판정이나 기록의 문제가 아니다.
- 비교 화면 **본문**에는 부모 `ce8d862`, 재시험 `374b122`가 맞게 나온다. 참여자에게 대상 버전을 물을 일이 있으면 본문 값이 기준이다.
- **진행자가 할 일**: 참여자가 상단 줄을 보고 "재시험이 확인되지 않았다", "아직 안 끝났다", "검증 안 된 것 같다"는 식으로 읽으면 **그 말을 그대로 §7 시트에 적는다.** 이것이 T071에서 확인하려는 핵심 위험 하나다. 그 자리에서 설명해 주지 않는다.
- 참여자가 상단 줄을 아예 언급하지 않았으면 그것도 "언급 없음"으로 적는다. 유도 질문을 하지 않는다.

이 표시는 Phase 9에서 발견했고 원인까지 확인했다. 화면 수정은 T072 판정 뒤로 미뤄 둔 상태다(실제 오독이 나오면 새 작업으로 만든다).

### 5-2. 참고 — "원본 값"이 비어 보이는 화면

H-03의 A1~A6, E-03의 규칙 일부는 봉인 기록 자체에 기대값·실제값이 들어 있지 않다. 그래서 화면의 "원본 값"도 비어 보인다. 웹이 봉인 기록을 그대로 보여 준 것이고 결함이 아니다. 참여자가 "값이 안 나온다"고 하면 기록만 하고 넘어간다.

### 5-3. 참고 — 규칙 표의 "기대" 열이 영문이다

"규칙별 결과" 표의 **기대** 열과 "원본 값" 안의 `detail`은 영문이다. 시나리오 정의 원천(`scenarios/E-01.yaml`)의 문장을 **그대로** 보여 주기 때문이고, 한국어로 바꾸면 "정의 원천을 그대로 보여야 한다"는 요구사항(FR-008)을 어기게 된다. 결함이 아니다.

- 실패 내용을 한국어로 읽을 수 있는 곳은 "비개발자용 설명" 카드의 **예상 영향**과 **판정 사유**다(정답 키 과업 2의 경로 ㄱ).
- **진행자가 할 일**: 참여자가 과업 2나 Q3·Q4에서 막혔을 때, 그 이유를 둘로 나눠 적는다.
  - (가) 영문을 읽지 못해서 막혔다 — "영어라 모르겠다", 영문을 한참 들여다보다 포기
  - (나) 화면에서 어디를 봐야 할지 못 찾았다 — 비개발자용 설명 카드 자체를 지나쳤다
  (가)와 (나)는 고칠 곳이 다르다. (가)가 여러 건이면 정의 원천의 번역·병기 여부를 따로 논의해야 하고, (나)는 화면 구조 문제다.
- 번역해 주거나 영문을 읽어 주지 않는다. 막힌 것 자체가 결과다.

### 5-4. 참고 — 무결성 실패로 표시되는 기록 1건

run root에 있는 기록 중 하나(`e2e8e71d`)는 봉인한 뒤 내용이 바뀌어서 웹과 CLI 모두 무결성 실패(INVALID)로 표시한다. 의도된 상태다. 참여자가 열어도 문제 없다.

### 5-5. 참고 — 준비 상태 열의 현재 표시와 "준비 상태 확인" 버튼

검토 중에는 대상 서비스(WhyYou·Docker)를 켜 두지 않는다. 과업과 질문에 준비 상태 확인 결과가 필요하지 않기 때문이다. 그래서 준비 상태 열이 네 가지로 보인다.

| 표시 | 해당 시나리오 | 뜻 |
|---|---|---|
| `RUNNER_NOT_READY` 각진 주황 | N-01, N-03, H-01, H-02 | 실행 프로필이 없다(이번 범위에서 실행하지 않음). 카탈로그가 정한 고정값 |
| `NO_TEST_TARGET` 각진 보라 | A-01, A-02, A-03 | 대상 기능이 없다. 카탈로그가 정한 고정값 |
| `READY` 각진 파랑 | E-01 | 준비 상태 확인 기록이 남아 있다(2026-10-12) |
| **확인 도구 오류** 각진 이중 테두리 | N-02, H-03, E-02 | 2026-10-13에 설정이 로드되지 않은 상태로 확인을 눌러 생긴 기록이다. 준비 상태 값이 아니라 **확인 요청 자체의 오류**다 |
| 빈칸 | E-03 | 확인 기록이 없다 |

**"확인 도구 오류"는 결함이 아니다.** 설정 누락 같은 사용 쪽 오류를 "준비 안 됨"으로 뭉개지 않고 따로 표시하는 것이 요구사항이다(FR-011). 그 표시가 보이는 것은 그 설계가 작동한 결과다. 경위는 `../validation.md`에 적혀 있다.

- 참여자가 "이건 뭐냐"고 물으면 **"확인 요청 자체가 잘못돼서 나온 표시이고, 시험 결과와는 다른 줄"** 이라고만 답한다. 그 이상 설명하지 않는다.
- 참여자가 **"확인 도구 오류"나 `RUNNER_NOT_READY`를 실패나 통과로 읽으면** 비고에 적는다. §4의 치명적 오독 1·2번과 성격이 다르므로 오독 표에는 넣지 않는다.
- 참여자가 버튼을 직접 눌러도 된다. 봉인 기록을 바꾸지 않고 Run을 만들지 않는다(SC-010). 다만 그 시나리오의 준비 상태 기록이 그 시점 값으로 갱신되므로, 눌렀으면 **누가 어느 시나리오를 눌렀는지 비고에 적는다.**

### 5-6. 진행 중 하지 않을 것

- 참여자의 답을 고쳐 주거나 힌트를 주지 않는다. 다음 질문의 답이 오염된다.
- 화면 어디를 누르라고 알려 주지 않는다. 찾지 못한 것 자체가 결과다.
- 시험을 다시 돌리거나 기록을 고치지 않는다. 화면에서 가능한 동작은 준비 상태 확인뿐이다.
- 참여자 이름을 기록 시트에 적지 않는다.

### 5-7. 준비

**세션 전 (연우가 준비)**

- 웹을 실제 run root로 띄운다(`python -m engine.web --run-root .controlproof/runs`). **별도 PowerShell 창에서 띄우고 그 창을 닫지 않는다.**
- Run 폴더가 11개인지 확인한다. `blocks`·`locks`는 Run 폴더가 아니므로 디렉터리 수로는 13으로 보인다.
- 워크벤치에 12개 항목과 E-01의 기록 2건(실패·재시험)이 보이는지 확인한다.
- 참여자용 브라우저 창 하나만 열어 둔다. 다른 창(개인 자료·알림)은 닫는다.
- 메모리 여유를 확보한다. 여유가 적으면 웹이 중간에 죽을 수 있다.
- §6 정답 키의 "화면 라벨" 표는 2026-10-13에 실제 기록으로 확인해 채워 뒀다. 진행 당일 화면 문구가 그와 다르면 **화면이 기준이다.**

**참여자 교체마다 (진행자)**

- 브라우저를 워크벤치 첫 화면으로 되돌린다(뒤로 가기가 아니라 주소를 다시 열어 처음 상태로).
- 이전 참여자가 펼친 "개발자용 원본"·"원본 값"이 접힌 상태인지 확인한다. 펼쳐진 채로 두면 다음 참여자가 찾는 과정을 건너뛴다.
- 기록 시트를 새 장으로 바꾼다.

**세션 후**

- 참여자별 기록 시트를 `results.md`의 해당 라운드 절로 옮긴다. 참여자는 P1~P3으로만 적고 개인 식별자를 넣지 않는다.
- 집계표를 채운다. 판정은 T072에서 한다.

## 6. 정답 키

판정 기준은 **뜻이 맞는지**다. 화면에 쓰인 문구를 그대로 말하지 않아도 정답이다. 상태 값 이름(`NOT_RUN` 등)을 영어로 말하지 않아도 뜻이 맞으면 정답이다.

### 과업 1 — 12개 상태

정답: 세 묶음을 구분하면 정답.

- **실제로 시험한 것 5개**: N-02, H-03, E-01, E-02, E-03
- **이번에 실행하지 않은 것 4개**: N-01, N-03, H-01, H-02 — "아직 시험하지 않았다"는 뜻으로 말해야 한다
- **시험할 대상 기능이 없는 것 3개**: A-01, A-02, A-03 — "그 기능이 서비스에 없어서 시험할 게 없다"는 뜻

부분 정답: 개수는 맞지만 어느 항목이 어디인지 틀린 경우 → 오답으로 기록하되 시트 비고에 적는다.
오답 중 치명적 오독: 뒤 4개나 3개를 "통과"로 말함 → §4의 1·2번.

### 과업 2 — E-01 최초 실패의 근거 증적

정답에 들어가야 하는 것:

1. 실패한 기록을 찾았다(Run `86cd0010`, 판정 FAIL).
2. 네 규칙 중 **하나만** 실패했고 나머지는 통과했다는 것을 읽었다.
3. 실패한 규칙의 내용을 뜻으로 말했다 — "근거를 지웠는데도 점수와 인용이 그대로 남아 있었다" / "근거가 사라진 점수가 근거 부족으로 표시되지 않았다".
4. 그 판정의 근거가 된 기록을 화면에서 짚었다 — 아래 증적 묶음 다섯 개 중 **하나 이상**.

4번은 증적 이름을 정확히 말할 필요는 없다. "이 화면의 이 부분을 보고 알았다"고 짚으면 정답이다.
개발자용 원본을 한 단계 더 여는 동작을 스스로 찾았는지는 별도로 기록한다(정답 요건은 아니다).

**3번을 말할 수 있는 경로는 세 가지다. 어느 경로든 뜻이 맞으면 정답이다.**

| 경로 | 화면 위치 | 언어 |
|---|---|---|
| ㄱ | "비개발자용 설명" 카드의 **예상 영향** — "근거가 사라진 뒤에도 점수만 남으면 검토자가 확인할 수 없는 숫자를 믿게 된다" | 한국어 |
| ㄴ | "규칙별 결과" 표 E01-A3 행의 **기대** 열 — `a score whose evidence was removed is exposed as insufficient` | 영문 |
| ㄷ | 같은 행의 **원본 값**을 펼친 뒤 `detail` — `P1: an affected item kept its score and citation after evidence removal` | 영문 |

ㄴ·ㄷ이 영문인 것은 결함이 아니다(§5-3 참고). 한국어만 읽는 참여자는 ㄱ으로 답할 수 있다.

### 화면 라벨 (2026-10-13 확인, 실제 기록 기준)

실패 규칙 행:

| 열 | 보이는 값 |
|---|---|
| 규칙 | `E01-A3` |
| 기대 | `a score whose evidence was removed is exposed as insufficient` / 근거 요구: `EV4-04, EV4-05, EV4-09` |
| 관찰 | `기대와 관찰이 다릅니다.` + 접힌 "원본 값" |
| 결과 | FAIL 배지 |

전체 판정(비개발자용 설명 카드): 판정 사유 "점수 근거 또는 평가 기준 보존의 직접 위반이 관찰되었습니다.", 누락 증적 "없음".

증적 묶음 라벨 5개(증적 열):

- `EV4-04 변경 전후 리포트 저장 기록 · 리포트 저장 기록`
- `EV4-04 변경 전후 리포트 저장 기록 · 저장소 직접 쓰기 진단`
- `EV4-05 리포트 조회(제거 전·후·복원 후) · 회사 화면 리포트 조회`
- `EV4-09 변경 주입·복원과 안전 상태 · 변경 주입·복원 기록`
- `EV4-09 변경 주입·복원과 안전 상태 · 복구 기록`

화면 문구가 위와 다르면 **화면이 기준이다.**

### 과업 3 — 재시험에서 달라진 점

정답에 들어가야 하는 것:

1. 실패했던 규칙이 **통과로 바뀌었다**(그 규칙 하나가 FAIL → PASS).
2. 시험 **대상 버전이 바뀌었다**(`ce8d862` → `374b122`). 커밋 값을 읽지 않아도 "시험한 대상이 수정된 버전으로 바뀌었다"는 뜻이면 정답.
3. 처음 실패 기록은 그대로 보존되어 있다(덮어쓰지 않았다).

1과 2를 둘 다 말하면 정답. 3은 가점으로 기록한다.
**상단 줄 관련 발언은 정답 판정과 별도로 §5-1에 따라 전부 기록한다.**

### 질문 1 — 무엇을 왜 시험했는가

정답: "근거(인용) 없는 점수가 저장되거나 그대로 보이지 않는지" 확인하려고 시험했다는 뜻. "평가 점수에 근거가 붙어 있는지", "근거가 없어지면 그게 드러나는지" 등도 정답.

### 질문 2 — 어떤 조건을 직접 만들었는가

정답: 일부러 조건을 만들었다는 것을 읽어야 한다 — "잘못된 인용을 넣어 봤다", "근거를 일부러 지워 봤다", "지운 뒤 다시 되돌려 봤다" 중 하나 이상.
가점: 실제 지원자 데이터가 아니라 만들어 낸 데이터로 했다는 것까지 말함.

### 질문 3 — 실제로 무엇이 일어났는가

정답: 근거를 지웠을 때 그 점수가 근거 부족으로 드러나지 않고 점수와 인용이 그대로 남아 있었다는 뜻.

### 질문 4 — 왜 이 판정이 나왔는가

정답: 네 규칙 중 하나가 어긋났기 때문이고, 그 판단이 화면에 있는 기록(바뀌기 전/후 기록, 조회 결과)에 근거한다는 뜻.
오답 예: "AI가 점수를 잘못 줬기 때문" — 판정 대상을 잘못 읽은 것이다.

### 질문 5 — 실패 후 무엇을 수정했는가

정답: 서비스 쪽 코드를 고쳐서 근거가 없어진 점수가 드러나게 만들었다는 뜻. "수정한 버전으로 바뀌었다"도 정답.
**중요**: "실패 기록을 고쳤다", "결과를 통과로 바꿨다"는 **오답**이다. 최초 실패 기록은 보존되고 재시험은 별도 기록이다. 이 오답이 나오면 비고에 적는다.

### 질문 6 — 같은 조건의 재시험에서 무엇이 달라졌는가

정답: 과업 3과 같다. 실패했던 규칙이 통과로 바뀌었고 대상 버전이 수정된 버전으로 바뀌었다.

### 질문 7 — 무엇은 아직 검증하지 못했는가 (SC-009)

정답에 **세 가지가 다 들어가야** 한다.

1. 12개 중 **4개는 아직 실행하지 않았다**
2. **3개는 대상 기능이 없어서** 시험하지 못했다
3. **AWS(실제 클라우드) 환경에서는 검증하지 않았다** — 전부 로컬에서만 했다

셋 중 하나라도 빠지면 SC-009 기준으로는 오답이다. 시트에 1·2·3 중 어느 것을 말했는지 따로 적는다.
가점: "통과는 실제로 돌린 시나리오와 그 증적 범위에만 해당한다", "법적 인증이 아니다"까지 말함.
