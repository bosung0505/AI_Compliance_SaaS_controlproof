## Clarifications

### Session 2026-10-08

다섯 질문 모두 제품 책임자가 추천안대로 승인했다(연우 전달). 근거는 Decision Log D-018.

- Q: 웹에서 preflight·Run·재시험을 시작하는가? → A: 웹은 준비 상태 확인(preflight)만 시작한다. Run·재시험·정리 확인은
  웹에서 시작하지 않고, 해당 명령줄 명령과 전제(잠금·복구·차단·사람 승인)를 안내한다. 준비 상태는 확인 시각과 함께 보이고
  사용법 오류와 준비 안 됨을 구분한다(Product Brief §7.2·V4 §8.3보다 줄인 범위).
- Q: 웹 actual validation에 쓸 실제 기록의 출처는? → A: 개발·자동 시험은 합성 기록(`DEMO DATA`)으로, actual validation은 웹을
  띄우는 PC에서 실행 시나리오 5개를 다시 실행한 봉인 기록으로 한다. 다른 PC 기록 가져오기는 범위 밖(플레이북 §7, 별도 Spec).
  E-01 계보는 부모를 WhyYou `ce8d862`, 재시험을 `374b122`로 실행해 만들고, 그 PC의 H-03(`H03_DLQ_V2`) 실행은 새 checkout 조건을
  갖추면 플레이북 §6 독립 재현 gate 기록으로도 쓴다.
- Q: 사용성 검토의 표본·과업·시간·통과 기준은? → A: 비작성자 6명(실행 담당자·검증 책임자·결과 검토자 각 2명), 워크벤치 과업 3개와
  Product Brief §10.3 질문 7개, 질문당 3분, 질문마다 6명 중 5명 이상 정답, 치명적 오독 0건. 섭외·진행은 태오가 맡는다.
- Q: 목업 프로토타입을 Plan 전에 먼저 하는가? → A: Clarify 뒤 `DEMO DATA` 목업으로 네 화면을 만들고, 태오 UX 검토와 제품 책임자
  승인 뒤 Plan을 시작한다.
- Q: 원천 기준선 §2의 엔진 결함은 어디서 고치는가? → A: 위험 1(경로 노출)·2(이스케이프 경로 미검출)·3(증적 링크 누락)과 위험 5 중
  웹이 기대는 출력 불일치는 Spec 005 안에서 실패 시험부터 고친다. 위험 4(Spec 004 재시험 정리 확인 경로)는 Spec 005 밖에서 따로
  작게 고치고 Spec 005 actual validation 전에 끝낸다. 스캐너 강화 전에 기존 봉인 bundle을 새 스캐너로 먼저 검사해 차이를 기록하고
  봉인 파일은 고치지 않는다.
- Q: 종료 코드 2가 사용법 오류와 준비 안 됨을 함께 뜻하는 문제는 어떻게 고치는가? → A: 종료 코드 값은 바꾸지 않고, 출력에 오류
  구분 필드를 추가한다. 웹은 종료 코드가 아니라 이 필드와 준비 상태 값으로 해석한다.
- Q: 보성 PC의 봉인 bundle은 어떻게 새 스캐너로 검사하는가? → A: 보성이 자기 PC에서 새 스캐너로 검사하고 결과만 기록한다. bundle은
  옮기지 않는다.
- Q: 웹 PC에서 다시 실행한 기록의 지위는? → A: Spec 005 웹 검증용 기록이다. 각 시나리오의 공식 상태는 해당 Spec Validation을 따른다.
  N-02는 Spec 003 converge를 따르고, H-03 `H03_DLQ_V2` 기록은 플레이북 §6 독립 재현 gate 기록으로도 쓸 수 있다.
- Q: 목업 검토 결과는? → A: 태오 UX 검토·제품 책임자 승인, 추천안 반영 조건부 승인. (a) 결과 개수는 V4 §8.5의 네 범주를 유지하고,
  판정 불가 카드는 중립색 제목 아래 표와 같은 배지 두 개(노란 `?` INSUFFICIENT_EVIDENCE, 보라 `∅` NO_TEST_TARGET)로 나눈다. (b) 시나리오
  표는 통제별로 묶어 통제 이름을 한 번만 쓰고, ID와 버튼은 줄바꿈하지 않으며, 준비 상태 확인 시각은 표 위에 한 번, 시각이 다른 줄만 따로
  표시한다. (c) 정책 근거에 법 조문을 연결하지 않고 내부 통제 기준과 V4 시나리오 근거만 보이며 "법 조문 대응은 표시하지 않음(법적 준수
  비보증)"을 둔다(V4 §2.2). (d) 워크벤치는 PC 전용, 너비 1280px 기준, 1024px까지 깨지지 않음, 휴대폰·태블릿은 범위 밖. (e) 비개발자용
  기본 문장에서 fixture 이름과 bundle 파일 이름을 빼 개발자용 원본 정보로 옮긴다.

## User Scenarios & Testing *(mandatory)*

### Feature Goal

ControlProof가 이미 만든 봉인된 판정과 증적을, 개발자가 아닌 사람도 웹 화면만으로 정확히 읽게 한다. 웹은 판정을 새로
만들거나 고치지 않는다. 12개 시나리오 가운데 실제 실행한 것, 실행하지 않은 것, 시험 대상이 없는 것을 사실대로 나눠
보여 주고, 실행한 것은 기대 결과에서 원본 증적까지 끊기지 않게 추적하게 한다.

### 용어

- **카탈로그 항목**: 통제 4종(고지·동의 N, 사람 결정 H, 근거·기록 E, 이의제기 A)과 시나리오 12개 각각의 표시 단위.
- **대상 존재 여부**: WhyYou에 시험할 기능이나 처리 경로가 있는지. 없으면 `NO_TEST_TARGET`.
- **준비 상태**: ControlProof가 그 시나리오를 실행할 준비가 됐는지. `READY`·`RUNNER_NOT_READY`·`ACCESS_BLOCKED`·
  `NO_TEST_TARGET`(D-011).
- **시나리오 결과**: `PASS`·`FAIL`·`INCONCLUSIVE`(판정 불가, reason code 필수)·`NOT_RUN`(미실행). `NOT_RUN`은 봉인된
  Run이 없다는 사실이며 판정이 아니다.
- **봉인 기록**: 무결성 검증을 거친 Run의 판정·assertion·증적 묶음(bundle). 웹이 보여 주는 판정의 유일한 원천이다.
- **계보**: 최초 Run(부모)과 재시험 Run(child·grandchild)의 연결.

### User Story 1 - 12개 시나리오의 현재 상태를 한 화면에서 본다 (Priority: P1)

검증 책임자가 워크벤치를 열면 검증 대상과 버전, 통제 4종 아래 12개 시나리오, 각 시나리오의 대상 존재 여부·준비 상태·
최근 결과·실행 방식이 보이고, 결과별 개수와 재시험이 필요한 실패가 요약된다.

**Why this priority**: 제품이 무엇을 실제로 검증했고 무엇을 안 했는지를 오해 없이 보여 주는 것이 ControlProof 주장 범위의
핵심이다(범위표 §2, V4 §12.3). 이것만 있어도 "12개 관리·5개 실행·4개 미실행·3개 대상 없음"을 정확히 전달할 수 있다.

**Independent Test**: 범위표의 12개 상태와 그 근거가 되는 봉인 기록(또는 합성 기록)만 있는 상태에서 워크벤치를 열어,
각 항목의 표시 상태가 범위표와 일치하고 결과별 개수가 맞는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 범위표 기준 상태, **When** 워크벤치를 연다, **Then** 12개가 모두 보이고 H-03·E-03·E-01·E-02는 실제 실행 결과,
   N-02는 `INCONCLUSIVE`와 사유(A5·A7 미입증), H-01·H-02·N-01·N-03은 `NOT_RUN`, A-01~A-03은 `NO_TEST_TARGET`로 보인다.
2. **Given** A-01~A-03, **When** 항목을 본다, **Then** 대상 기능 부재 근거가 연결돼 있고 ControlProof가 새로 구현했거나
   실행한 것처럼 보이는 표현(실행 버튼, 진행률, 통과 표시)이 없다.
3. **Given** 실행기 준비가 안 된 시나리오와 대상이 없는 시나리오, **When** 두 항목을 나란히 본다, **Then**
   `RUNNER_NOT_READY`와 `NO_TEST_TARGET`이 다른 이름·다른 시각 표시·다른 설명으로 구분된다.
4. **Given** 미실행 시나리오와 판정 불가 시나리오, **When** 결과 개수를 본다, **Then** `미실행`과 `판정 불가`가 서로 다른
   칸으로 집계되고 어느 쪽도 `PASS`에 더해지지 않는다.
5. **Given** 워크벤치, **When** 실행 가능한 항목·실패·판정 불가 항목으로 거른다, **Then** 해당 항목만 남는다.

### User Story 2 - 실행 결과에서 판정 근거를 원본 증적까지 추적한다 (Priority: P1)

실행 담당자나 검증 책임자가 한 Run을 열어 실행 ID·대상 버전·실행 시각, 단계별 진행, 적용·해제한 시험 조건, assertion별
기대값·관찰값·결과, 전체 판정과 reason code, 누락·충돌 증적, 복구 확인 결과를 보고, 각 판정에 쓰인 원본 증적과 그 SHA-256을
연다.

**Why this priority**: "근거 없는 PASS 금지"(Constitution I)를 사용자가 직접 확인하는 화면이다. 판정에서 증적까지 이동할 수
없으면 웹 보고서는 판정 문구만 보여 주는 화면이 된다(V4 §12.4).

**Independent Test**: 합성 PASS·FAIL·INCONCLUSIVE·복구 실패 기록 각각을 열어 모든 assertion에 기대값·관찰값과 하나 이상의
증적(경로 대신 사람이 읽는 이름, SHA-256, 형식)이 연결되는지, 표시된 판정이 봉인 판정과 같은지 확인한다.

**Acceptance Scenarios**:

1. **Given** 봉인 무결성이 확인된 Run, **When** 결과 화면을 연다, **Then** 표시된 전체 판정·assertion 결과·reason code가
   봉인 기록과 글자 그대로 같다.
2. **Given** 한 assertion, **When** 증적을 연다, **Then** 그 assertion이 요구한 증적과 실제 연결된 증적이 구분돼 보이고, 각 증적의
   SHA-256과 수집 단계(기준선·주입·복구)가 보인다.
3. **Given** 무결성 검증에 실패한 기록, **When** 화면을 연다, **Then** 판정 대신 무결성 실패가 먼저 보이고 그 기록의 판정을
   사실로 표시하지 않는다.
4. **Given** 복구 실패(`RESTORE_FAILED`) Run, **When** 결과를 본다, **Then** 대상 서비스의 FAIL이 아니라 실행 안전 문제로
   표시되고 수동 정리 필요 여부가 보인다.
5. **Given** `FAIL` 또는 `INCONCLUSIVE`, **When** 비개발자용 설명을 본다, **Then** 실패 의미·예상 영향·누락 증적이 대상
   서비스 내부 이름(테이블·큐·내부 필드)을 기본 문장에 쓰지 않고 설명되며, 원본 정보는 한 단계 더 열어야 보인다.
6. **Given** 실패한 규칙만 보기, **When** 필터를 켠다, **Then** FAIL·INCONCLUSIVE assertion만 남는다.

### User Story 3 - 검증 범위와 한계를 하나의 화면 보고서로 확인한다 (Priority: P1)

결과 검토자가 보고서 화면 하나에서 검증 대상과 버전, 목적과 범위, 합성 데이터 사용, 12개 상태 요약, 시나리오별 기대·관찰 결과,
주요 실패와 영향, 증적 목록과 누락, 적용 정책·모델·프롬프트·평가기준 버전, 최초 실행과 재시험 비교, 시험 목적으로 대상에
추가한 기능, 실행 환경(`LOCAL_EMULATED`)과 AWS `NOT_RUN`, 미검증 범위, 법적 준수 비보증을 읽는다.

**Why this priority**: V4 §8.7·§12.4가 요구하는 결과물이며 비개발자가 읽는 최종 산출물이다. Product Brief §10.3의 일곱 질문이
이 화면에서 답돼야 한다.

**Independent Test**: 보고서 화면만 보고 V4 §8.7의 13개 항목과 §12.4의 9개 항목(모두 22개)이 있는지 점검표로 확인하고, 일곱
질문에 대한 답의 위치를 찾는다.

**Acceptance Scenarios**:

1. **Given** 보고서, **When** 범위 절을 읽는다, **Then** "12개 관리, 5개 실제 실행 대상, 4개 `NOT_RUN`, 3개 `NO_TEST_TARGET`"이
   범위표 고정 문구와 같은 의미로 보이고 "12개 검증 완료"로 읽히는 표현이 없다.
2. **Given** AI 점수를 다루는 결과(E-01·E-02), **When** 보고서를 읽는다, **Then** AI 점수는 참고 정보이고 최종 채용 결정은 권한
   있는 사람이 한다는 원칙과, 사람의 최종 결정·판단 사유를 확인할 위치가 보인다.
3. **Given** 보고서, **When** 한계 절을 읽는다, **Then** 합성 데이터, 외부 AI 차단과 고정 모델 사용(해당 Run), `LOCAL_EMULATED`,
   AWS `NOT_RUN`, 다른 PC 재현 여부, 법적 준수 전체를 보증하지 않는다는 문장이 보인다.
4. **Given** 시험 목적으로 WhyYou에 추가된 기능(예: 고정 모델 fixture, 시험용 hook), **When** 보고서를 읽는다, **Then** 그것이
   제품 기능이 아니라 시험 수단으로 표시된다.

### User Story 4 - 시나리오를 이해하고 실행 조건을 확인한다 (Priority: P2)

실행 담당자가 시나리오 상세에서 의도와 보호 대상, 정책 근거, WhyYou에서의 구현 위치, 전제조건과 준비 상태, 합성 데이터와 대조군,
시험 조건과 복구 방법, 실행 단계, 기대 결과와 판정 규칙, 필수 증적, 수동 단계를 보고, 이전 실행을 열고, 실행할 수 없으면 그
사유와 조치를 본다. 웹에서는 준비 상태 확인만 시작하고, Run·재시험은 복사할 수 있는 명령과 그 전제(잠금·복구·차단·사람 승인)로 안내한다(FR-012).

**Why this priority**: 결과를 이해하려면 무엇을 왜 시험했는지가 먼저 보여야 한다(§10.3 첫 질문). 다만 실행 시작 없이도 조회만으로
가치가 있어 P1 다음이다.

**Independent Test**: 실행 시나리오 5개(7개 실행 프로필)와 미실행·대상 없음 7개의 상세를 열어, 실행 시나리오는 정의 원천과
같은 단계·assertion·필수 증적이 보이고, 미실행 항목은 미실행 사유와 후속 실행 조건이, 대상 없음 항목은 부재 근거가 보이는지
확인한다.

**Acceptance Scenarios**:

1. **Given** 실행 프로필이 둘인 시나리오(H-03, E-03), **When** 상세를 연다, **Then** 프로필별 조건과 결과가 구분된다.
2. **Given** 준비 상태가 `READY`가 아닌 시나리오, **When** 상세를 본다, **Then** 준비 상태 이름, 확인 시각, 막힌 항목, 비민감 조치
   문장이 보이고 실행 명령 안내가 "준비 안 됨" 상태임을 표시한다.
4. **Given** 실행 시나리오, **When** 준비 상태 확인을 누른다, **Then** 새 확인 결과와 확인 시각이 보이고, 사용법 오류는 "준비 안 됨"과
   다른 상태로 보인다. Run·재시험 시작 버튼은 없고 명령과 전제 안내만 있다.
3. **Given** `NOT_RUN` 시나리오(H-01 등), **When** 상세를 본다, **Then** 왜 이번 범위에서 실행하지 않았는지와 실행하려면 필요한
   조건(별도 Spec 또는 범위 변경)이 보이며 판정처럼 보이지 않는다.

### User Story 5 - 최초 FAIL과 재시험을 비교한다 (Priority: P2)

검증 책임자가 최초 Run과 그 재시험(child·grandchild)을 나란히 놓고 대상 버전 차이, 수정 내용, assertion별 이전·이후 결과,
이전·이후 증적, 결과 변화와 남은 실패를 본다. 최초 Run과 재시험이 별도 기록이며 최초 결과가 바뀌지 않았다는 사실이 보인다.

**Why this priority**: "최초 FAIL 보존 → 수정 → 재시험"은 제품 원칙(§2.4)이고 E-01 부모 FAIL → 수정 child PASS 계보가 실제로
있다. 비교 화면은 그 계보를 읽는 방법이다.

**Independent Test**: 합성 FAIL 부모와 PASS child(및 grandchild) 기록으로 비교 화면을 열어, 계보 연결·부모 기록 불변 확인·
assertion별 변화가 보이는지 확인한다.

재시험은 웹에서 시작하지 않으며 화면은 재시험 명령과 전제를 안내한다(FR-012).

**Acceptance Scenarios**:

1. **Given** FAIL 부모와 PASS child, **When** 비교를 연다, **Then** 두 기록이 별도 실행 ID로 보이고 부모의 판정이 FAIL 그대로이며
   child가 부모를 참조한다는 연결이 보인다.
2. **Given** 대상 버전·fixture·평가 원본이 바뀐 재시험, **When** 비교를 본다, **Then** 바뀐 차원(대상 commit, 환경, 모델 fixture,
   점수 규칙 원본 등)이 기록에 있는 그대로 보인다.
3. **Given** 결과 화면에서 수정 메모를 남긴다, **When** 저장한다, **Then** 메모는 봉인 기록과 분리된 별도 기록으로 남고 봉인
   기록의 판정·파일·무결성 값은 바뀌지 않는다.
4. **Given** 계보 검증이 실패한 재시험(부모 기록 변경 등), **When** 비교를 연다, **Then** 비교 대신 계보 무결성 문제를 보여 준다.

### User Story 6 - 역할별 이해도와 사용성을 실제 웹 화면으로 검토한다 (Priority: P3)

D-012가 웹 결과 화면 구현 뒤로 미룬 사람 대상 검토를 실제 화면으로 수행한다. 비작성자 6명(실행 담당자·검증 책임자·결과 검토자 각
2명)이 워크벤치 과업 3개와 Product Brief §10.3의 일곱 질문에 화면만 보고 답하고, 질문별 시간·정답·치명적 오독을 기록한다. 섭외와
진행은 태오가 맡는다(D-018).

**Why this priority**: 화면이 완성돼야 할 수 있고 결과가 정보 구조 수정으로 이어진다. 그러나 Spec 005 완료에는 필요하다(D-012
재검토 조건).

**Independent Test**: 검토 절차 문서와 결과 기록만으로 표본·과업·시간·오답 기준을 충족했는지 판단할 수 있다.

**Acceptance Scenarios**:

1. **Given** 승인된 검토 계획, **When** 참여자가 과업을 수행한다, **Then** 질문별 소요 시간·정답 여부·오독 유형이 기록된다.
2. **Given** 참여자가 `NOT_RUN`이나 `NO_TEST_TARGET`을 통과로, AI 점수를 채용 결정으로, 결과를 법적 인증으로 읽었다, **When**
   기록한다, **Then** 치명적 오독으로 분류되고 통과 기준 판단에 반영된다.

### Edge Cases

- 같은 시나리오에 Run이 여러 개(부모·child·재현 Run)일 때 "최근 결과"는 무엇인가 → 계보의 마지막 공식 결과를 기본으로 보이고,
  최초 결과와 다른 계보로 이동할 수 있어야 한다(가정 A-4).
- 봉인 기록이 하나도 없는 실행 시나리오(예: 다른 PC에만 기록이 있는 경우) → `NOT_RUN`이 아니라 "이 화면에 기록 없음"과 공식
  기록 위치(Validation에 적힌 Run ID와 무결성 해시)를 보여 준다. 실행 사실을 지우지도, 재현된 것처럼 보이지도 않는다.
- 무결성 검증 실패·부분 기록·읽을 수 없는 파일 → 판정을 보이지 않고 무결성 상태를 보인다.
- 경로·토큰·개인정보가 섞인 원본 파일 → 화면에 그대로 보이지 않는다(FR-031, 원천 기준선 §2 위험 1·2).
- 시나리오 정의 버전이 바뀐 뒤의 옛 Run → Run이 기록한 정의 snapshot 기준으로 보여 준다.
- `RESTORE_FAILED` 뒤 차단이 남아 있는 대상 → 명령 안내를 "차단됨"으로 표시하고 정리 확인 절차(명령줄)를 안내한다.
- 준비 상태 확인 결과가 오래됐을 때 → 확인 시각을 함께 보여 지금 상태로 오해하지 않게 한다.
- 준비 상태 확인이 사용법 오류로 끝났을 때 → "준비 안 됨"(`RUNNER_NOT_READY` 등)으로 표시하지 않고 별도의 오류로 보인다.
- 합성 기록과 실제 기록이 함께 있을 때 → 합성 기록은 항상 `DEMO DATA`로 표시되고 실제 결과 개수·보고서 요약에 섞이지 않는다.
- N-02처럼 일부 assertion만 `INCONCLUSIVE`인 Run → 전체 판정과 assertion별 상태를 함께 보여 PASS가 섞인 결과를 통과로 읽지 않게 한다.

## Requirements *(mandatory)*

### Functional Requirements

#### 카탈로그와 상태 표시

- **FR-001**: 워크벤치는 검증 대상과 버전, 적용 정책·평가기준 버전(기록이 있는 경우), 통제 4종과 시나리오 12개를 보여야 한다.
- **FR-002**: 각 시나리오에 대상 존재 여부, 준비 상태, 실행 방식(실제 실행·`NOT_RUN`·`NO_TEST_TARGET`), 최근 결과, 담당 Spec과
  관련 Run 수를 보여야 한다. 시나리오 표는 통제별로 묶어 통제 이름을 묶음 머리에 한 번만 쓰고, 시나리오 ID와 동작 버튼은 줄바꿈하지
  않는다. 준비 상태 확인 시각은 표 위에 한 번 보이고, 확인 시각이 다른 줄만 그 줄에 따로 표시한다.
- **FR-003**: 12개 시나리오의 상태는 범위표(`ControlProof_MVP_Scenario_Coverage_Matrix.md`)와 같아야 하며, 범위표에 없는 상태나
  개수를 화면이 계산해 만들어서는 안 된다. 범위표와 봉인 기록이 어긋나면 어긋남을 표시한다.
- **FR-004**: 결과 개수는 V4 §8.5의 네 범주 `PASS`·`FAIL`·`판정 불가`·`미실행`으로 따로 집계한다. `판정 불가`는 중립색 제목 아래
  reason code별 배지(시나리오 표와 같은 아이콘·색·글자)로 나누어, 색으로 세어도 글자로 세어도 같은 숫자가 나와야 한다.
- **FR-005**: `NOT_RUN`과 `INCONCLUSIVE`, `NO_TEST_TARGET`과 `RUNNER_NOT_READY`(및 `ACCESS_BLOCKED`)는 이름·시각 표시·설명이
  모두 달라야 한다. 상태 이름은 D-011과 Constitution의 명칭만 쓴다.
- **FR-006**: A-01~A-03은 대상 기능 부재 근거와 함께 `NO_TEST_TARGET`로 보이고, 실행 시작·진행률·통과 표시처럼 구현·실행된 것으로
  읽힐 요소를 보여서는 안 된다.
- **FR-007**: 워크벤치는 실행 가능 항목, 실패, 판정 불가 항목으로 거를 수 있어야 하고, 재시험이 필요한 실패와 보고서 진입을 보여야 한다.

#### 시나리오 상세

- **FR-008**: 실행 시나리오의 상세는 시나리오 정의 원천의 의도·전제조건·단계(구간·항상 실행 여부)·assertion 설명과 기대·필수 증적·
  복구 방법·시간 정책·제외 범위를 그대로 보여야 하며, 실행 프로필이 여럿이면 프로필별로 구분해야 한다.
- **FR-009**: 상세는 보호 대상, 정책 근거, WhyYou에서의 구현 위치, 합성 데이터와 대조군, 수동 단계를 사람이 읽는 문장으로 보여야
  한다. 정의 원천에 없는 설명은 출처가 표시된 별도 설명 자료에서 가져와야 한다. 정책 근거는 내부 통제 기준과 V4 시나리오 근거만
  보이고 법 조문(예: AI 기본법 조항)을 연결하지 않으며 "법 조문 대응은 표시하지 않음(법적 준수 비보증)"을 함께 보인다(V4 §2.2).
  조문 연결은 법률 검토된 근거 자료가 생기면 별도 Spec으로 한다.
- **FR-010**: `NOT_RUN` 항목은 미실행 사유와 후속 실행 조건을, `NO_TEST_TARGET` 항목은 부재 근거와 기능이 생겼을 때의 처리(자동 PASS가
  아니라 새 Spec)를 보여야 한다.
- **FR-011**: 준비 상태는 확인 시각과 함께 보여야 하고, `READY`가 아니면 막힌 항목과 비민감 조치 문장을 보여야 한다. 확인 도구의
  사용법 오류는 준비 상태 값과 구분된 오류로 보여야 한다.
- **FR-012**: 웹은 준비 상태 확인(preflight)만 시작할 수 있다. Run·재시험·정리 확인은 웹에서 시작하지 않으며, 화면은 해당
  명령줄 명령(복사 가능)과 전제(대상 잠금, 필수 복구, 차단 해제, 사람의 실행 승인)를 안내한다. 이는 Product Brief §7.2·V4 §8.3의
  "웹에서 실행 시작"을 줄인 범위다(D-018).

#### 실행 결과와 증적

- **FR-013**: 결과 화면은 실행 ID, 시나리오와 프로필, 대상 버전, 실행 시각, 실행 상태, 전체 판정, reason code, 요약을 보여야 한다.
- **FR-014**: assertion마다 기대값·관찰값·결과·설명·근거 요구사항을 보여야 하며, `INCONCLUSIVE`에는 reason code를 반드시 보여야 한다.
- **FR-015**: 각 assertion에서 연결된 원본 증적으로 이동할 수 있어야 하고, 증적마다 사람이 읽는 이름, 형식, 크기, SHA-256, 수집 단계를
  보여야 한다. 요구했으나 연결되지 않은 증적은 누락으로 따로 보여야 한다.
- **FR-016**: 판정·assertion 결과는 봉인 기록에서 읽은 값만 보여야 한다. 화면이나 중간 계층이 기대값과 관찰값을 다시 비교해 판정을
  만들거나 바꿔서는 안 된다.
- **FR-017**: 기록을 보여 주기 전에 봉인 무결성을 확인해야 하며, 실패하면 판정 대신 무결성 실패와 문제 항목을 보여야 한다.
- **FR-018**: 적용·해제한 시험 조건, 복구 결과, 복구 시간 예산 준수 여부, 수동 정리 필요 여부를 보여야 하고, `RESTORE_FAILED`를 대상
  서비스 판정으로 표시해서는 안 된다.
- **FR-019**: `FAIL`·`INCONCLUSIVE`에는 비개발자용 실패 의미·예상 영향·누락 증적을 기본으로, 개발자용 원본 정보를 한 단계 더 열어
  보여야 한다. 기본 문장에는 대상 서비스 내부 이름, 고정 모델 fixture 이름, 봉인 파일 이름을 쓰지 않고 개발자용 원본 정보에만 둔다.
- **FR-020**: 실패 규칙만 보기를 제공해야 한다.

#### 재시험 비교

- **FR-021**: 같은 계보의 부모·child·grandchild를 연결해 보여야 하고, 각 Run의 판정은 그 Run 기록 그대로 보여야 한다.
- **FR-022**: 비교는 assertion별 이전·이후 결과, 이전·이후 증적, 결과 변화, 남은 실패, 재시험 기록이 담은 변경 차원(대상·환경·
  fixture·점수 원본 등)을 보여야 한다.
- **FR-023**: 부모 기록이 바뀌지 않았음을 계보 기록의 부모 무결성 값으로 확인해 보여야 하고, 확인 실패는 계보 문제로 보여야 한다.

#### 데이터 출처와 안전

- **FR-030**: 화면이 보여 주는 모든 판정과 증적의 출처(어느 봉인 기록인지, 합성 기록인지)를 표시해야 하며, 합성 기록에는
  `DEMO DATA` 표시를 해야 한다. 개발과 자동 시험은 합성 기록으로 하고, actual validation은 웹을 띄우는 PC에서 실행 시나리오 5개를
  다시 실행해 만든 봉인 기록으로 한다. E-01 계보는 부모를 WhyYou `ce8d862`, 재시험을 `374b122`로 실행해 만든다. 다른 PC 기록
  가져오기는 범위 밖이다(D-018). 재실행 기록은 Spec 005 웹 검증용이며 각 시나리오의 공식 상태는 해당 Spec Validation을 따른다(N-02는
  Spec 003 converge). H-03 `H03_DLQ_V2` 재실행 기록은 플레이북 §6 독립 재현 gate 기록으로도 쓸 수 있다.
- **FR-031**: 화면과 응답에 개인 절대 경로, 토큰·쿠키·자격 증명, 실제 개인정보, 원문 텍스트(답변·자막·보고서 본문 등)를 보여서는
  안 된다. 이스케이프된 경로 표기를 포함한 경로 노출 검사를 화면 출력 전에 해야 한다.
- **FR-032**: 웹은 봉인 기록·시나리오 정의·범위표를 읽기만 하며 수정·삭제하지 않는다.
- **FR-033**: 이 화면들은 합성 데이터와 로컬 시험 환경의 결과만 다루며 실제 지원자 데이터에 연결하지 않는다.

#### 사용성 검토

- **FR-034**: 실제 웹 화면으로 역할별 사용성 검토를 수행하고 표본·과업·질문·제한 시간·정답 기준·치명적 오독 기준·결과를 기록해야
  한다(D-012, D-018). 표본은 비작성자 6명(세 역할 각 2명), 과업은 워크벤치 과업 3개와 §10.3 질문 7개, 기준은 SC-008을 따른다.
  섭외와 진행은 태오가 맡는다.

#### 웹이 기대는 엔진 결함 보완

- **FR-035**: 원천 기준선 §2의 위험 1(경로 노출), 위험 2(이스케이프된 경로 미검출), 위험 3(증적 링크 누락)과 위험 5 중 웹이 기대는
  출력 불일치는 이 Spec 안에서 실패 시험을 먼저 쓴 뒤 고쳐야 한다. 종료 코드 값은 바꾸지 않고, 출력에 오류 구분 필드를 추가해 사용법
  오류와 준비 안 됨을 구분한다. 웹은 종료 코드가 아니라 이 필드와 준비 상태 값으로 해석한다.
- **FR-036**: 경로·민감정보 검사를 강화하기 전에 기존 봉인 bundle(이 PC와 보성 PC의 것)을 새 검사로 먼저 검사해 기존 검사와의
  결과 차이를 기록해야 하며, 봉인 파일은 고치지 않는다. 보성 PC의 bundle은 보성이 자기 PC에서 새 검사로 검사하고 결과만 기록하며
  bundle을 옮기지 않는다. 강화된 검사가 기존 bundle을 위반으로 판정해도 그 bundle의 판정과 무결성 기록을 바꾸지 않고 차이로만 기록한다.
- **FR-037**: 위험 4(Spec 004 재시험의 정리 확인 경로)는 이 Spec 밖의 별도 작은 보완으로 고치며, 이 Spec의 actual validation 전에
  끝나 있어야 한다.

### 승인된 화면 구조와 상태 이름 (목업 승인 2026-10-08, D-018)

Product Brief §12에 따라 승인된 목업(`mockups/workbench-mockup.html`, 검토 기록 `mockups/REVIEW.md`)의 화면 구조와 상태 이름을
요구사항으로 고정한다. 화면은 PC 전용이며 너비 1280px 기준, 1024px까지 깨지지 않는다(A-10). 모든 합성 기록 화면에는 `DEMO DATA`
표시를 상단에 고정한다.

**① 워크벤치**: 검증 대상·대상 버전·실행 환경(`LOCAL_EMULATED`)·AWS `NOT_RUN`·주장 범위 머리글 → 결과 개수 카드 네 개(PASS, FAIL,
판정 불가, 미실행; 판정 불가는 중립 제목 아래 reason code 배지) → 필터 세 개(실행 가능, 실패·재시험 필요, 판정 불가)와 "준비 상태 확인"
(웹에서 시작하는 유일한 동작)·보고서 진입 → 표 위 공통 준비 상태 확인 시각 → 통제별로 묶은 12개 시나리오 표(ID, 질문, 대상 존재,
준비 상태, 실행 방식, 최근 결과, 상세; ID·버튼 줄바꿈 없음, 다른 시각에 확인한 줄만 시각 표시) → 재시험이 필요한 실패와 보존된 최초
FAIL 계보 → 상태 읽는 법(범례).

**② 시나리오 상세·실행**: 의도, 보호 대상, 정책 근거(내부 통제 기준과 V4 시나리오 근거만, "법 조문 대응은 표시하지 않음(법적 준수
비보증)"), WhyYou에서의 구현 위치(사람 말로), 전제조건, 합성 데이터와 대조군, 시험 조건과 복구, 실행 단계(기준선·주입·복구), 기대
결과와 판정 규칙, 필수 증적, 수동 단계, 실행 안내(전제 네 가지와 복사 가능한 명령; 실행 버튼 없음), 이전 실행·재시험 비교 진입.
`NOT_RUN` 상세는 미실행 사유와 후속 실행 조건, `NO_TEST_TARGET` 상세는 부재 근거·ControlProof의 처리·기능이 생겼을 때의 처리를 보이며
둘 다 실행 버튼·진행률·통과 표시가 없다.

**③ 실행 결과·증적**: 실행 정보(실행 ID, 시나리오·프로필·정의 버전, 대상 버전, 실행 시각, 실행 상태, 복구, 봉인 무결성) → 비개발자용
설명(무엇이 실패했나, 예상 영향, 누락 증적, 판정 사유) → 단계별 진행과 적용·해제한 시험 조건 → 규칙별 결과(기대, 관찰, 결과, 증적;
실패 규칙만 보기) → 증적 표(이름, 형식, 크기, SHA-256, 수집 단계, 연결 규칙) → 개발자용 원본 정보(펼치기; 봉인 파일 이름, 고정 모델
이름, 원본 관찰값은 여기에만) → 수정 메모(봉인 기록과 분리 표시) → 무결성 실패·복구 실패 표시.

**④ 재시험 비교·보고서**: 최초 실행과 재시험을 다른 실행 ID로 좌우에 놓고 → 부모 기록 불변 확인 → 수정 내용 → 바뀐 차원 → 규칙별
이전·이후 결과와 증적 → 결과 변화와 남은 실패(재시험은 명령 안내) → 한 화면 보고서(V4 §8.7 13개 R1~R13, §12.4 9개 C1~C9, 범위표 고정
문구, AI 점수는 참고 정보라는 원칙, 실행 한계).

**상태 이름·아이콘·설명**. 색만으로 구분하지 않는다. 모양 계열은 판정=둥근 배지, 준비 상태=각진 배지, 실행 안전 문제=채운 배지다.
같은 상태는 모든 화면에서 같은 아이콘·글자·모양을 쓴다. 화면 언어는 한국어, 상태 이름과 reason code는 표준 영문을 함께 쓴다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 워크벤치의 12개 시나리오 상태가 범위표와 12/12 일치하고, `NOT_RUN`·`NO_TEST_TARGET`·`INCONCLUSIVE` 항목이 `PASS`로
  표시되거나 집계되는 경우가 0건이다.
- **SC-002**: 화면에 표시된 판정·assertion 결과·reason code가 사용한 모든 봉인 기록(합성 PASS·FAIL·INCONCLUSIVE·복구 실패 포함)과
  100% 같고, 무결성을 일부러 깬 기록은 100% 무결성 실패로 표시된다.
- **SC-003**: 표시된 모든 `PASS`·`FAIL` assertion에서 기대값·관찰값과 원본 증적 하나 이상(SHA-256 포함)에 워크벤치에서 세 번 이하의
  이동으로 닿는다.
- **SC-004**: 보고서 화면이 V4 §8.7 13개 항목과 §12.4 9개 항목을 모두(22/22) 포함한다.
- **SC-005**: 최초 FAIL과 재시험이 있는 계보(실제 E-01 계보 또는 같은 구조의 합성 계보)에서 부모 판정이 그대로 보이고 assertion별
  변화와 변경 차원이 모두 보인다.
- **SC-006**: `NO_TEST_TARGET`과 `RUNNER_NOT_READY`, `판정 불가`와 `미실행`을 구분하는 표시가 화면 점검에서 12개 항목 모두 맞다.
- **SC-007**: 화면과 응답 전체를 대상으로 한 경로·토큰·개인정보·원문 노출 검사에서 위반이 0건이다(이스케이프된 Windows 경로 포함).
- **SC-008**: 실제 웹 화면 사용성 검토: 비작성자 6명(실행 담당자·검증 책임자·결과 검토자 각 2명)이 워크벤치 과업 3개(상태 읽기,
  판정 근거 증적 찾기, 재시험 비교)와 Product Brief §10.3의 일곱 질문을 화면만 보고 수행한다. 질문마다 3분 안에 답하고, 질문마다
  6명 중 5명 이상이 정답이며, 치명적 오독(`NOT_RUN`·`NO_TEST_TARGET`·`INCONCLUSIVE`를 통과로, AI 점수를 채용 결정으로, 결과를 법적
  인증으로 읽음)이 0건이다.
- **SC-009**: 사용성 검토 참여자 6명 중 5명 이상이 "무엇은 아직 검증하지 못했는가"에 범위표와 같은 답(4개 미실행, 3개 대상 없음,
  AWS 미검증)을 한다.
- **SC-010**: 웹에서 시작할 수 있는 동작은 준비 상태 확인뿐이며(Run·재시험·정리 확인 시작 0건), 준비 상태는 모든 화면에서 확인
  시각과 함께 보이고 사용법 오류가 준비 안 됨으로 표시되는 경우가 0건이다.
- **SC-011**: actual validation에 쓴 실제 기록은 모두 웹을 띄운 PC에서 실행한 봉인 기록이고, 화면의 합성 기록은 100% `DEMO DATA`로
  표시되며 실제 결과 개수·보고서 요약에 섞이지 않는다.

## Assumptions

- **A-1 웹은 판정을 만들지 않는다**: 판정·assertion·증적은 봉인 기록에서만 읽는다(Product Brief §12, Constitution I). 근거: 원천 기준선
  §1.3~1.4의 봉인 기록과 검토 요약 구조가 이미 있다.
- **A-2 `NOT_RUN`은 화면 값이다**: 봉인 판정은 `NOT_RUN`을 가질 수 없으므로(원천 기준선 §1.4), 시나리오 단위 `NOT_RUN`은 범위표와 Run
  기록 부재에서 나온다.
- **A-3 12개 카탈로그 데이터는 새로 만든다**: 12개와 그 상태는 지금 문서에만 있으므로(원천 기준선 §1.1), 범위표에서 파생한 카탈로그
  데이터를 따로 두고 범위표와의 일치를 자동 확인한다.
- **A-4 최근 결과**: 계보가 있으면 그 계보의 마지막 공식 결과를 "최근 결과"로 보이되 최초 결과는 항상 같은 화면에서 열 수 있다. 공식 여부는
  Validation 기록을 따른다.
- **A-5 사용자 구분**: 세 역할은 정보 강조 순서만 다르게 하고 로그인·권한 체계는 두지 않는다(Product Brief §11 "복잡한 조직·권한" 제외).
- **A-6 수정 메모**: 메모는 짧은 텍스트·작성자 이름(자기 입력)·시각·대상 Run만 저장하고, 봉인 기록과 별도 위치에 둔다. 첨부·승인 흐름은 없다.
- **A-7 목업 순서(결정, D-018)**: Clarify 뒤 `DEMO DATA` 목업으로 네 화면을 만들고, 태오 UX 검토와 제품 책임자 승인 뒤 Plan을
  시작한다. 승인된 화면 구조와 상태 이름을 Plan에 반영한다. 근거: Product Brief §12, 저장소에 승인된 목업 없음(원천 기준선 §4).
- **A-8 성능**: 로컬에서 한 사용자가 쓰는 도구이며 화면 전환은 사람이 기다림을 느끼지 않을 수준(대략 2초 안)을 기본으로 한다.
- **A-9 언어**: 기본 화면 언어는 한국어이고 상태 이름·reason code는 표준 영문 명칭을 함께 쓴다.
- **A-10 화면 크기(결정, D-018 추가 결정)**: 워크벤치는 PC 전용이다. 너비 1280px 기준으로 설계하고 1024px까지 깨지지 않아야 한다.
  휴대폰·태블릿 대응은 MVP 범위 밖이다.

## Dependencies

- Spec 001~004의 봉인 기록 형식, 검토 요약, 무결성 검증(ControlProof `865b0ed`).
- 범위표·Decision Log D-011~D-014·D-017의 상태와 문구.
- actual validation용 실제 기록: 웹을 띄우는 PC에서 실행 시나리오 5개 재실행(E-01 계보는 WhyYou `ce8d862` 부모 → `374b122` 재시험).
- 위험 4 보완(FR-037)이 actual validation 전에 끝나 있어야 한다.
- 목업 프로토타입의 태오 UX 검토·제품 책임자 승인(A-7)이 Plan의 전제다. 사용성 검토 참여자 6명 섭외·진행은 태오가 맡는다(SC-008).

## Risks and Product Responses

- 화면이 판정을 다시 계산하면 엔진과 화면 판정이 갈라질 수 있다 → FR-016으로 봉인 판정만 보여 주고 일치를 SC-002로 측정한다.
- 경로·원문이 원본 증적 보기로 새어 나갈 수 있다(원천 기준선 §2 위험 1·2) → FR-031·SC-007로 화면 출력 전 검사를 요구한다.
- 현재 엔진의 검토 요약은 일부 증적 연결을 빠뜨린다(원천 기준선 §2 위험 3) → FR-015는 봉인 기록의 증적 목록 전체를 기준으로 추적하도록 요구하고 원천은 Plan에서 정한다.
- 실제 기록이 각 PC에 흩어져 있다 → 개발은 `DEMO DATA` 합성 기록으로, actual validation은 웹을 띄우는 PC의 재실행 기록으로 한다(FR-030).
- 웹에서 Run을 시작하면 실행 안전 규칙이 우회될 수 있다 → 웹은 준비 상태 확인만 시작하고 Run·재시험·정리 확인은 명령 안내로 둔다(FR-012).
- 검사 강화가 기존 봉인 bundle을 소급해 위반으로 만들 수 있다 → 강화 전 기존 bundle을 먼저 검사해 차이만 기록하고 봉인 파일·판정은 바꾸지 않는다(FR-036).
