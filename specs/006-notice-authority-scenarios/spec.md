## User Scenarios & Testing *(mandatory)*

### Feature Goal

V4가 관리하지만 실행하지 않았던 고지(N-01·N-03)와 사람 결정 권한(H-01·H-02) 네 시나리오를, 이미 검증된 판정·봉인·복구·
재시험 계약 위에서 실제 WhyYou 격리 환경에 대해 실행하고 원본 증적과 함께 판정한다. 결과는 기존 웹 워크벤치에서 다른
시나리오와 같은 방식으로 읽힌다. ControlProof의 실행기 완료와 WhyYou 대상 동작의 판정은 Spec 003·004처럼 분리해 기록한다.

### 용어

- **필수 고지 다섯 항목**: AI 평가 보조, 사람의 최종 결정, 녹화·처리 목적, 보관기간, 삭제 방법(V4 §10.1·§7.1). 이의제기
  문구는 대상 기능이 없으므로 항목에 넣지 않는다.
- **읽을 수 있게 표시됨**: 동의 제출 전에 지원자가 그 동의 단계 안에서 도달할 수 있는 화면 상태에서, 항목 문구가 화면 영역
  안에 있고 잘리지 않으며 버튼·팝업·다른 요소에 가려지지 않은 상태.
- **정책 식별값**: 정책 버전과 정책 내용 해시. 화면이 받은 값, 서버가 제공한 현재 값, 저장된 동의 기록의 값을 구분한다.
- **최종결정 쓰기 경로**: 최종결정을 기록하는 API와, 지원자를 최종 단계(최종합격·불합격)로 옮기는 채용 단계 이동 API
  (원천 기준선 1절).
- **주체**: 최종결정 시도를 보내는 쪽. 정상 회사 사용자, 인증 없음, 지원자 자격, 유효하지 않은 자격, 작업자(`SYSTEM`),
  AI 어시스턴트.
- **기능 표면**: AI 어시스턴트가 외부에 여는 경로 전체와 작업자가 처리하는 사건·작업 전체의 목록.
- **대상 접근 종류**: 판정에 필요한 접근. 화면(브라우저로 대상 화면을 엶), API(대상 HTTP 경로 호출·조회), 소스 열람(대상
  소스 코드를 읽음).

### User Story 1 - 권한 없는 주체의 최종결정이 거부되는지 확인한다 (Priority: P1)

H-01. 검토 가능한 리포트가 준비된 합성 지원자를 쓰기 경로마다 따로 준비하고, 정상 회사 사용자의 결정이 허용되는 기준 동작을
먼저 확인한다. 그 뒤 같은 요청을 인증 없음·지원자 자격·유효하지 않은 자격으로 두 쓰기 경로에 각각 보내, 거부와 무변경과
감사 기록을 확인한다.

**Why this priority**: "최종 채용 결정은 권한 있는 사람만 확정한다"는 Constitution III과 제품 불변식의 직접 시험이고,
원천 기준선상 WhyYou 수정 없이 대상이 있다.

**Independent Test**: H-01 Run 한 건만으로 경로×주체별 요청·응답, 시도 전후 상태, 감사 기록을 봉인하고 판정할 수 있다.

**Acceptance Scenarios**:

1. **Given** 리포트가 준비된 합성 지원자, **When** 정상 회사 사용자가 각 쓰기 경로로 결정을 기록하면, **Then** 결정이 저장되고
   이 결과가 기준 동작으로 기록된다.
2. **Given** 아직 결정이 없는 합성 지원자, **When** 인증 없음·지원자 자격·유효하지 않은 자격으로 각 쓰기 경로에 결정을 보내면,
   **Then** 모든 시도가 성공 응답 없이 거부된다.
3. **Given** 2의 거부된 시도, **When** 시도 전후 상태를 비교하면, **Then** 사람 검토 기록·최종결정·채용 단계·재전송 방지 기록 중
   어느 것도 바뀌지 않았다.
4. **Given** 2의 거부된 시도, **When** 감사 기록을 조회하면, **Then** 시도마다 요청 주체·시각·대상 지원자·실패 사유가 남아 있는지가
   관찰 사실로 기록된다.
5. **Given** 작업자와 AI 어시스턴트에는 HTTP 자격 증명이 없음(원천 기준선 1절), **When** 결과를 판정하면, **Then** 이 두 주체는
   FR-023에서 정한 방식으로 다뤄지고 결과에 그 방식이 표시된다.

### User Story 2 - PC·모바일 동의 화면의 필수 고지를 확인한다 (Priority: P1)

N-01. 합성 지원자가 접근·본인 확인을 마치고 동의 단계에 들어간 상태를 PC 화면과 390px 모바일 화면에서 각각 연다. 다섯 항목이
읽을 수 있게 표시되는지 확인하고, 화면이 받은 정책 식별값으로 제품 흐름에서 동의를 완료해 저장된 동의 기록과 연결한다.

**Why this priority**: 지원자가 AI 평가·녹화·사람 결정 원칙을 알고 참여했는지의 출발점이고, Constitution 품질 게이트가 N-01에
PC·모바일 화면 증적을 명시적으로 요구한다.

**Independent Test**: N-01 Run 한 건으로 두 화면 캡처, 항목별 표시 판정, 화면·서버·저장 기록의 정책 식별값 대조를 봉인한다.

**Acceptance Scenarios**:

1. **Given** 동의 단계의 PC 화면, **When** 다섯 항목을 확인하면, **Then** 항목마다 표시·잘림·가림 여부가 판정되고 캡처가 남는다.
2. **Given** 같은 단계의 390px 모바일 화면, **When** 같은 확인을 하면, **Then** 1과 같은 판정과 캡처가 따로 남는다.
3. **Given** 화면이 받은 정책 식별값, **When** 지원자가 그 값으로 동의를 완료하면, **Then** 화면 값·서버 현재 값·저장된 동의 기록의
   값이 같은지 판정되고 동의 완료 시각과 합성 지원자 식별자가 함께 남는다.
4. **Given** 한 화면에서만 항목이 잘리거나 가려짐, **When** 판정하면, **Then** 다른 화면의 결과와 섞이지 않고 해당 화면의 assertion이
   FAIL이다.

### User Story 3 - AI 어시스턴트·작업자의 쓰기 권한 표면을 검사한다 (Priority: P2)

H-02. 검사 대상 커밋의 소스에서 AI 어시스턴트의 공개 경로 전체와 작업자의 처리 목록 전체를 열거하고, 항목마다 읽기·쓰기를
구분해 최종결정·채용 단계 쓰기가 직접 또는 간접으로 노출됐는지 정적으로 검사한다.

**Why this priority**: H-01이 "문이 잠겼는가"라면 H-02는 "문이 아예 없는가"다(V4 §10.5). 실행 상태 변경이 없어 복구 위험은 낮지만
소스 열람이 필요하다.

**Independent Test**: H-02 Run 한 건으로 두 목록 전체, 항목별 분류와 근거 위치, 검사 대상 커밋을 봉인한다.

**Acceptance Scenarios**:

1. **Given** 검사 대상 커밋, **When** 어시스턴트 공개 경로를 열거하면, **Then** 모든 경로가 읽기·쓰기 분류와 근거 위치를 가진다.
2. **Given** 같은 커밋, **When** 작업자 처리 목록을 열거하면, **Then** 모든 항목이 같은 분류와 근거 위치를 가진다.
3. **Given** 두 목록, **When** 최종결정·채용 단계 쓰기 기능에 도달하는지 검사하면, **Then** 도달하는 항목이 없으면 PASS, 있으면 그
   항목이 실제로 바꿀 수 있는 상태와 함께 FAIL이다.
4. **Given** 열거하거나 분류하지 못한 항목, **When** 판정하면, **Then** PASS로 추정하지 않고 사유 코드와 함께 `INCONCLUSIVE`다.

### User Story 4 - 정책 교체 구간의 동의 귀속을 확인한다 (Priority: P3)

N-03. 합성 지원자가 동의 화면에서 정책 식별값을 읽은 뒤, 이전 정책 식별값으로 낸 동의가 거부되는지, 최신 정책을 다시 읽고 낸
동의가 정상 저장되는지, 이미 완료된 다른 지원자의 과거 동의가 바뀌지 않는지 확인한다. 실행 중 정책 교체와 분석 작업 귀속의
범위는 FR-031에서 정한다.

**Why this priority**: 원천 기준선 4절상 낡은 정책 거부만 대상이 있고 교체 수단과 분석 귀속 저장 필드가 없어 범위가 아직 열려
있다.

**Independent Test**: N-03 Run 한 건으로 이전·최신 식별값, 거부 응답, 최종 저장 기록, 과거 동의 기록 전후를 봉인한다.

**Acceptance Scenarios**:

1. **Given** 이전 정책 식별값, **When** 그 값으로 동의를 제출하면, **Then** 거부되고 그 지원자의 동의 기록·동의 상태가 생기거나
   바뀌지 않는다.
2. **Given** 1의 지원자, **When** 최신 정책을 다시 읽고 그 값으로 제출하면, **Then** 동의가 저장되고 저장 기록의 식별값이 다시 읽은
   값과 같다.
3. **Given** 시험 전에 동의를 완료한 별도 합성 지원자, **When** 1·2 뒤 그 기록을 다시 읽으면, **Then** 기록이 시험 전과 같다.
4. **Given** FR-031에서 교체 주입을 범위에 넣은 경우, **When** 교체와 제출을 근접 시점에 실행하면, **Then** 저장 기록의 식별값이
   지원자가 실제로 읽은 값과 같은지와 교체가 복구됐는지가 판정된다.

### User Story 5 - 결과와 한계를 기존 워크벤치에서 검토한다 (Priority: P2)

검증 책임자와 결과 검토자는 네 시나리오의 Run 결과를 기존 웹 워크벤치에서 다른 시나리오와 같은 방식(조건·기대·관찰·근거,
판정과 사유 코드, 복구 상태, 미검증 범위)으로 읽는다. 각 결과는 사용한 대상 접근 종류와 격리 환경의 한계를 함께 보여 준다.

**Independent Test**: 봉인된 Run 하나를 워크벤치에서 열어 assertion별 기대·관찰·증적 링크와 한계 표시를 확인한다.

**Acceptance Scenarios**:

1. **Given** 네 시나리오 중 하나의 봉인 Run, **When** 워크벤치에서 열면, **Then** 기존 시나리오와 같은 화면 구조로 assertion별 결과와
   증적이 보인다.
2. **Given** closure 전, **When** 카탈로그를 보면, **Then** 네 시나리오의 공식 상태는 `NOT_RUN`이고 12/5/4/3 숫자가 바뀌지 않는다.

---

### User Story 6 - 최초 결과를 보존하고 수정 후 재시험한다 (Priority: P3)

Spec 003·004와 같다. 최초 FAIL·INCONCLUSIVE는 봉인 뒤 덮어쓰지 않고, 원인을 분류한 뒤 승인된 수정이 있으면 같은 프로필의
parent-linked child Run으로만 재시험한다.

**Acceptance Scenarios**:

1. **Given** 최초 Run의 FAIL, **When** 수정 후 재시험하면, **Then** 새 child Run이 생기고 부모의 판정·증적·manifest는 바뀌지 않는다.

### Edge Cases

- 고지 항목이 접힘·펼침 영역 안에 있으면, 동의 제출 전 그 단계 안에서 도달할 수 있는 상태를 기준으로 판정하고 필요한 조작
  (스크롤·펼침)을 증적에 남긴다. 펼치지 않고도 동의 제출이 가능하다는 사실은 따로 관찰로 기록한다.
- 390px에서 항목을 읽으려면 가로 스크롤이 필요하면 잘림으로 본다. 세로 스크롤은 허용한다.
- 화면 텍스트에는 항목이 있지만 화면 영역 밖이거나 다른 요소에 덮여 있으면 표시되지 않은 것으로 본다. 텍스트 존재만으로
  PASS하지 않는다.
- 화면이 받은 정책 식별값과 저장 기록의 값이 다르면 N-01 FAIL이다. 화면 값을 읽지 못했으면 PASS·FAIL을 주장하지 않고
  `INCONCLUSIVE`(`INSUFFICIENT_EVIDENCE`)다.
- H-01에서 정상 회사 사용자의 기준 동작이 실패하면 거부 시도의 의미를 판정할 수 없으므로 해당 경로의 거부 assertion은
  `INCONCLUSIVE`다.
- H-01 거부 응답의 상태 코드 종류(인증 실패·권한 없음·입력 오류)는 기록만 한다. 판정은 성공 응답 부재와 상태 무변경으로 한다.
- 결정이 이미 기록된 지원자로 거부 시도를 하면 무변경을 구분할 수 없으므로, 거부 시도는 결정이 없는 지원자에게만 한다.
- H-02에서 동적 호출·주입 때문에 도달 여부를 정적으로 정할 수 없는 항목은 `INCONCLUSIVE`이며, 정적 검사의 범위(호출 그래프
  깊이, 동적 디스패치 처리)는 Plan에서 고정하고 결과에 표시한다.
- N-03의 "이전 정책 식별값"이 실제 교체 없이 만든 값이면(FR-031 결정에 따라) 그 사실을 결과의 한계로 표시한다.
- 과거 동의 기록 불변 확인에 쓰는 지원자는 Run 소유 합성 지원자이며 다른 Run·lane과 공유하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

#### 공통 — 대상·준비·판정 단위

- **FR-001**: 네 시나리오는 `LOCAL_EMULATED` 격리 WhyYou 대상에서만 실행한다. 외부 AI 차단, 소스 clean, 대상 버전 확인을 기존
  preflight 계약대로 요구하고 실제 AWS는 `NOT_RUN`으로 둔다.
- **FR-002**: N-01·N-03·H-01·H-02는 시나리오 ID·실행 프로필·시나리오 정의·Run·bundle·재시험 계보를 각각 따로 가진다. 준비·관찰·
  봉인 구현은 공유할 수 있으나 한 Run의 결과가 다른 시나리오의 판정 근거가 되지 않는다(Spec 004 FR-043 선례).
- **FR-003**: 모든 지원자·리포트·동의 기록은 Run 소유 합성 데이터이며 Run 종료 시 Run 소유 데이터만 정리하고 잔여를 확인한다.
- **FR-004**: 실행 준비 상태는 `READY`, `RUNNER_NOT_READY`, `ACCESS_BLOCKED`, `NO_TEST_TARGET`만 쓴다. 대상은 있으나 실행기·화면
  수집·시험 수단이 준비되지 않았으면 `RUNNER_NOT_READY`이며 `NO_TEST_TARGET`으로 쓰지 않는다.
- **FR-005**: 시나리오마다 판정에 필요한 대상 접근 종류(화면, API, 소스 열람)를 시나리오 정의와 결과에 기록한다. 이 정보를
  구매자(공급기업·채용기업)별 판정 범위로 결과에서 읽을 수 있게 할지 [NEEDS CLARIFICATION: 시나리오별 대상 접근 종류를
  결과에 명시해 구매자별 판정 범위를 읽을 수 있게 할지, 한다면 기록만 할지·워크벤치에 표시할지·접근이 없을 때 준비 상태를
  어떻게 둘지].

#### N-01 — 고지 표시

- **FR-010**: N-01은 합성 지원자를 접근·본인 확인까지 진행시킨 뒤 동의 단계를 PC 화면과 390px 폭 모바일 화면에서 각각 연다.
  PC 폭은 Plan에서 고정하고 두 폭 모두 증적에 기록한다.
- **FR-011**: 화면마다 다섯 필수 고지 항목의 표시 여부, 잘림, 가림을 항목별로 판정하고 전체 화면 캡처를 남긴다. 판정은 화면
  텍스트의 존재와 화면 영역 안의 실제 보임을 함께 근거로 한다.
- **FR-012**: 화면이 받은 정책 식별값, 서버가 제공한 현재 정책 식별값, 그 값으로 제품 흐름에서 완료한 동의의 저장 기록 식별값을
  대조한다. 동의 완료 시각과 합성 지원자 식별자를 함께 남긴다.
- **FR-013**: 고지 확인은 자료 제출·분석 시작 전 단계에서 이뤄져야 한다. 동의 전 처리 차단 자체는 N-02가 소유하므로 N-01은 다시
  판정하지 않는다.

#### H-01 — 권한 없는 최종결정 거부

- **FR-020**: H-01은 두 최종결정 쓰기 경로 각각에 대해 독립 합성 지원자를 쓰고, 검토 가능한 리포트가 준비된 상태에서 시작한다.
- **FR-021**: 각 경로에서 정상 회사 사용자의 결정을 먼저 실행해 허용되는 기준 동작을 기록한다.
- **FR-022**: 각 경로에서 인증 없음, 지원자 자격, 유효하지 않은 자격의 세 주체로 같은 결정 요청을 보내고, 주체별 요청·응답·
  권한 정보를 수집한다. 시험용 자격 증명은 local/test 값만 쓰고 원문은 봉인하지 않는다.
- **FR-023**: 작업자(`SYSTEM`)와 AI 어시스턴트는 HTTP 자격 증명이 없다. 이 두 주체의 처리 방식 [NEEDS CLARIFICATION: 자격
  증명 부재를 구조상 차단의 증거로 보고 H-01 assertion에 넣을지, 별도 판정(예: H-02 정적 검사 결과에 위임, 또는 해당 주체
  `NOT_RUN`·사유 표시)으로 둘지, 시험용 호출 수단을 만들어 실제로 시도할지].
- **FR-024**: 거부된 모든 시도의 전후로 사람 검토 기록, 최종결정, 채용 단계, 재전송 방지 기록과 관련 이력을 비교한다. 하나라도
  바뀌면 FAIL이다. 전후 상태를 수집하지 못하면 `INCONCLUSIVE`다.
- **FR-025**: 거부된 시도마다 감사 기록에 요청 주체·시각·대상 지원자·실패 사유가 남는지 관찰한다. 남지 않으면 그 사실을 판정
  근거로 기록한다(감사 assertion의 FAIL 여부는 H01 Assertion Contract를 따른다).

#### N-03 — 정책 교체 구간

- **FR-030**: N-03은 이전 정책 식별값으로 낸 동의의 거부와 무변경, 최신 정책을 다시 읽고 낸 동의의 정상 저장과 식별값 일치, 이미
  완료된 과거 동의 기록의 불변을 판정한다.
- **FR-031**: 원천 기준선 4절상 WhyYou에는 실행 중 정책을 바꿀 수단이 없고 분석 작업에 정책 버전이 저장되지 않는다. 교체 주입과
  분석 귀속의 범위 [NEEDS CLARIFICATION: 시험용 정책 교체 수단을 만들어 실제 교체·근접 제출·복구까지 범위에 넣을지, 이전
  식별값을 직접 보내는 우회만으로 판정할지; 분석 작업의 정책 귀속을 범위에 넣는다면 저장 필드가 없는 현재 상태를 FAIL·
  INCONCLUSIVE·범위 밖 중 무엇으로 판정할지].
- **FR-032**: 교체 주입을 쓰면 그 주입은 local/test 환경에서만 켜지고 Run·대상 allowlist로 제한되며, Run 종료 전 원래 정책으로
  되돌리고 안전 상태를 확인한다.

#### H-02 — 쓰기 권한 표면

- **FR-040**: H-02는 검사 대상 커밋을 고정하고 AI 어시스턴트의 공개 경로 전체와 작업자의 처리 목록 전체를 열거한다.
- **FR-041**: 항목마다 읽기·쓰기 구분, 바꿀 수 있는 상태의 종류, 근거 위치를 기록한다.
- **FR-042**: 어떤 항목이든 최종결정·채용 단계 쓰기 기능에 직접 또는 간접으로 도달하면 FAIL이며, 그 항목이 실제로 바꿀 수 있는
  상태를 함께 기록한다. 도달 여부를 정할 수 없는 항목이 하나라도 있으면 전체를 PASS로 두지 않는다.
- **FR-043**: H-02는 대상 상태를 바꾸지 않는다. 결과에는 복구 대상 없음과 정적 검사의 범위·한계를 표시한다.

#### 공통 — 판정·증적·복구·표시

- **FR-050**: assertion별 PASS·FAIL·INCONCLUSIVE를 기존 판정 모델로 낸다. PASS·FAIL은 기대·관찰·근거로 사유를 제시하고
  INCONCLUSIVE에는 D-011 사유 코드를 요구한다. 시나리오 Run의 전체 PASS는 그 시나리오의 필수 assertion이 모두 PASS일 때만이다.
- **FR-051**: 증적은 기존 봉인·`verify`·redaction 계약을 따른다. 자격 증명·토큰·쿠키 원문과 실제 개인정보는 봉인하지 않는다.
- **FR-052**: 변경·장애 주입이나 상태 변경을 쓴 Run은 종료 전 복구하고 안전 상태를 확인한다. 미확인이면 `RESTORE_FAILED`
  (판정 INCONCLUSIVE)로 두고 같은 대상의 후속 주입을 차단한다.
- **FR-053**: 최초 FAIL·INCONCLUSIVE는 봉인 뒤 덮어쓰지 않는다. 원인을 대상 결함·실행기 결함·복구 운영 결함으로 분류하고, 대상
  결함 수정은 최초 사실 봉인 뒤 결정 기록과 승인을 거쳐 개인 브랜치에서 실패 시험부터 한다. 검증은 parent-linked child Run으로만
  한다.
- **FR-054**: 새 결과는 기존 웹 워크벤치에서 기존 화면 구조·상태 이름으로 보인다. 웹에서 Run·재시험을 시작하지 않는다(D-018).
- **FR-055**: 실제 Run과 closure 전까지 범위표·카탈로그·README의 네 시나리오 상태와 12/5/4/3 숫자를 바꾸지 않는다(D-024 3항).
- **FR-056**: 모든 결과는 실행한 시나리오와 증적의 범위만 주장하며 합성 데이터·`LOCAL_EMULATED`·외부 AI 차단·사용한 시험 수단을
  한계로 표시한다. 법적 준수 전체를 검증했다고 표현하지 않는다.

### Assertion Contract (초안)

각 assertion은 해당 시나리오 Run에서만 판정한다. 세부 판정 규칙과 증적 매핑은 Plan의 계약에서 고정한다.

| ID | 주장 | 판정 근거 |
|---|---|---|
| N01-A1 | PC 화면에 다섯 필수 고지가 읽을 수 있게 표시된다 | PC 캡처, 항목별 텍스트·보임 판정 |
| N01-A2 | 390px 모바일 화면에 다섯 필수 고지가 잘림·가림 없이 표시된다 | 모바일 캡처, 항목별 텍스트·보임 판정 |
| N01-A3 | 화면 정책 식별값이 서버 현재 값·저장된 동의 기록과 같다 | 세 값, 동의 완료 시각, 지원자 식별자 |
| N03-A1 | 이전 정책 식별값의 동의는 거부되고 동의 기록·상태가 바뀌지 않는다 | 거부 응답, 시도 전후 동의 기록·상태 |
| N03-A2 | 최신 정책 재확인 뒤 동의는 저장되고 식별값이 재확인한 값과 같다 | 재조회 값, 저장 기록 |
| N03-A3 | 이미 완료된 과거 동의 기록은 바뀌지 않는다 | 과거 기록 전후 비교 |
| N03-A4 | (FR-031 결정에 따름) 교체 구간 제출·분석 작업의 정책 귀속 | 교체 전후 식별값, 저장 기록, 분석 작업 기록 |
| H01-A1 | 정상 회사 사용자의 결정은 두 경로에서 허용된다(기준 동작) | 경로별 요청·응답, 저장 결정 |
| H01-A2 | 인증 없음·지원자 자격·유효하지 않은 자격의 시도는 두 경로에서 거부된다 | 경로×주체별 요청·응답 |
| H01-A3 | 거부된 시도는 상태를 바꾸지 않는다 | 시도 전후 사람 검토·결정·단계·재전송 방지 기록 |
| H01-A4 | 거부된 시도가 감사 기록에 주체·시각·대상·사유와 함께 남는다 | 감사 기록 조회 |
| H02-A1 | AI 어시스턴트 공개 경로가 전부 열거·분류된다 | 경로 목록, 분류, 근거 위치, 커밋 |
| H02-A2 | 작업자 처리 목록이 전부 열거·분류된다 | 처리 목록, 분류, 근거 위치, 커밋 |
| H02-A3 | 두 목록 어디에서도 최종결정·채용 단계 쓰기에 도달하지 않는다 | 도달 분석 결과 |

#### Included

A-01~A-03(`NO_TEST_TARGET` 유지), 실제 AWS(`NOT_RUN`), 실제 지원자 데이터, 외부 AI 호출, main 병합, 시험용 수단을 뺀 WhyYou
기능 추가, 웹에서 Run·재시험 시작, 범위표·카탈로그·README 숫자의 사전 변경(closure에서만), N-02가 소유하는 동의 전 처리 차단의
재판정, 법 조문 대응 표시.

## Success Criteria *(mandatory)*

### Measurable Outcomes

## Assumptions

- Spec 001~004의 Run·관찰·증적·판정·복구·불변 재시험·대상 스냅샷 계약과 Spec 005 워크벤치 표시 계약을 재사용한다.
- 기준 source는 ControlProof `994dd3f`, WhyYou `33aa996`(D-024)이며, 원천 기준선이 다루는 동의·최종결정·어시스턴트·작업자
  코드는 `374b122`와 같다. 기준이 바뀌면 원천 기준선을 다시 만든다.
- N-01의 판정 범위는 V4 §10.1의 다섯 항목이다. 이의제기 고지는 대상 기능이 없어 확인하지 않는다(V4 §7.1).

  assertion에 넣지 않았고, 포함 여부는 Clarify에서 확인한다.

- 최초 actual Run 전에 확인되지 않은 WhyYou 결함을 미리 고치지 않는다(V4 §7.3).
