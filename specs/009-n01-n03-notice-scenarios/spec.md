## User Scenarios & Testing *(mandatory)*

### Feature Goal

V4가 관리하지만 실행하지 않았던 고지 영역 두 시나리오(N-01·N-03)를, 이미 검증된 판정·봉인·복구·재시험 계약 위에서 실제 WhyYou
격리 환경에 대해 실행하고 원본 증적과 함께 판정한다. 결과는 기존 웹 워크벤치에서 다른 시나리오와 같은 방식으로 읽힌다.
ControlProof의 실행기 완료와 WhyYou 대상 동작의 판정은 Spec 003·006·007처럼 분리해 기록한다.

### 용어

- **필수 고지 다섯 항목**: AI 평가 보조, 사람의 최종 결정, 녹화·처리 목적, 보관기간, 삭제 방법(V4 §10.1·§7.1). 이의제기
  문구는 대상 기능이 없으므로 항목에 넣지 않는다.
- **읽을 수 있게 표시됨**: 동의 제출 전에 지원자가 그 동의 단계 안에서 도달할 수 있는 화면 상태에서, 항목 문구가 화면 영역
  안에 있고 잘리지 않으며 버튼·팝업·다른 요소에 가려지지 않은 상태.
- **정책 식별값**: 정책 버전과 정책 내용 해시. 화면이 받은 값, 서버가 제공한 현재 값, 저장된 동의 기록의 값을 구분한다.
- **대상 접근 종류**: 판정에 필요한 접근. 화면(브라우저로 대상 화면을 엶), API(대상 HTTP 경로 호출·조회), 소스 열람(대상
  소스 코드를 읽음). 이 Spec의 두 시나리오는 화면·API만 쓴다.

### User Story 1 - PC·모바일 동의 화면의 필수 고지를 확인한다 (Priority: P1)

N-01. 합성 지원자가 접근·본인 확인을 마치고 동의 단계에 들어간 상태를 PC 화면과 390px 모바일 화면에서 각각 연다. 다섯 항목이
읽을 수 있게 표시되는지 확인하고, 화면이 받은 정책 식별값으로 제품 흐름에서 동의를 완료해 저장된 동의 기록과 연결한다.

**Why this priority**: 지원자가 AI 평가·녹화·사람 결정 원칙을 알고 참여했는지의 출발점이고, Constitution 품질 게이트가 N-01에
PC·모바일 화면 증적을 명시적으로 요구한다.

**Independent Test**: N-01 Run 한 건으로 두 화면 캡처, 항목별 표시 판정, 화면·서버·저장 기록의 정책 식별값 대조를 봉인한다.

**Acceptance Scenarios**:

1. **Given** 동의 단계의 PC 화면, **When** 다섯 항목을 확인하면, **Then** 항목마다 표시·잘림·가림 여부가 판정되고 캡처가 남는다.
2. **Given** 같은 단계의 390px 모바일 화면, **When** 같은 확인을 하면, **Then** 1과 같은 판정과 캡처가 따로 남는다.
3. **Given** 화면이 받은 정책 식별값, **When** 지원자가 그 값으로 동의를 완료하면, **Then** 화면 값·서버 현재 값·저장된 동의 기록의
   값이 같은지 판정되고 동의 완료 시각과 합성 지원자 식별자가 함께 남는다.
4. **Given** 한 화면에서만 항목이 잘리거나 가려짐, **When** 판정하면, **Then** 다른 화면의 결과와 섞이지 않고 해당 화면의 assertion이
   FAIL이다.

### User Story 2 - 정책 교체 구간의 동의 귀속을 확인한다 (Priority: P2)

N-03. 합성 지원자가 동의 화면에서 정책 식별값을 읽은 뒤, 이전 정책 식별값으로 낸 동의가 거부되는지, 최신 정책을 다시 읽고 낸
동의가 정상 저장되는지, 이미 완료된 다른 지원자의 과거 동의가 바뀌지 않는지 확인한다. 실행 중 정책 교체·근접 제출·분석 작업
정책 귀속은 범위 밖이며 결과의 미검증 범위로 적는다(FR-031). 공식 표기는 "N-03 일부 실행"이다.

**Why this priority**: 원천 기준선 2절상 낡은 정책 거부만 대상이 있고 교체 수단과 분석 귀속 저장 필드가 없어 일부만 실행한다.

**Independent Test**: N-03 Run 한 건으로 이전·최신 식별값, 거부 응답, 최종 저장 기록, 과거 동의 기록 전후를 봉인한다.

**Acceptance Scenarios**:

1. **Given** 이전 정책 식별값, **When** 그 값으로 동의를 제출하면, **Then** 거부되고 그 지원자의 동의 기록·동의 상태가 생기거나
   바뀌지 않는다.
2. **Given** 1의 지원자, **When** 최신 정책을 다시 읽고 그 값으로 제출하면, **Then** 동의가 저장되고 저장 기록의 식별값이 다시 읽은
   값과 같다.
3. **Given** 시험 전에 동의를 완료한 별도 합성 지원자, **When** 1·2 뒤 그 기록을 다시 읽으면, **Then** 기록이 시험 전과 같다.
4. **Given** 봉인된 N-03 Run, **When** 결과를 보면, **Then** 교체 주입·근접 제출·분석 작업 정책 귀속이 판정 없이 미검증 범위로
   표시되고 후속 조건이 함께 보인다.

### User Story 3 - 결과와 한계를 기존 워크벤치에서 검토한다 (Priority: P2)

검증 책임자와 결과 검토자는 두 시나리오의 Run 결과를 기존 웹 워크벤치에서 다른 시나리오와 같은 방식(조건·기대·관찰·근거,
판정과 사유 코드, 복구 상태, 미검증 범위)으로 읽는다. 각 시나리오·결과 화면은 필요한 대상 접근 종류를 한 줄로 보이고, 격리
환경의 한계를 함께 보여 준다.

**Independent Test**: 봉인된 Run 하나를 워크벤치에서 열어 assertion별 기대·관찰·증적 링크와 한계 표시를 확인한다.

**Acceptance Scenarios**:

1. **Given** 두 시나리오 중 하나의 봉인 Run, **When** 워크벤치에서 열면, **Then** 기존 시나리오와 같은 화면 구조로 assertion별 결과와
   증적이 보인다.
2. **Given** 시나리오 화면이나 결과 화면, **When** 열면, **Then** 그 시나리오의 대상 접근 종류가 한 줄로 보이고, N-03은 미검증
   범위가 함께 보인다.
3. **Given** closure 전, **When** 카탈로그를 보면, **Then** 두 시나리오의 공식 상태는 `NOT_RUN`이고 12/7/2/3 숫자가 바뀌지 않는다.

---

### User Story 4 - 최초 결과를 보존하고 수정 후 재시험한다 (Priority: P3)

Spec 003·006·007과 같다. 최초 FAIL·INCONCLUSIVE는 봉인 뒤 덮어쓰지 않고, 원인을 분류한 뒤 승인된 수정이 있으면 같은 프로필의
parent-linked child Run으로만 재시험한다.

**Acceptance Scenarios**:

1. **Given** 최초 Run의 FAIL, **When** 수정 후 재시험하면, **Then** 새 child Run이 생기고 부모의 판정·증적·manifest는 바뀌지 않는다.

### Edge Cases

- 고지 항목이 접힘·펼침 영역 안에 있으면, 동의 제출 전 그 단계 안에서 도달할 수 있는 상태를 기준으로 판정하고 필요한 조작
  (스크롤·펼침)을 증적에 남긴다. 펼치지 않고도 동의 제출이 가능하다는 사실은 따로 관찰로 기록한다.
- 390px에서 항목을 읽으려면 가로 스크롤이 필요하면 잘림으로 본다. 세로 스크롤은 허용한다.
- 화면 텍스트에는 항목이 있지만 화면 영역 밖이거나 다른 요소에 덮여 있으면 표시되지 않은 것으로 본다. 텍스트 존재만으로
  PASS하지 않는다.
- 화면이 받은 정책 식별값과 저장 기록의 값이 다르면 N-01 FAIL이다. 화면 값을 읽지 못했으면 PASS·FAIL을 주장하지 않고
  `INCONCLUSIVE`(`INSUFFICIENT_EVIDENCE`)다.
- N-03의 "이전 정책 식별값"은 실제 교체 없이 만든 값이므로(FR-031) 그 사실을 결과의 한계로 표시한다.
- 과거 동의 기록 불변 확인에 쓰는 지원자는 Run 소유 합성 지원자이며 다른 Run·lane과 공유하지 않는다.
- 지원자 앱이 켜져 있지 않거나 응답하지 않으면 N-01은 `ACCESS_BLOCKED`(화면 접근 없음)다. 브라우저 실행 파일이 없는 것은
  실행기 준비 문제라 `RUNNER_NOT_READY`다(FR-004).

## Requirements *(mandatory)*

### Functional Requirements

#### 공통 — 대상·준비·판정 단위

- **FR-001**: 두 시나리오는 `LOCAL_EMULATED` 격리 WhyYou 대상에서만 실행한다. 외부 AI 차단, 소스 clean, 대상 버전 확인을 기존
  preflight 계약대로 요구하고 실제 AWS는 `NOT_RUN`으로 둔다.
- **FR-002**: N-01·N-03은 시나리오 ID·실행 프로필·시나리오 정의·Run·bundle·재시험 계보를 각각 따로 가진다. 준비·관찰·봉인 구현은
  공유할 수 있으나 한 Run의 결과가 다른 시나리오의 판정 근거가 되지 않는다(Spec 004 FR-043 선례). 보성이 마감한 H-01·H-02 결과도
  이 두 시나리오의 판정 근거로 쓰지 않는다.
- **FR-003**: 모든 지원자·동의 기록은 Run 소유 합성 데이터이며 Run 종료 시 Run 소유 데이터만 정리하고 잔여를 확인한다.
- **FR-004**: 실행 준비 상태는 `READY`, `RUNNER_NOT_READY`, `ACCESS_BLOCKED`, `NO_TEST_TARGET`만 쓴다. 대상은 있으나 실행기·화면
  수집·시험 수단이 준비되지 않았으면 `RUNNER_NOT_READY`이며 `NO_TEST_TARGET`으로 쓰지 않는다.
- **FR-005**: 시나리오 정의마다 판정에 필요한 대상 접근 종류(화면, API, 소스 열람 중 해당하는 것)를 기록한다. N-01 = 화면 + API,
  N-03 = API다. 이 값을 Run 결과와 워크벤치의 시나리오·결과 화면에 한 줄로 보여 구매자(공급기업·채용기업)가 받는 접근에 따라
  판정 범위를 읽을 수 있게 한다. 새 화면은 만들지 않는다. 필요한 접근이 없으면 새 준비 상태 값을 만들지 않고 `ACCESS_BLOCKED`로
  둔다. 기존 열 시나리오의 접근 종류 기록은 범위 밖이다.

#### N-01 — 고지 표시

- **FR-010**: N-01은 합성 지원자를 접근·본인 확인까지 진행시킨 뒤 동의 단계를 PC 화면과 390px 폭 모바일 화면에서 각각 연다.
  PC 폭은 Plan에서 고정하고 두 폭 모두 증적에 기록한다.
- **FR-011**: 화면마다 다섯 필수 고지 항목의 표시 여부, 잘림, 가림을 항목별로 판정하고 전체 화면 캡처를 남긴다. 판정은 화면
  텍스트의 존재와 화면 영역 안의 실제 보임을 함께 근거로 한다.
- **FR-012**: 화면이 받은 정책 식별값, 서버가 제공한 현재 정책 식별값, 그 값으로 제품 흐름에서 완료한 동의의 저장 기록 식별값을
  대조한다. 동의 완료 시각과 합성 지원자 식별자를 함께 남긴다.
- **FR-013**: 고지 확인은 자료 제출·분석 시작 전 단계에서 이뤄져야 한다. 동의 전 처리 차단 자체는 N-02가 소유하므로 N-01은 다시
  판정하지 않는다.

#### N-03 — 정책 교체 구간

- **FR-030**: N-03은 이전 정책 식별값으로 낸 동의의 거부와 무변경, 최신 정책을 다시 읽고 낸 동의의 정상 저장과 식별값 일치, 이미
  완료된 과거 동의 기록의 불변을 판정한다.
- **FR-031**: 원천 기준선 2절상 WhyYou에는 실행 중 정책을 바꿀 수단이 없고 분석 작업에 정책 버전이 저장되지 않는다. 이번
  Spec은 FR-030의 세 항목(N03-A1~A3)만 판정하고, 이전 정책 식별값은 실제 교체 없이 직접 보내 만든다. 실행 중 정책 교체 주입,
  근접 제출, 분석 작업의 정책 귀속은 FAIL·INCONCLUSIVE로 판정하지 않고 결과의 미검증 범위로 적는다. 후속 조건은 "WhyYou
  시험용 정책 교체 수단과 분석 작업 정책 귀속 저장 필드"다. 공식 표기는 "N-03 일부 실행"이다.
- **FR-032**: 정책 교체 주입은 이번 범위 밖이므로 WhyYou에 교체 수단을 만들지 않고 N-03 Run은 정책을 바꾸지 않는다. 후속 Spec이
  교체 주입을 넣을 때는 local/test 전용·Run·대상 allowlist·종료 전 원래 정책 복구와 안전 상태 확인을 조건으로 한다.

#### 공통 — 판정·증적·복구·표시

- **FR-050**: assertion별 PASS·FAIL·INCONCLUSIVE를 기존 판정 모델로 낸다. PASS·FAIL은 기대·관찰·근거로 사유를 제시하고
  INCONCLUSIVE에는 D-011 사유 코드를 요구한다. 시나리오 Run의 전체 PASS는 그 시나리오의 필수 assertion이 모두 PASS일 때만이다.
- **FR-051**: 증적은 기존 봉인·`verify`·redaction 계약을 따른다. 자격 증명·토큰·쿠키 원문과 실제 개인정보는 봉인하지 않는다.
- **FR-052**: 상태 변경을 쓴 Run은 종료 전 복구하고 안전 상태를 확인한다. 미확인이면 `RESTORE_FAILED`(판정 INCONCLUSIVE)로 두고
  같은 대상의 후속 주입을 차단한다.
- **FR-053**: 최초 FAIL·INCONCLUSIVE는 봉인 뒤 덮어쓰지 않는다. 원인을 대상 결함·실행기 결함·복구 운영 결함으로 분류하고, 대상
  결함 수정은 최초 사실 봉인 뒤 결정 기록과 승인을 거쳐 개인 브랜치에서 실패 시험부터 한다. 검증은 parent-linked child Run으로만
  한다.
- **FR-054**: 새 결과는 기존 웹 워크벤치에서 기존 화면 구조·상태 이름으로 보인다. 웹에서 Run·재시험을 시작하지 않는다(D-018).
- **FR-055**: 실제 Run과 closure 전까지 범위표·카탈로그·README의 두 시나리오 상태와 12/7/2/3 숫자를 바꾸지 않는다(D-030 3항).
- **FR-056**: 모든 결과는 실행한 시나리오와 증적의 범위만 주장하며 합성 데이터·`LOCAL_EMULATED`·외부 AI 차단·사용한 시험 수단을
  한계로 표시한다. 법적 준수 전체를 검증했다고 표현하지 않는다.

### Assertion Contract (초안)

각 assertion은 해당 시나리오 Run에서만 판정한다. 세부 판정 규칙과 증적 매핑은 Plan의 계약에서 고정한다.

| ID | 주장 | 판정 근거 |
|---|---|---|
| N01-A1 | PC 화면에 다섯 필수 고지가 읽을 수 있게 표시된다 | PC 캡처, 항목별 텍스트·보임 판정 |
| N01-A2 | 390px 모바일 화면에 다섯 필수 고지가 잘림·가림 없이 표시된다 | 모바일 캡처, 항목별 텍스트·보임 판정 |
| N01-A3 | 화면 정책 식별값이 서버 현재 값·저장된 동의 기록과 같다 | 세 값, 동의 완료 시각, 지원자 식별자 |
| N03-A1 | 이전 정책 식별값의 동의는 거부되고 동의 기록·상태가 바뀌지 않는다 | 거부 응답, 시도 전후 동의 기록·상태 |
| N03-A2 | 최신 정책 재확인 뒤 동의는 저장되고 식별값이 재확인한 값과 같다 | 재조회 값, 저장 기록 |
| N03-A3 | 이미 완료된 과거 동의 기록은 바뀌지 않는다 | 과거 기록 전후 비교 |

N-03의 교체 주입·근접 제출·분석 작업 정책 귀속은 assertion이 아니라 미검증 범위 항목이다(FR-031).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 두 시나리오 각각에 봉인된 Run이 1건 이상 있고, 그 Run의 필수 assertion 100%가 PASS·FAIL·INCONCLUSIVE 중 하나로
  판정되며 INCONCLUSIVE는 100% 사유 코드를 가진다.
- **SC-002**: 두 시나리오의 봉인 bundle은 100% `verify` 결과 VERIFIED이고, 자격 증명·토큰·쿠키 원문과 실제 개인정보가 들어간
  파일은 0건이다.
- **SC-003**: N-01 Run은 PC와 390px 두 화면 각각에서 다섯 항목 전부(5/5)를 판정하고 두 화면 캡처와 세 출처의 정책 식별값을
  남긴다. 한 화면의 한 항목을 가린 고정 FAIL fixture는 그 화면의 assertion만 100% FAIL로 판정된다.
- **SC-004**: N-03 Run은 이전 식별값 제출 거부와 최신 재확인 저장을 모두 판정하고, 과거 동의 기록의 변경 건수 0을 확인한다.
  결과의 100%가 교체 주입·근접 제출·분석 작업 정책 귀속을 판정 없이 미검증 범위로 표시하고 후속 조건을 함께 보인다.
- **SC-005**: 상태 변경을 쓴 Run의 100%가 종료 전 복구·안전 상태 확인을 거치고 Run 소유 잔여 데이터가 0건이다. 복구
  실패 fixture는 100% `RESTORE_FAILED`와 후속 주입 차단으로 나타난다.
- **SC-006**: 재시험 뒤 부모 Run의 판정·증적·manifest 변경 건수는 0건이다.
- **SC-007**: 준비된 격리 환경에서 실행 담당자는 시나리오별 Run 한 건과 bundle 검증을 10분 안에 끝낼 수 있다.
- **SC-008**: 두 시나리오의 봉인 Run은 기존 워크벤치에서 새 화면 없이 열리고, assertion별 기대·관찰·증적과 한계 표시가 다른
  시나리오와 같은 항목으로 보인다.
- **SC-009**: closure 전 범위표·카탈로그·README에서 두 시나리오 상태나 12/7/2/3 숫자가 바뀐 건수는 0건이다.
- **SC-010**: 결과 설명의 100%가 실행한 시나리오·`LOCAL_EMULATED`·합성 데이터 범위만 주장하며, A 계열·실제 AWS·법적 준수
  전체를 검증했다고 표현한 경우는 0건이다.
- **SC-011**: 두 시나리오 정의·봉인 Run 결과·워크벤치 시나리오·결과 화면의 100%가 FR-005의 대상 접근 종류를 한 줄로 보인다.

## Assumptions

- Spec 001~004의 Run·관찰·증적·판정·복구·불변 재시험·대상 스냅샷 계약과 Spec 005 워크벤치 표시 계약을 재사용한다. 보성이 Spec
  006·007에서 더한 프로필 등록·증적 계약 방식(H-01·H-02)을 같은 모양으로 따른다.
- 기준 source는 ControlProof `b76af4c`, WhyYou `0166d9e`(D-030)이며, 원천 기준선이 다루는 동의·지원자 앱 코드는 `33aa996`·`374b122`와
  같다. 기준이 바뀌면 원천 기준선을 다시 만든다.
- N-01의 판정 범위는 V4 §10.1의 다섯 항목이다. 이의제기 고지는 대상 기능이 없어 확인하지 않는다(V4 §7.1).
- Spec 009 closure 작업: 범위표 §3과 카탈로그의 N-03 질문을 V4 §10.3 기준 "정책 교체 구간에서 동의가 지원자가 실제로 읽은
  버전에 귀속되는가"로 고친다. N-03은 "N-03 일부 실행"으로 실제 실행 수에 넣고 범위표·카탈로그·워크벤치에 미검증 범위를 항상
  같이 보인다. 그 전에는 범위표·카탈로그를 고치지 않는다(FR-055).
- 390px 모바일 판정에서 세로 스크롤은 허용하고 가로 스크롤이 필요하면 잘림으로 본다.
- 최초 actual Run 전에 확인되지 않은 WhyYou 결함을 미리 고치지 않는다(V4 §7.3).
- 실제 Run마다 사용자 승인을 받는다(D-030 5항).
